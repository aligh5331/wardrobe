### [ING-035] Integration test: interactive create + edit round trip and create-failure recovery

**As a** wardrobe owner
**I want** one black-box acceptance test that drives the real interactive
create/edit API end to end — upload, draft, persist, fetch, update — plus the
create-failure cleanup path
**So that** the settled contracts in `06-decisions.md` are verified against a
running router and the real store/photo code, not only against per-endpoint
units

**Acceptance criteria** (Gherkin):
```
Given the real Gin engine from internal/api built against an isolated temp data
  root and a local stub VLM (the existing newING012VLM-style test server)
When the test uploads a garment photo (POST /api/items/photo), corrects the
  returned draft's tagging fields, persists it (POST /api/items), fetches it
  (GET /api/items/:id), and updates it (PUT /api/items/:id)
Then the full round trip succeeds: exactly one row exists with the corrected
  values, exactly one photo is stored under data/photos/<item_id>.<ext>, the
  staged upload is gone, and the earlier and updated reads reflect the changes —
  proving the four approved routes compose into one flow

Given a persist that fails at the photo/filesystem write (e.g. data/photos is
  pre-occupied so the move cannot complete)
When the create returns an error
Then the test observes no catalog row for that id and no orphan photo in
  data/photos/ (06-decisions.md "Catalog writes must not leave orphan photos or
  dangling rows"), and the failure surfaces rather than being swallowed

Given the shared persistence contract (ING-028)
When cmd/ingest and the API each persist the same item id and tagging fields
  into separate isolated roots
Then both produce an equivalent result — same seven field values, same
  added_date-at-create semantics, empty notes, and the same
  data/photos/<item_id>.<ext> photo_path shape and stored bytes — confirming
  one implementation (internal/catalog) rather than two copies

Given the test suite
When it runs
Then it is stdlib-only (testing / net/http/httptest), adds no runtime
  dependency or model, follows the existing integration-test conventions
  (build tag, moduleRoot, stub VLM), and never reads or writes the repo's real
  data/ (personal wardrobe data)

Given a corrected record that fails taxonomy validation
When it is PUT to an existing id
Then the test observes 400 naming the field and the stored row is unchanged —
  the integration-level check of the write-path validation contract
```

**Spec reference:** `07-architecture.md` "Backend" → "Catalog write API
(interactive create/edit)" (the four routes and their composition; invalid field
400 naming the field, unknown id 404; staged uploads removed on save/failed
create); `06-decisions.md` "Interactive catalog create/edit UI" (upload → human

"Write-path rules (interactive create/edit)"; baseline suites

(read API + stub-VLM harness).

Findings:

- **Not tautological / not over-mocked.** AC1 drives the real `api.New` Gin
  engine with only the VLM boundary stubbed (in-process `httptest`, ING-005
  pattern) against `t.TempDir()` roots, then asserts the store row, the
  `data/photos/<id>.jpg` bytes, the emptied staging dir, and both GETs — a

- **Create-failure contract is really exercised.** AC2's induction (occupying
  `data/photos` with a regular file) fails inside `catalog.Create`'s
  `os.MkdirAll`, i.e. the filesystem write path the ticket scopes; the test then
  verifies the occupier is untouched, `List()==0` / `Get==ErrNotFound`, a
  surfaced non-2xx with a non-empty `error`, and the staged upload removed. The
  insert-failure rollback remains ING-028's unit-level scope, as the ticket
  states.

  `ParseTaggingResult` path (invalid enum, invalid category/subcategory pair,

  the real engine in separate isolated roots with identical fields/bytes and
  checks field equality, `added_date` create-window semantics, the
  `data/photos/<id>.jpg` shape, stored-byte equality, one row/photo per writer,
  plus the `catalog.Create(` call-site check.

  `moduleRoot` and existing helpers reused; every root is `t.TempDir()`, so the
  repo's real `data/`/`logs/` are never read or written. No runtime dependency,
  no model, no cloud, no fine-tuning, one photo per garment — no hard-constraint
  violation.
