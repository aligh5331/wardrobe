### [ING-015] Build the ingest CLI's VLM client in a single call

**As a** wardrobe owner
**I want** `cmd/ingest` to construct its VLM client once, conditionally adding
the serialization option instead of re-running the constructor in an `if`/`else`
**So that** the config→client wiring has one copy that cannot drift from itself

**Acceptance criteria** (Gherkin):
```
Given VLM_SERIALIZE_REQUESTS is true or false
When the ingest CLI processes a photo
Then its observable behavior is unchanged: the temperature is read fresh
  per call, no serialization queue is used when the flag is false, and the
  configured post-response delay applies when it is true

Given the existing suite is run
When go build ./..., go vet ./..., and go test ./... run
Then all three are clean/green
And no new test file or test function is added for this refactor, and no
  existing test file is modified
```

"One `NewClient` call instead of two" is a diff-level implementation claim,
not observable behavior — the single-call and duplicated-call forms are
indistinguishable from outside the process. Confirm it by reading
`cmd/ingest/main.go`, **not** by writing a test that inspects the source.
The existing `tests/ing_012_cli_test.go` already guards the config→client
behavior (temperature per call, serialized queue with delay) and stays the
regression guard here.

**Spec reference:** `07-architecture.md` "VLM request behavior" and "Env var
contract" (`VLM_SERIALIZE_REQUESTS`, `VLM_REQUEST_DELAY_MS`,
`VLM_TEMPERATURE`); `06-decisions.md` "VLM request concurrency" and "Malformed
VLM output: retry once at nonzero temperature, then flag"

**Status:** Done

**Context:** Audit finding (duplication): `cmd/ingest/main.go` (lines 38–50)
calls `tagging.NewClient` twice in an `if`/`else`, repeating the
`WithTemperature` option so the serialize branch has a second, parallel copy
of the wiring. The constructor's option set is the natural place to vary one
option without duplicating the rest. Behavior-preserving only — the
temperature getter (ING-007) and the serialization delay (ING-003) semantics
must not change.

**Files:** `cmd/ingest/main.go` only.

## Implementation notes

Single-call config→client wiring in `cmd/ingest/main.go` only.

**Change**
- Removed the duplicate `tagging.NewClient(...)` from the
  `if cfg.VLMSerializeRequests` branch.
- Built the option set once and passed it to one constructor call:

  ```go
  opts := []tagging.Option{
      tagging.WithTemperature(func() float64 { return cfg.VLMTemperature }),
  }
  if cfg.VLMSerializeRequests {
      opts = append(opts, tagging.WithSerialization(cfg.VLMRequestDelayMS))
  }
  client := tagging.NewClient(cfg.VLMURL, cfg.VLMAPIKey, opts...)
  ```

- Exactly one `NewClient` call remains (`cmd/ingest/main.go:44`), confirmed
  by reading the file + `grep NewClient` (the ticket asks for a diff/source
  check here, not a test).

**Behavior preservation** (`07-architecture.md` "VLM request behavior" /
"Env var contract"; `06-decisions.md` "VLM request concurrency")
- `WithTemperature` is always present with the same getter closure, so the
  temperature is still read fresh per request — ING-007 semantics unchanged.
- `VLM_SERIALIZE_REQUESTS=false`: the option set is exactly
  `[WithTemperature]` — no serialization queue, concurrent default preserved
  (ING-003).
- `VLM_SERIALIZE_REQUESTS=true`: the option set is
  `[WithTemperature, WithSerialization(cfg.VLMRequestDelayMS)]` — the
  post-response delay applies exactly as before.
- Option order is unchanged (`WithTemperature` then `WithSerialization`), and
  the two options set disjoint `Client` fields (`temperature` vs
  `serialize`/`delay`), so ordering cannot change the resulting client.
