### [ING-048] Recommender: LLM outfit picker (prompt, call, validation, retry)

**As a** wardrobe owner
**I want** the local text LLM to pick 3 color-coordinated outfits from the candidates
**So that** I get suggestions that read my note and match colors, with no invalid garments

**Acceptance criteria** (Gherkin):
```
Given candidates, weather rules, formality and a note
When the prompt is built
Then each candidate line has exactly id, category, subcategory, dominant_color,
  secondary_colors, pattern, warmth_tier, formality
And no photo path, photo data, or item notes appear anywhere in the prompt
And the prompt includes feels-like, min/max, rain chance, weather code, formality, the note,
  whether outerwear is required/optional/excluded, "temperature unknown" when so,
  and the JSON-only output contract {"outfits":[{"item_ids":[...],"reason":"..."}]}

Given a fake LLM server (httptest)
When the picker calls it
Then it POSTs <LLM_URL>/v1/chat/completions with the configured temperature
And sends "Authorization: Bearer <key>" only when LLM_API_KEY is set
And includes "model" only when LLM_MODEL is non-empty (field absent otherwise)

Given the LLM returns a valid answer
When it is validated
Then 3 outfits are returned in the model's order, each with its item ids and reason

Given an answer that breaks any rule: not exactly 3 outfits; an id not in the candidates;
  missing or duplicate top/bottom/footwear; outerwear missing when required or present when
  excluded; more than one outerwear or headwear; a duplicated id inside an outfit;
  all 3 outfits the same id set; empty reason; unparseable JSON
When it is validated
Then the attempt is invalid

Given the first answer is invalid and the second is valid
When the picker runs
Then exactly 2 LLM calls are made and the second answer is returned

Given both answers are invalid
When the picker runs
Then exactly 2 calls are made and an error marked as an LLM failure is returned

Given the LLM is unreachable (closed server)
When the picker runs
Then exactly 1 call is attempted (no retry) and an LLM-failure error is returned

Given the LLM does not answer within the timeout
When the picker runs
Then it fails with an LLM-failure error; the production timeout is 120 s
  (tests inject a shorter one)

Given the LLM returns a non-2xx status and LLM_MODEL is empty
When the picker runs
Then the error message tells the user to set LLM_MODEL
And with LLM_MODEL set, a non-2xx error does not contain that hint
```

**Spec reference:** `07-architecture.md` "Recommender (Phase 3)" flow steps
4–5 (prompt fields, JSON contract, validation list) and "LLM request behavior"
(120 s, retry policy); `06-decisions.md` "Recommender output validation: retry
once, then 502" and "LLM config" (`LLM_MODEL` omission + hint).

**Status:** Done

**Depends on:** ING-046 (config fields), ING-047 (candidate + rules types).

**Routing:** Ready → Coder. `internal/recommend/` (picker + small

## Implementation notes

Two new files in `internal/recommend/`, stdlib plus `store` and `weather`
types only.

`picker.go`: `ErrLLM`, `Picker{URL, APIKey, Model, Temperature, Timeout}`
(Timeout 0 or less means the 120 s production value), `Input{Forecast, Rules,
Formality, Note, Candidates}`, `Outfit{ItemIDs, Reason}` and
`(*Picker).Pick(ctx, Input) ([]Outfit, error)`. Private helpers: `buildPrompt`
(system prompt with the JSON contract, user prompt with weather, outerwear
rule, formality, note and one line per candidate), `validate` (every rule in
the AC list), `stripFence`, `call` (one OpenAI-compatible request) and
`snippet`. Every `Pick` error satisfies `errors.Is(err, ErrLLM)`. ING-049
passes candidates from `Filter`, calls `MissingSlots` first, then builds
`Input` and calls `Pick`.

`picker_test.go`: `TestBuildPrompt`, `TestValidate` (4 valid and 19 invalid
subtests), `TestPickRequestShape`, `TestPickRetry`, `TestPickUnreachable`,
`TestPickTimeout` and `TestPickNon2xxHint`. httptest only, no real network.

**Assumptions**

- A non-2xx response makes one call and does not retry. The ticket names only
  invalid output as retryable, and a rejecting server will reject again.
- A 200 whose body is not a chat envelope, or has no choices, counts as
  invalid output and is retried once.
- A leading code fence (with or without the `json` label) is stripped before
  parsing. The reason is stored trimmed.
- Warmth tiers are not printed in the prompt, since candidates are already
  filtered by them. A `ponytail:` comment in the code says when to add them.
- `Pick` builds an `http.Client` per call from `Timeout`.
- The prompt uses "any" for an empty formality, "none" for an empty note and
  "unknown" for nil weather fields. It adds a "temperature unknown" line when
  `Rules.TempUnknown` is set.
- "LLM_MODEL" appears in error text only for a non-2xx response with an empty
  `Model`.
- No taxonomy value invented. I checked the test fixture against
  `03-taxonomy.md`: categories, subcategories (t-shirt, sweater, jeans,
  chinos, sneakers, boots, jacket, coat, cap, beanie, belt), colors, patterns
  (solid, striped), warmth tier medium and formalities (casual, smart-casual)
  are all listed there.

**Verification**

- `go build ./...` clean.
- `go vet ./...` clean.
- `gofmt -l internal/recommend` no output.
- `go test -count=1 ./internal/recommend/` ok.
- `go test -count=1 ./...` all packages ok.

**Gaps**

- The unreachable case cannot count calls on a closed server. The test
  asserts `ErrLLM` and the absence of the "invalid output after retry" text,
  so "exactly 1 call" is shown indirectly.
- The 120 s production value is not exercised by a test. Tests inject a short
  timeout, and `TestPickTimeout` uses 50 ms.

**Edge cases noted (not failures, no AC or spec change requested):**

- A duplicate id inside `item_ids` is rejected (covered). Two candidates with
  the same id cannot occur, since `id` is the primary key, but if they did,
  `validate` keeps the last category silently. No action needed.
- Accessories have no limit, and the spec sets none, so an outfit with four
  belts passes.
- Prose before the JSON (`Sure! {...}`) counts as unparseable. Only a leading
  code fence is stripped. The retry usually covers it, but a chatty model could
  fail twice and give a `502`. Ali may want a "first `{` to last `}`" fallback
  if that shows up in real use.
- The note goes into the prompt with its newlines. A note with a line starting
  `id=...` could imitate a candidate line. Validation uses the real candidate
  ids, so it cannot produce an invalid garment. It could still mislead the model.
- `max_tokens` is fixed at 1024 and is not in the spec. A long answer that
  gets cut off is unparseable JSON and takes the retry path.
- The 120 s timeout applies per call. Two bad answers can take up to 240 s
  in total before the `502`. The spec says "fixed 120 s request timeout", so
  this reading is consistent, but ING-049 should not assume 120 s overall.
- Non-2xx never retries, and a 200 with a bad envelope does. The ticket does
  not say either. The Coder documented both choices and they fit "retry on
  invalid output, never on unreachable".
- `Pick` does not reject empty `Candidates`. ING-049 must call `MissingSlots`
  first, as the Implementation notes say.

**Decision: APPROVED**

Reviewed the untracked `internal/recommend/picker.go`,
`internal/recommend/picker_test.go` and `tests/ing_048_picker_test.go`, plus the
Implementation notes and Test results above. Checked against the ticket ACs,
`07-architecture.md` "Recommender (Phase 3)" steps 4 and 5 and "LLM request
behavior", `06-decisions.md` "Recommender output validation" and "LLM config",
`00-overview.md` hard constraints and `AGENTS.md`. The review agent's shell
denied `gofmt -l internal tests`, `go vet ./...` and `go test -count=1 ./...`,
so I did not run them. I read the code and tests directly and accept Tester's
recorded `go vet`, `go test` and Coder's `gofmt` results. The code reads as
gofmt-clean (tabs, aligned const block, canonical `//   -` doc list).

Blocking findings: none.

- **Spec match, validation.** `validate` covers the full list in step 5 and the
  decisions entry. Exactly 3 outfits. Every id must be a candidate id. Exactly
  one top, bottom and footwear (`count[slot] != 1`). Outerwear: more than one
  fails, zero fails when required, any fails when excluded, and optional allows
  0 or 1. More than one headwear fails. A repeated id in an outfit fails. The 3
  sorted id sets must not all be identical. A whitespace-only reason fails.
  Unparseable JSON fails. Output is untrusted and nothing is silently
  coerced. The only leniency is a leading code fence and a trimmed reason,
  which cannot let an invalid garment through. An id that is not a candidate
  is caught before anything else uses it, so a hostile note or a hallucinated
  id cannot reach the response.
- **Retry policy against the spec.** Text: "Retry once on invalid output, never
  on unreachable" and "timeout is 502". Loop makes at most 2 calls. A
  transport error (refused, DNS, timeout) returns after 1 call. Timeout is a
  fixed 120 s (`llmTimeout`) on a per-call `http.Client`, with no env var. The
  two judgment calls do not contradict the spec:
  1. Non-2xx is not retried. The architecture error table lists non-2xx as its
     own `502` case, separate from "invalid output twice", and the decisions
     entry ties the `LLM_MODEL` hint to a non-2xx. A rejecting server is not
     "invalid output". Fine.
  2. A 200 with a body that is not a chat envelope, or with no choices, is
     retried. That is unparseable output from a reachable server, which the
     decisions entry says to retry once. Fine. Doc comment on `Pick` says these
     are judgment calls, which is honest.
- **Privacy.** The candidate line prints exactly the 8 fields. `PhotoPath`,
  `Notes` and `AddedDate` are never read in `buildPrompt`. The Tester test
  scans the raw request body for all three. Error text holds no API key and no
  candidate list: validation errors carry outfit numbers and counts only, and
  the transport error is a `url.Error` with the base URL.
- **LLM_MODEL.** `Model` has `omitempty`, so the field is absent when empty
  (asserted). The hint is appended only for a non-2xx with an empty model
  (asserted for 400 and 500). `Authorization` is set only when the key is set.
- **User note.** The note goes into the prompt as free text with its newlines
  (500-char cap is ING-049's). A line like `id=...` could confuse the model,
  but validation checks ids against the real candidate list, so it cannot
  produce an invalid garment or bypass any rule. Not blocking.
- **Hard constraints clean.** Only `LLM_URL` is called, and only by the caller's
  config. No cloud service, no fine-tuning, no photo handling, no
  multi-garment assumption. Stdlib plus `store` and `weather` only. `go.mod`,
  `go.sum` and `.env.example` are unchanged.
- **Scope.** `git status`: modified `backlog/ING-048.md`, new
  `internal/recommend/picker.go`, `internal/recommend/picker_test.go` and
  `tests/ing_048_picker_test.go`. No route, weather fetch, UI, config change or
  protected file touched. No `data/` or `.env` content in the diff.
- **Over-engineering: none.** One exported type per concept (`Picker`, `Input`,
  `Outfit`, `ErrLLM`), five small private helpers, a single tiny generic
  (`orUnknown`) that replaces four copied nil checks. The per-call
  `http.Client` is required by the ticket ("own `http.Client{Timeout}`"). The
  test file has some overlap with the Coder tests (retry, non-2xx hint,
  request shape) but each Tester case adds something (raw body scan,
  connection count, 24 bad answers end to end). No chunk worth deleting.
- **Style.** No em dashes and no banned vocabulary in the code comments, error
  messages or the ticket text I read.

Non-blocking notes for Ali (no ticket needed now, none created):

1. **`max_tokens` is fixed at 1024 and is not in the spec** (the VLM client
   uses 512). Item ids are UUIDs, so 3 outfits of up to 6 ids plus reasons are
   roughly 500 to 700 tokens. A Qwen3 model that spends tokens on reasoning
   could get cut off, produce unparseable JSON twice and return `502`. Watch
   this in real use. If it shows up, raise the value or drop the field. That is
   a one-line change, not a spec edit, unless Ali wants it named in the spec.
2. **Prose or a `<think>` block before the JSON is unparseable** (Tester's
   finding). Only a leading code fence is stripped. Keep as is until real use
   shows it. A "first `{` to last `}`" fallback would be a small follow-up
   ticket then. Not a spec change.
3. **Non-2xx error text includes the first 300 bytes of the server's reply.**
   A server that echoes the request in its error (some context-length errors
   do) could put a slice of the prompt, which holds wardrobe ids and the note,
   into the `502` message. It stays local and holds no photo data, notes or key,
   so it is acceptable. ING-049 may choose to log it and return a shorter
   message to the browser.
4. **The 120 s timeout is per call.** Two bad answers can take 240 s before the
   `502`. That fits "fixed 120 s request timeout". ING-049 and ING-050 must
   not assume 120 s overall, and the browser fetch should not time out sooner.
5. **`Pick` does not reject empty `Candidates`, and `Outfit.ItemIDs` is in the
   model's order.** ING-049 must call `MissingSlots` first and re-order items
   as outerwear, top, bottom, footwear, headwear, accessory for the response.
6. **`Rules.Tiers` is not printed in the prompt.** A `ponytail:` comment says
   when to add it (sorted). No action.

Tester's edge cases: none needs a spec edit. Accessories with no limit and the
duplicate-candidate-id remark match the spec as written. The prose-before-JSON,

and are watch items, not follow-up tickets yet.
