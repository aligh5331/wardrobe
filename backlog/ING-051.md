### [ING-051] Config: parse and validate `LOG_LEVEL` and `LOG_FORMAT`

**As a** wardrobe owner
**I want** `LOG_LEVEL` and `LOG_FORMAT` validated at startup like the other
`VLM_*` vars
**So that** a typo in a logging setting fails fast naming the variable instead
of silently choosing the wrong level or format

**Acceptance criteria** (Gherkin):
```
Given LOG_LEVEL and LOG_FORMAT are both unset (or empty)
When config.Load runs
Then the resolved config carries LogLevel "info" and LogFormat "text"
And no warning is produced for either

Given LOG_LEVEL is one of debug, info, warn, error in any letter case
  (for example "WARN" or "Debug")
When config.Load runs
Then Config.LogLevel is the lower-case name ("warn", "debug")
And Load returns no error

Given LOG_FORMAT is one of text, json in any letter case (for example "JSON")
When config.Load runs
Then Config.LogFormat is the lower-case name ("json")
And Load returns no error

Given LOG_LEVEL is an unrecognized value (for example "verbose")
When config.Load runs
Then Load returns a startup error whose message names LOG_LEVEL
And no fallback level is silently used

Given LOG_FORMAT is an unrecognized value (for example "yaml")
When config.Load runs
Then Load returns a startup error whose message names LOG_FORMAT
And no fallback format is silently used

Given the existing VLM_* and LLM_* contract
When the two logging vars are added
Then Load still validates VLM_URL and the other VLM and LLM vars exactly as before
And the existing config tests still pass
```

**Spec reference:** `07-architecture.md` "### Env var contract", the
`LOG_LEVEL` row ("one of `debug`, `info`, `warn`, `error` (case-insensitive).
Anything else is a startup error naming the variable", default `info`) and the
`LOG_FORMAT` row ("one of `text`, `json` (case-insensitive)", default `text`);
`07-architecture.md` "## Logging" ("Level and format": `LOG_LEVEL` sets the
minimum level, `LOG_FORMAT` selects a text or JSON handler);
`06-decisions.md` "Structured logging: stdlib `log/slog`, local stderr + file,
env-configurable level/format" (Config bullet: validated at startup in the same
strict style as the other env vars; an unrecognized value is a startup error
naming the variable, not a silent fallback).

## Implementation notes

`internal/config/config.go`: `Config` gains `LogLevel` and `LogFormat` (both
`string`, stored lower-case). `Load` resolves them after the temperature vars
with a new helper, `enumEnv(name, fallback, allowed...)`. The helper reads the
variable, trims whitespace, lower-cases it and returns the fallback when the
result is empty. A value outside the allowed list returns an error that names
the variable, quotes the raw value and lists the accepted values. `LOG_LEVEL`
allows `debug`, `info`, `warn`, `error` (default `info`). `LOG_FORMAT` allows
`text`, `json` (default `text`).

`internal/config/config_test.go`: `LOG_LEVEL` and `LOG_FORMAT` are added to the
`setEnv` list. `TestLoad` gets two optional expectation fields, `wantLogLevel`
and `wantLogFormat`, which default to `info` and `text` when left empty. The
check runs for every non-error case, so all existing cases also assert the
defaults. 15 new table cases were added.

No `go.mod`/`go.sum`, protected file, `.env.example` or other package touched.

**Assumptions**

- Surrounding whitespace is trimmed before matching, so `" warn "` is accepted
  as `warn`, and a whitespace-only value counts as unset. The existing string
  vars `VLM_URL`, `LLM_URL` and `LLM_MODEL` are trimmed, while `boolEnv`,
  `intEnv` and `floatEnv` are not (`"TRUE "` is rejected for
  `VLM_SERIALIZE_REQUESTS`). The ticket left the choice open. Trimming follows
  the free-text vars and is the friendlier behavior for a `.env` typo.
- The error message quotes the raw value as the user typed it, not the trimmed
  form.
