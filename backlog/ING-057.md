### [ING-057] `cmd/ingest`: use the configured slog logger; stdout stays JSON-only

**As a** wardrobe owner
**I want** `cmd/ingest` to log every diagnostic through the logger built from
`LOG_LEVEL`/`LOG_FORMAT`, and to report config errors on stderr before that logger exists
**So that** level, format and sinks apply to the CLI too, and its stdout stays a strict
one-JSON-object-per-line channel for the next pipeline stage (ING-012)

**Acceptance criteria** (Gherkin):
```
Given config.Load fails (for example VLM_URL missing, or LOG_LEVEL=verbose)
When cmd/ingest runs
Then the error is logged at error level through slog.Default() on stderr in text
  format (never JSON, even if LOG_FORMAT=json is also set)
And the process exits with status 1
And stdout is empty
And no logs/app.log is created

Given LOG_LEVEL=verbose (an unrecognized value)
When the real cmd/ingest process is run with a photo path
Then it exits with a non-zero status
And a stderr line names LOG_LEVEL
And stdout is empty

Given valid config
When cmd/ingest runs
Then the ING-052 logger is built from cfg.LogLevel and cfg.LogFormat
And every later diagnostic goes through it (stderr + logs/app.log)
And nothing is written to stdout except the tagged record

Given cfg.Warnings() returns a warning (for example VLM_REQUEST_DELAY_MS=15 with
  VLM_SERIALIZE_REQUESTS=false)
When cmd/ingest runs
Then it is one warn-level record whose message contains "startup warning" and the
  warning text (for example "will not be applied")
And it is on stderr, not stdout

Given no photo path argument (valid config)
When cmd/ingest runs
Then an error-level record carries "usage: ingest <photo-path> [photo-path...]"
And the process exits with status 1
And stdout is empty
And config errors still take precedence over the usage error, as today

Given store.Open fails, a path argument cannot be expanded (for example a missing
  photo), the VLM is unreachable, processing hits a hard error, the result cannot be
  encoded, or catalog.Create fails
When cmd/ingest handles each case
Then each is one error-level record through the logger, then exit status 1 (as today)
And the record still names what today's message names: "error expanding" with the
  path, "VLM unreachable" with the photo path, "hard error processing" with the photo
  path, "encode result" with the photo path, "persist" with the photo path
And stdout carries no tagged JSON for the failing photo

Given a photo and a reachable VLM
When cmd/ingest runs with LOG_LEVEL=debug and LOG_FORMAT=json
Then stdout contains exactly one JSON object per processed photo
And every stdout line parses as a tagged record with no log record mixed in
And the same holds with LOG_FORMAT=text and LOG_LEVEL=debug

Given a successful run at the default level
When stderr is read
Then it does not mention "registry" or "wardrobe.db" or "LLM_URL"

Given the change
When cmd/ingest/main.go is read
Then it no longer imports the stdlib "log" package and contains no log.Printf or
  log.Fatalf call
And its only stdout write is the existing fmt.Println of the tagged record
And the emitted JSON shape, the retry/flag policy and the exit codes are unchanged
And it adds no dependency (go.mod and go.sum unchanged)
```

**Status:** Ready

**Context:** Split out of the entrypoint ticket (ING-054) to keep each ticket inside one
Coder pass. `cmd/ingest/main.go` has nine stdlib log calls: `log.Fatalf` x3 (config
load, usage, `store.Open`), `log.Printf` x6 (each warning, expand error, VLM
unreachable, hard error, encode result, persist). Replace all nine. The ING-054 pattern
applies: `config.Load()` first, on error `slog.Error(...)` (default logger, text,
stderr) then `os.Exit(1)`; only on success build the ING-052 logger. Keep the current
order (config, warnings, usage check, store, pipeline) so config errors still win over
the usage error.

**Windows path caveat:** several existing tests assert the raw photo path appears on
stderr (`tests/ing_012_cli_test.go`: `strings.Contains(stderr, photo)` and
`strings.Contains(stderr, missing)`), and the test paths are Windows paths with
backslashes. The slog text handler quotes any value that contains a space or quote and
escapes backslashes when it does, so a path embedded in a message (always quoted,
because messages contain spaces) would not match. Put each path in its own attribute
(for example `path=`) and keep the message text free of the path and the error text,
so the raw path appears on stderr. If a test path still gets quoted (for example a
temp dir containing a space), do not edit the assertion yourself: record it on the
ticket and flag it to Ali.

`logs/app.log` is created under the working directory; the ING-012 harness
(`newING012Harness`) runs the binary in a temp root, so use it for every new test.
