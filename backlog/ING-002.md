### [ING-002] VLM client — send one garment photo for tagging

**As a** wardrobe owner
**I want** a client that sends a single garment photo plus the tagging
prompt to `VLM_URL` and returns the raw model response
**So that** photos can be tagged by the locally running VLM

**Acceptance criteria** (Gherkin):
```
Given a valid image file path and a reachable VLM at VLM_URL
When the client sends a tagging request
Then it returns the raw text response from the model, sending an auth
  header only if VLM_API_KEY is set

Given VLM_URL is unreachable (connection refused, timeout, DNS
  failure)
When the client attempts a tagging request
Then it returns a distinct "VLM unreachable" error, separate from the
  malformed-output case handled in ING-005 — connectivity failure and
  bad model output are different failure modes and must not be
  conflated

Given multiple tagging requests are in flight at once and
  VLM_SERIALIZE_REQUESTS=false (default)
When they are sent
Then they execute concurrently with no artificial single-request queue
```

**Spec reference:** `05-vlm-tagging-spec.md` "Model" and "Prompt"
sections; `07-architecture.md` "VLM request behavior" (default
concurrent)

**Status:** Done

## Implementation notes

Implemented the VLM client in `internal/tagging` (the package the
architecture tree already reserves for it) plus a unit self-check.

**Files**
- `internal/tagging/client.go` — `Client`, `NewClient(vlmURL, apiKey)`,
  `(*Client).Tag(ctx, imagePath) (string, error)`, sentinel
  `ErrVLMUnreachable`, and the spec's tagging prompt as `taggingPrompt`.
- `internal/tagging/client_test.go` — unit self-check of request shape,
  auth-header gating, error classification, and concurrency (Tester still
  owns the acceptance suite under `tests/`).
- Removed `internal/tagging/.gitkeep` now that the package has real
  files.

**Behavior**
- `Tag` reads the photo, then `POST {VLM_URL}/v1/chat/completions` —
  llama.cpp's OpenAI-compatible endpoint per `05-vlm-tagging-spec.md`
  "Model". System message is the spec's tagging prompt sent **verbatim**;
  user message carries the image as a `data:<mime>;base64,...` part
  plus a short text part.
- `Authorization: Bearer <key>` is set **only when the key is
  non-empty**; empty key sends no header.
- Returns `choices[0].message.content` as the raw text, unvalidated —
  schema/enum validation and malformed-output handling are ING-005's job.
- **Unreachable** (connection refused, timeout, DNS) → wrapped
  `ErrVLMUnreachable`, so `errors.Is(err, tagging.ErrVLMUnreachable)`
  is true. Non-2xx status and an unusable response envelope return plain
  errors that are deliberately **not** `ErrVLMUnreachable`; empty model
  content is returned as-is so ING-005 can reject it.
- No queue or lock anywhere in the client → concurrent requests by
  default.

**Assumptions / deviations (for Tester + Reviewer)**
1. **Scope: default concurrent behavior only.** The ticket's AC3 and its
   cited section are annotated "(default concurrent)", so
   `VLM_SERIALIZE_REQUESTS=true` serialization and
   `VLM_REQUEST_DELAY_MS` are **not** implemented here. This also
   defers ING-001's open question about a negative delay to whichever
   ticket implements serialization. Needs a follow-up ticket — flagging
   for Planner/Ali rather than silently expanding scope.
2. **Wire-format choices not stated in the spec:** model name
   `"qwen3-vl"`, `max_tokens: 512`, `temperature: 0`, and a short user
   text part (`"Tag this garment in the image."`) alongside the image.
   Chosen to match llama.cpp's documented multimodal request shape and
   keep tagging deterministic. Easy to change if the model needs
   different sampling.
3. Image MIME type comes from the file extension, falling back to
   `image/jpeg` when unknown. No image content validation — that is the
   VLM's job, and the ticket says "a valid image file path".
4. The client is **not wired into `cmd/server`/`internal/api`** — no
   ticket has a route/handler yet, and none is asked for here.
5. The `*http.Client` has no built-in timeout (vision inference can be
   slow); the client is `ctx`-driven, so the eventual API handler must
   pass a context with a deadline.
6. ING-001 follow-up #3 ("VLM-client ticket must gate the header on
   `cfg.VLMAPIKey != ""` and test it") is addressed: the constructor
   takes the key, gates on non-empty, and both header-present and
   header-absent paths are unit-tested.

**Follow-ups for Planner (not failures; out of this ticket's AC scope)**

  absent/empty. That is deliberate and documented: it is raw model
  output that ING-005 must reject, not a connectivity failure, and it is
  not conflated with `ErrVLMUnreachable`. Acceptable.
