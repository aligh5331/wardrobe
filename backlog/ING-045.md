### [ING-045] Frontend: "change location" city search saving via `PUT /api/weather/location`

**As a** wardrobe owner
**I want** to search for a city and pick it as my weather location
**So that** the weather panel shows weather where I actually am

**Acceptance criteria** (Gherkin):
```
Given the weather panel is shown
When the user activates "change location" and submits search text
Then the UI calls GET /api/weather/cities?q=<text> (URL-encoded) and lists each
  result as name with admin1 and country

Given the search returns []
When results render
Then the UI shows a "no cities found" message

Given the search text is empty or whitespace-only
When the user submits
Then no request is sent (the backend would answer 400)

Given the search returns 502 or fails
When results render
Then the UI shows an error and the current location stays unchanged

Given a list of results
When the user picks one
Then the UI PUTs /api/weather/location with {name, country, latitude, longitude}
  of that result (admin1 is not sent)
And on success the panel reloads GET /api/weather and shows the new location

Given the PUT returns 400
When the response arrives
Then the server's error message (naming the field) is shown and the panel
  keeps the previous location

Given the user cancels the search
When it closes
Then no PUT is sent and the panel is unchanged
```

**Spec reference:** `07-architecture.md` "Backend" → "Weather (Phase 2)" (UI
paragraph: "change location" city search that saves via
`PUT /api/weather/location`; `cities` result shape; `PUT` body
`{name, country, latitude, longitude}`); `04-data-schema.md` "Settings —
weather location (Phase 2)"; `06-decisions.md` "Weather location: chosen in
the web UI, persisted in SQLite, default Tehran".

## Implementation notes

**Changes**
- `frontend/src/WeatherPanel.jsx`: extended (not a new component, per the
  ticket's "Routing" note) with the "change location" flow, closed by
  default:
  - `changing` state gates a "Change location" button (hidden while the
    search panel is open) vs. the search `<form aria-label="Change location">`.
  - `loadWeather()` factored out of the mount `useEffect` so it can be
    reused after a successful `PUT` (reload requirement).
  - `submitSearch`: trims the query; empty/whitespace-only returns before
    any `fetch` call (AC: "no request is sent"). Otherwise
    `GET /api/weather/cities?q=${encodeURIComponent(text)}` — encoding via
    the query-string builder, not the URL constructor, since the base is a
    relative path. Non-OK surfaces the server's `errorMessage` (same
    helper convention as `ItemAddForm.jsx`); a network-level reject is
    caught separately. Results render as `name, admin1, country` (empty
    parts filtered via `.filter(Boolean).join(', ')` — `04-data-schema.md`/
    `07-architecture.md` say `admin1`/`country` can be `""`).
  - Empty results (`[]`) render "No cities found." — distinct `searchStatus`
    ('done' with `results.length === 0`) from the error state so the two
    never collide.
  - `pickCity(city)`: `PUT /api/weather/location` with exactly
    `{name, country, latitude, longitude}` — `admin1` is never read off the
    result into the body. On success, calls `loadWeather()` (re-fetches
    `GET /api/weather`, replacing `weather`/`status` state) and then closes
    the search panel via `cancelChange()`. On a non-OK response, surfaces
    `errorMessage` (400's field-naming message per spec) and leaves
    `weather` untouched — the failed `PUT` never triggers a reload, so the
    previous location stays displayed.
  - `cancelChange()`: closes the panel, clears query/results/errors. Never
    calls `PUT`.
- `frontend/src/WeatherLocation.test.jsx` (new): 7 tests, one per AC —
  search GETs the encoded query and lists results (AC1), `[]` shows "no
  cities found" (AC2), whitespace-only text sends no `cities` request
  (AC3), a 502 search shows an error with location unchanged (AC4), picking
  a result PUTs the trimmed body (admin1 dropped) and reloads
  `GET /api/weather`, closing the panel (AC5), a PUT 400 surfaces the
  server's field-naming message with the previous location kept (AC6),
  cancel sends no PUT and leaves the panel/location unchanged (AC7). Fetch
  stubbed per method+URL with `vi.stubGlobal`, same pattern as
  `ing_034_add.test.jsx`/`WeatherPanel.test.jsx`.

**Assumptions**
- Kept everything inside `WeatherPanel.jsx` rather than a separate
  top-level component — the ticket's own "Routing" line says "Extends the
  ING-044 panel component," and the search UI has no reason to exist
  without the panel it mutates.
- Activator label "Change location" (button text) — not specified verbatim
  by the ticket; chosen to match the ticket's own phrase ("change
  location") title-cased for a button.
- Result list button label is the full `name, admin1, country` string (same
  text used for AC1's assertion) so a human and a test can both target one
  string per city; no separate "select" affordance needed since the whole
  row is one button.
- On successful save, the search panel closes automatically (`cancelChange`
  after `pickCity` succeeds) — the ticket doesn't say explicitly, but
  "shows the new location" reads most naturally as returning to the normal
  panel view, and every other write flow in this codebase (`ItemAddForm`,
  edit form) closes/resets on success.
- If `loadWeather()` itself fails right after a successful `PUT` (separate
  from the PUT failing), the code swallows that reload error and closes the
  panel anyway rather than surfacing a spurious error for a save that did
  succeed — no AC covers this compound failure; flagging here rather than
  guessing further.
- No debounce/typeahead added (explicit out-of-scope); search only fires on
  form submit.

**Spec validation**
- `07-architecture.md` "Weather (Phase 2)": `cities` query param name (`q`),
  result shape `{name, country, admin1, latitude, longitude}`, `PUT` body
  `{name, country, latitude, longitude}` (no `admin1`, no `id`) — body
  constructed by explicit key list in `pickCity`, not a spread of `city`,
  so `admin1` structurally cannot leak in.
- `04-data-schema.md` "Settings — weather location": `name` required,
  `country` optional, `latitude`/`longitude` required floats — the PUT body
  passes these through as received from the `cities` result; trimming/range
  validation is the backend's job per spec (`PUT location: ... is 400 with
  the field named`), which the 400-path test (AC6) exercises end-to-end
  through the UI's error surface rather than re-validating client-side.

**Edge cases considered, not flagged as gaps:**
- Result list `admin1`/`country` as `""` (spec L91: "a result missing
  `country` or `admin1` returns `\"\"` for it") — already exercised
  structurally by AC6's `city` fixture (`country: '', admin1: ''`); the
