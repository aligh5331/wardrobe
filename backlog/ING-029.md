### [ING-029] Catalog store: `Get` and `Update` for the interactive edit path

**As a** wardrobe owner
**I want** `internal/store` to read one item by id and update its mutable fields
**So that** the API can serve `GET /api/items/:id` and apply `PUT /api/items/:id`
without a second persistence path

**Acceptance criteria** (Gherkin):
```
Given an item id that exists
When Get(id) is called
Then the full item is returned with all 04-data-schema.md fields intact,
  including empty notes and a 0-length secondary_colors list

Given an item id that does not exist
When Get(id) is called
Then it returns an error the caller can identify as "not found" without
  importing gorm — so the API layer can map it to 404

Given an existing item and new values for the mutable fields (the seven tagging
  fields plus notes)
When Update is called
Then exactly those fields are persisted and read back changed, while id,
  added_date, and photo_path are unchanged

Given an item id that does not exist
When Update is called
Then it returns the same identifiable "not found" error and writes nothing

Given empty notes and an empty secondary_colors list
When an update writes them
Then they round-trip as "" and [] (not null), matching ING-017's read shape

Given the existing store behavior
When this change lands
Then Insert and List are unchanged and ING-017's tests still pass
```

**Spec reference:** `04-data-schema.md` "Write-path rules (interactive
create/edit)" (`id` and `added_date` are immutable; `notes` and all other fields
are editable; the photo / `photo_path` is not replaced); `07-architecture.md`
"Catalog write API" (`GET`/`PUT /api/items/:id`); `backlog/ING-017.md` (the
store surface, and its explicit out-of-scope deferral of update/delete "until a
second writer exists" — now met per `06-decisions.md` "Second catalog writer
exists").

**Status:** Review

**Context:** ING-017 built `internal/store` with `Insert`/`List` only and
deferred update/delete because `cmd/ingest` was the only writer. The approved
interactive create/edit feature makes the API a second writer, so the edit path
needs `Get` and `Update`. This ticket adds only those two operations; the write
validation (`03-taxonomy.md` enums) stays in the tagging/API layer and is not
duplicated here.

**Routing:** Ready → Coder. Touches `internal/store/` and the store tests.
ING-030 (`GET`/`PUT /api/items/:id`) and ING-033 (frontend edit form) depend on
this.

**Depends on:** nothing.

**Out of scope:** taxonomy/enum validation (owned by `internal/tagging`,
ING-004/ING-005); photo copying or `data/photos/` writes (ING-028); any delete
operation (no delete route in Phase 1 — `07-architecture.md`); changing the
`Item` model or schema.

## Implementation notes

**Changes**
- `internal/store/store.go` (+40 lines, no deletions):
  - `var ErrNotFound = errors.New("item not found")` — the identifiable
    "not found" sentinel; callers use `errors.Is(err, store.ErrNotFound)`
    with no gorm import at the call site.
  - `func (s *Store) Get(id string) (Item, error)` — `db.First` by primary
    key; maps `gorm.ErrRecordNotFound` → `ErrNotFound` (zero `Item` +
    error), passes any other error through.
  - `func (s *Store) Update(item Item) error` — keys on `item.ID` via
    `Get` first (not-found → `ErrNotFound`, **zero writes** before the
    save), then copies the seven tagging fields + `Notes` onto the loaded
    row and `db.Save`s it. `id`, `added_date`, and `photo_path` come from
    the loaded row, so values passed in for them are ignored
    (`04-data-schema.md` "Write-path rules (interactive create/edit)").
  - `Insert`, `List`, `Open`, `Close`, `Item`, `DefaultDBPath` untouched.
- `tests/ing_029_store_test.go` (new) — 6 test functions covering all six
  ACs; reuses `sampleItem`/`assertItemEqual`/`newStorePath`/`findItem`
  helpers from `tests/ing_017_store_test.go` (same package). The file
  intentionally does **not** import gorm — AC2's "without importing gorm"
  is exercised at the call site.

**Assumptions**
- `Update(item Item) error` keyed by `item.ID` (mirrors `Insert(item Item)`)
  rather than an explicit 8-parameter signature; the API layer is expected
  to Get → mutate → Update. No new exported type needed.
- Load-then-Save was chosen over `Updates(map/struct)` because GORM skips
  zero-value fields on struct updates (empty `Notes` would not persist) and
  map updates do not reliably run the `serializer:json` tag for
  `SecondaryColors`. Consequence: the UPDATE statement's SET clause also
  rewrites `photo_path`/`added_date` — always with the row's existing
  values loaded a moment earlier, never with values from the passed item;
  AC3's test proves this by passing deliberately different immutable
  values and asserting they do not stick. Observable behavior matches the
  AC: only the eight mutable fields change.
- No taxonomy/enum validation added (out of scope — stays in
  `internal/tagging` / API layer). No photo writes, no delete, no
  model/schema change, no new env var.

### Edge cases checked (spec-implied)

- **Nil `secondary_colors` on update** — AC5's "empty list" can be a nil
  slice (Go zero value; ING-017's insert stores SQL NULL for nil). Feeding a
  nil list back through Get→Update reads back length-0 + `""` notes on both
  Get and List — matches ING-017's read shape, no leaked sentinel.
- **Empty-id Update** — no row can have `id=""`, so Update hits the same
  `ErrNotFound` and writes nothing; pre-existing rows field-equal after.
- **Zero-value immutable fields** — AC3 only proves *different* values are
  ignored; `Edge_ImmutableFieldsZeroValueIgnored` proves `PhotoPath=""` and
  `AddedDate=time.Time{}` are ignored too (the realistic Get→mutate→Update
  bug where the caller forgets to copy them).
- **Not-found precision** — `Get` maps only `gorm.ErrRecordNotFound` to
  `ErrNotFound`; any other DB error passes through raw (code inspection),
  so the API layer's future `errors.Is(..., ErrNotFound) → 404` mapping
  cannot misfire on a real DB failure.
- **Out of scope, deliberately not tested** — taxonomy/enum rejection,
  photo copying, delete, HTTP status mapping: all owned by other tickets
  (ING-004/005, ING-028, `07-architecture.md` "No delete route in Phase 1",
  ING-030).
