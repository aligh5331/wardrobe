### [ING-029] Catalog store: `Get` and `Update` for the interactive edit path

**As a** wardrobe owner
**I want** `internal/store` to read one item by id and update its mutable fields
**So that** the API can serve `GET /api/items/:id` and apply `PUT /api/items/:id`
without a second persistence path

**Acceptance criteria** (Gherkin):
```
Given an item id that exists
When Get(id) is called
Then the full item is returned with all 04-data-schema.md fields intact,
  including empty notes and a 0-length secondary_colors list

Given an item id that does not exist
When Get(id) is called
Then it returns an error the caller can identify as "not found" without
  importing gorm — so the API layer can map it to 404

Given an existing item and new values for the mutable fields (the seven tagging
  fields plus notes)
When Update is called
Then exactly those fields are persisted and read back changed, while id,
  added_date, and photo_path are unchanged

Given an item id that does not exist
When Update is called
Then it returns the same identifiable "not found" error and writes nothing

Given empty notes and an empty secondary_colors list
When an update writes them
Then they round-trip as "" and [] (not null), matching ING-017's read shape

Given the existing store behavior
When this change lands
Then Insert and List are unchanged and ING-017's tests still pass
```

**Spec reference:** `04-data-schema.md` "Write-path rules (interactive
create/edit)" (`id` and `added_date` are immutable; `notes` and all other fields
are editable; the photo / `photo_path` is not replaced); `07-architecture.md`
"Catalog write API" (`GET`/`PUT /api/items/:id`); `backlog/ING-017.md` (the
store surface, and its explicit out-of-scope deferral of update/delete "until a
second writer exists" — now met per `06-decisions.md` "Second catalog writer
exists").

**Status:** Ready

**Context:** ING-017 built `internal/store` with `Insert`/`List` only and
deferred update/delete because `cmd/ingest` was the only writer. The approved
interactive create/edit feature makes the API a second writer, so the edit path
needs `Get` and `Update`. This ticket adds only those two operations; the write
validation (`03-taxonomy.md` enums) stays in the tagging/API layer and is not
duplicated here.

**Routing:** Ready → Coder. Touches `internal/store/` and the store tests.
ING-030 (`GET`/`PUT /api/items/:id`) and ING-033 (frontend edit form) depend on
this.

**Depends on:** nothing.

**Out of scope:** taxonomy/enum validation (owned by `internal/tagging`,
ING-004/ING-005); photo copying or `data/photos/` writes (ING-028); any delete
operation (no delete route in Phase 1 — `07-architecture.md`); changing the
`Item` model or schema.
