### [ING-054] `cmd/server`: use the configured slog logger; bootstrap-logger config errors

**As a** wardrobe owner
**I want** `cmd/server` to log through the logger built from `LOG_LEVEL`/`LOG_FORMAT`,
and to report config errors (including an invalid `LOG_LEVEL`) on stderr before that
logger exists
**So that** level, format and sinks apply to every server log line, and a bad logging
setting still fails fast with a readable message

**Acceptance criteria** (Gherkin):
```
Given config.Load fails (for example VLM_URL missing, or LOG_LEVEL=verbose)
When cmd/server starts
Then the error is logged at error level through slog.Default() on stderr in text
  format (never JSON, even if LOG_FORMAT=json is also set)
And the process exits with status 1
And no logs/app.log is created

Given LOG_LEVEL=verbose (an unrecognized value)
When the real cmd/server process is started
Then it exits with a non-zero status
And a stderr line names LOG_LEVEL
And a stderr line contains "startup"

Given LOG_LEVEL=verbose and LOG_FORMAT=json
When the real cmd/server process is started
Then the stderr error line is text format (not a JSON object)

Given config.Load succeeds but cfg.RequireLLMURL() fails (LLM_URL empty)
When cmd/server starts
Then it is reported like any other config error (slog.Default(), text, exit 1)
And stderr names LLM_URL

Given valid config
When cmd/server starts
Then the ING-052 logger is built from cfg.LogLevel and cfg.LogFormat
And every later startup record goes through it (stderr + logs/app.log)

Given cfg.Warnings() returns warnings (for example VLM_REQUEST_DELAY_MS=15 with
  VLM_SERIALIZE_REQUESTS=false)
When cmd/server starts
Then each warning is one warn-level record through the configured logger
And its message contains "startup warning" and the warning text (for example
  "will not be applied")

Given store.Open fails
When cmd/server starts
Then an error-level record through the configured logger carries the failure
And the process exits with status 1

Given a successful start
When the server begins to listen
Then an info-level record whose message contains "listening on <addr>" (for example
  "listening on :8080") is logged through the configured logger

Given http.ListenAndServe returns an error (for example the port is taken)
When the server stops
Then an error-level record carries the error text (including "bind" or "listen tcp")
And the process exits with status 1

Given LOG_FORMAT=json and a running server
When the "listening on" record and a startup warning are logged
Then each stderr line is a parseable JSON object with level, msg and its attributes
And the same records are appended to logs/app.log

Given a running server started with the configured logger
When GET /api/taxonomy is served
Then stderr carries one JSON access-log record (ING-053) with a request_id
And it went to the configured logger (via api.WithLogger), not slog.Default()

Given the change
When cmd/server/main.go is read
Then it no longer imports the stdlib "log" package and contains no log.Printf,
  log.Fatalf or log.Fatal call
And it passes the configured logger to api.New with the ING-053 WithLogger option
And it adds no dependency (go.mod and go.sum unchanged)

Given the existing static and process tests on cmd/server
When they run after the change
Then they still pass (see Test note for the exact assertions)
```

**Spec reference:** `07-architecture.md` "## Logging": "Bootstrap logger: config is
loaded before the configured logger exists. Config errors are reported through
`slog.Default()` on stderr (text format), then the process exits with status 1. `slog`
has no fatal level; startup failures log at `error` and call `os.Exit(1)`", "Sinks",
"Level and format", "Failure to open `logs/app.log`: startup logs a warning and
continues with stderr only" (ING-052 owns this fallback); `07-architecture.md`

`06-decisions.md` "Structured logging: stdlib `log/slog`, local stderr + file,
env-configurable level/format" (Bootstrap logger and Fatal exits bullets).

**Status:** Testing

**Context:** `cmd/server/main.go` has six stdlib log calls today: `log.Fatalf` x3
(config load, `RequireLLMURL`, `store.Open`), `log.Printf` x2 (each warning,
"listening on"), and `log.Fatal(http.ListenAndServe(...))`. Replace all six.

Flow: `config.Load()` and `cfg.RequireLLMURL()` first; on error call
`slog.Error(...)` (which is `slog.Default()`, text on stderr) and `os.Exit(1)`. Only
after both pass, build the ING-052 logger from `cfg.LogLevel`/`cfg.LogFormat`
(constructor name is ING-052's Coder choice; use it as built). The logger is not
installed as `slog.Default()` unless the Coder needs that; record the choice on the
ticket either way. Nothing in this ticket depends on it because the request-scoped
logger reaches ING-055/056 through the ING-053 middleware.

**Decision on ING-055/056 wiring: leave defaults.** `cmd/server` passes the logger only
to `api.WithLogger(logger)`. The `recommend.Picker{...}` literal and the
`weather.New(...)` call stay exactly as they are (no logger field, no new argument).
ING-055 and ING-056 read the logger from the request context that ING-053's middleware
fills from `WithLogger`, so no wiring is needed here.

Message text is kept as today so existing substring assertions hold: `startup: <err>`
(config, `RequireLLMURL`), `startup: open store: <err>`, `startup warning: <warning>`,
`listening on <addr>`. A structured `err` attribute may be added alongside, but the
message must still contain that text. Message `startup:` must not appear in any
success-path output (an existing test treats it as a hard error).

`logs/app.log` is created under the working directory. Existing tests that
`go run ./cmd/server` from the module root will therefore append to the repo's own
`logs/` (gitignored, harmless). All new tests must use the temp-root harness
(`newING019Harness` in `tests/ing_019_server_integration_test.go`) so nothing new lands
in the repo's `logs/`.

## Implementation notes

Two commits: 9b4c7e4 (`cmd/server/main.go` and `contractVars`) and part 2 (process
tests and these notes). Part 2 found no bug in `main.go` and changed no non-test code.

**Part 1 choices**

- Config errors (`config.Load`, `RequireLLMURL`, and a `logging.New` failure) go
  through `slog.Error("startup: " + err.Error())` on `slog.Default()`, then
  `os.Exit(1)`.
- The configured logger is not installed as `slog.Default()`. It reaches handlers
  only through `api.WithLogger(logger)`.
- The `io.Closer` from `logging.New` is discarded. `logs/app.log` is opened with
  `O_APPEND` and the process ends with `os.Exit` or a kill, so the close would do
  nothing useful (`logging.New` documents that a long-running process may skip it).
- A `ListenAndServe` failure logs `server stopped: <err>` at error level and exits 1.
  The message has no `startup:` prefix, because `assertReachedListenStage` treats that
  prefix as a config failure.
- No `err` attribute is added. The error text is in the message, which is what the
  existing substring assertions read.
- `LOG_LEVEL` and `LOG_FORMAT` were added to `contractVars`, so `envWith` drops any
  value exported in the developer's shell.

**Assumptions**

- Listening tests use `-addr 127.0.0.1:<free port>` from `ing019FreePort`, not the
  default `:8080`. The listen record is asserted as `listening on <addr>`. The risk is
  a race between releasing the reserved port and the server binding it (same as
  ING-019 AC2). No test binds `:8080`.
- "Same records in `logs/app.log`" is checked as: every stderr line appears verbatim
  in the file. The tests poll the file for up to 5 seconds, because the file write
  follows the stderr write for each record.
- The text-format check uses the `ERROR` level word in the text handler output and
  requires that no stderr line parses as JSON.
- `AC3` uses `LOG_FORMAT=json` with empty `LLM_URL` to also prove the bootstrap
  logger ignores the format.
