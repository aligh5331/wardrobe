### [ING-041] Weather: `internal/weather` Open-Meteo client (forecast + geocoding search)

**As a** wardrobe owner
**I want** a backend client that fetches today's weather and searches cities from Open-Meteo
**So that** the API can serve weather for my saved location without the browser ever calling a third party

**Acceptance criteria** (Gherkin):
```
Given a latitude/longitude and a fake Open-Meteo forecast server (httptest)
When the client fetches the forecast
Then it sends exactly one GET to the forecast endpoint with latitude, longitude,
  current=temperature_2m,apparent_temperature,weather_code,precipitation,
  daily=temperature_2m_min,temperature_2m_max,precipitation_probability_max,weather_code,
  timezone=auto and forecast_days=1
And it returns current {temperature_c, apparent_temperature_c, weather_code,
  precipitation_mm} and today {temperature_min_c, temperature_max_c,
  precipitation_probability_max, weather_code} mapped 1:1 from the response
  (daily values taken from index 0), weather_code as the raw WMO integer

Given a search text and a fake geocoding server returning results
When the client searches cities
Then it calls the geocoding search endpoint with that text and a count of 10
And it returns at most 10 results, each {name, country, admin1, latitude, longitude}

Given the fake geocoding server returns zero results (no "results" key, or an empty list)
When the client searches cities
Then it returns an empty, non-nil list and no error

Given the fake server is unreachable (closed), returns a non-2xx status, or returns an unparseable body
When either call (forecast or search) is made
Then it returns an error (no panic, no partial result) that callers can identify
  as an upstream weather failure (errors.Is on an exported sentinel), and the
  error message distinguishes unreachable/timeout vs non-2xx status vs unparseable body

Given a fake server that does not answer within the timeout
When either call is made
Then the call fails with the upstream error after the client's outbound timeout;
  the production timeout is 10 s (tests may inject a shorter one)

Given the package tests
When they run
Then all HTTP goes to httptest servers via injectable base URLs; no test touches the real network
```

**Spec reference:** `07-architecture.md` "Backend" → "Weather (Phase 2)" (exact
`current`/`daily` params, `timezone=auto`, `forecast_days=1`, raw WMO code,
city result shape, up to 10 results, 10 s outbound timeout);
`06-decisions.md` "Weather provider: Open-Meteo, backend-proxied, no API key"
(endpoints `api.open-meteo.com/v1/forecast` and
`geocoding-api.open-meteo.com/v1/search`, no key, no cache, httptest);
`07-architecture.md` "Full project structure" (`internal/weather/`).

**Status:** Review

**Depends on:** nothing.

**Routing:** Ready → Coder. New package `internal/weather/` plus its test.
Stdlib `net/http` + `encoding/json`; no new dependency.

**Out of scope:** HTTP routes (ING-043), persistence (ING-042), caching,

## Implementation notes

New package `internal/weather`, stdlib only (`net/http`, `net/url`,
`encoding/json`); `go.mod` untouched. No other file changed.

**What was done**

1. `internal/weather/weather.go`:
   - `New(forecastBase, geocodingBase string, timeout time.Duration) *Client`
     — base URLs are scheme+host (paths `/v1/forecast`, `/v1/search` are
     appended), timeout is `http.Client.Timeout`. Production call is
     `New(DefaultForecastBaseURL, DefaultGeocodingBaseURL, DefaultTimeout)`
     = `https://api.open-meteo.com`, `https://geocoding-api.open-meteo.com`,
     10 s.
   - `(*Client).Forecast(ctx, lat, lon) (Forecast, error)` — one GET with
     exactly `latitude`, `longitude`, `current=temperature_2m,apparent_temperature,weather_code,precipitation`,
     `daily=temperature_2m_min,temperature_2m_max,precipitation_probability_max,weather_code`,
     `timezone=auto`, `forecast_days=1`. Returns `Forecast{Current, Today}`
     whose JSON tags are exactly the `07-architecture.md` response keys
     (`temperature_c`, `apparent_temperature_c`, `weather_code`,
     `precipitation_mm`; `temperature_min_c`, `temperature_max_c`,
     `precipitation_probability_max`, `weather_code`). Daily values from
     index 0; `weather_code` raw WMO int.
   - `(*Client).SearchCities(ctx, text) ([]City, error)` — GET
     `/v1/search?name=<text>&count=10` only (no `language`). Returns ≤10
     `City{name, country, admin1, latitude, longitude}`; missing
     `country`/`admin1` decode to `""`; no `results` key or `[]` returns
     `[]City{}` (non-nil), no error.
   - `ErrUpstream` sentinel wraps every failure; message prefix after the
     sentinel distinguishes `unreachable or timed out` (transport error,
     incl. timeout), `status <code>` (non-2xx), `unparseable body` (bad
     JSON). On error both calls return a zero value / nil slice — no
     partial result.
2. `internal/weather/weather_test.go` (package-internal, same placement as
   `internal/tagging/*_test.go`): all HTTP via `httptest`; covers exact
   forecast query + single GET + 1:1 mapping, search query + 10-cap +
   missing-field `""`, empty results (3 bodies), and closed / 500 /
   garbage / slow (100 ms injected timeout) for both calls, checking
   `errors.Is(err, ErrUpstream)`, the distinguishing message, and no
   partial result. `TestDefaults` pins the production URLs and 10 s.

**Assumptions**

- A 2xx forecast body that is valid JSON but lacks `current` or any of
  the four `daily` arrays (or has them empty) is treated as
  `unparseable body` — otherwise index 0 would panic or yield a silent
  zero-valued "partial" result, which the AC forbids.
- `SearchCities` does not trim/validate `text`; empty/whitespace `q` →
  `400` is the route's job (ING-043, `07-architecture.md`).
- Client-side cap to 10 results is kept even though `count=10` is sent,
  so the "at most 10" guarantee does not depend on upstream.

## Review

**Decision: APPROVED**

Reviewed the uncommitted diff (`internal/weather/weather.go`,
`internal/weather/weather_test.go`, `tests/ing_041_weather_test.go`) against
the ticket ACs, `07-architecture.md` "Weather (Phase 2)", `06-decisions.md`
"Phase 2 scope", "Weather provider", "Weather location", `00-overview.md` hard
constraints, and `AGENTS.md`. ING-042 files in the working tree were not
reviewed here.

- **Spec match.** Forecast query is exactly the `07-architecture.md` param
  set (`current=…`, `daily=…`, `timezone=auto`, `forecast_days=1`) plus
  lat/lon; nothing extra. Output JSON tags equal the `GET /api/weather`
  `current`/`today` keys; daily index 0; `weather_code` is a raw `int`, with
  no label mapping (that belongs to the frontend). Search sends
  `name=<q>&count=10` only, with no `language`, per spec. Missing
  `country`/`admin1` become `""`. Zero results return `[]City{}`, so the
  route can return `200 []`.
- **Error contract.** Every failure wraps the exported `ErrUpstream`. The
  message says `unreachable or timed out`, `status <code>`, or
  `unparseable body`, so ING-043 can map every case to `502` with one
  `errors.Is`. On error, callers get a zero `Forecast` or a `nil` slice, never
  a partial value. `http.Client.Timeout` covers both the dial and the body
  read, so a slow body still fails at 10 s. A missing `current` block, or a
  missing or empty `daily` array, returns `unparseable` instead of panicking
  on `[0]`. That is correct.
- **Hard constraints clean.** The only external calls go to the two
  Open-Meteo hosts named in `06-decisions.md`, from the backend. No API key,
  no env var, no cache. Only coordinates and search text leave the machine.
  No model, fine-tuning, or tagging change. No `LLM_URL` use and no Phase 3
  logic. `go.mod`/`go.sum` are unchanged (`git status`), and the code uses
  stdlib only. No protected file (`0*.md`, `agents/`, `AGENTS.md`) is
  modified.
- **Over-engineering check: none blocking.** There is one `Client` struct
  with one constructor. It is needed because the ACs require injectable base
  URLs and timeout. No interface, no options/config struct, no retry, no
  cache. One shared `get` helper serves exactly the two callers. The
  client-side `maxCities` cap duplicates `count=10`, but it is 3 lines and
  enforces the spec's "up to 10" guarantee. Keep it.
- **Tests.** All HTTP goes through `httptest`. The production URLs appear
  only as constants and are never dialed. Tester's added
  `tests/ing_041_weather_test.go` pins index 0 with multi-day upstream data
  and the exact wire key sets. Both are useful and small. Tester's evidence,
  including `-race`, is accepted as recorded; not re-run per role.

**Ruling on Tester's open note (null/missing field inside `current`, and
likewise a `null` element in a `daily` array, decodes to `0`): acceptable for
this ticket, not a send-back.** Reasons:
1. The spec defines only three failure classes: unreachable, non-2xx, and
   unparseable. A syntactically valid body with a `null` leaf is not clearly
   "unparseable". The spec also does not say whether a field is nullable in
   the `GET /api/weather` response. Either option (strict `502` or a nullable
   wire field) means choosing a contract the spec has not set. Per
   `AGENTS.md` §16, that decision goes to Ali or the Planner. The Coder
   should not guess it.
2. AC4's "no partial result" is scoped to the error cases, and those are
   met.
3. The Coder's missing-block guard already covers the realistic structural
   failure, which would otherwise panic.

**Escalation to Ali/Planner (follow-up, not blocking merge):** the risk is
real. A `null` `temperature_2m` would show `0 °C`, and a `null`
`precipitation_probability_max` would show `0 %`. Both look like valid data.
Once the Phase 3 recommender consumes these values, a silent 0 would become a
wrong input. Recommend a one-line addition to `07-architecture.md`: "a `null`
or missing requested field is unparseable → `502`." The fix is then about 10
lines in `Forecast`: decode into `*float64`/`*int` and reject nil. If the
spec prefers nullable fields instead, that changes the wire types and belongs
in the same spec change as ING-044.

Non-blocking notes:
1. `io.ReadAll` on the upstream body has no size limit. The timeout bounds
   it in practice. Wrap it in `io.LimitReader` only if a real problem
   appears.
2. Unreachable and timeout errors share one message
   (`unreachable or timed out`). The AC groups them as one class, so this is
   acceptable.

Status remains `Review`, ready for Ali's final review and merge.

## Follow-up: null = missing data (Ali decision)

Ali ruled on the open null question: a `null`/absent Open-Meteo variable is
**missing data, not an error**. Spec updated (`07-architecture.md` "Weather
(Phase 2)"): the field is JSON `null` in `/api/weather` (never `0`), the UI
shows `-`. Missing `current` object or empty daily arrays stays `502`.

Change: `Current`/`Today` fields are now `*float64`/`*int`; upstream decoded
into pointers and passed through. New `TestForecastNulls` asserts nil fields
and exact JSON `null` output. `TestForecast`, the partial-result check, and
`tests/ing_041_weather_test.go` adjusted for pointer fields.
Evidence: `gofmt -l` clean, `go vet ./...` clean, `go test -count=1 ./...` all ok.
ING-043 and ING-044 acceptance criteria extended for null pass-through / `-` rendering.
