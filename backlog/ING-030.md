### [ING-030] API: `GET /api/items/:id` and `PUT /api/items/:id` (edit)

**As a** wardrobe owner
**I want** the catalog API to return one item and to accept corrections to its
mutable fields
**So that** the edit form can load an item and save corrected tags without
re-running the model or touching the photo

**Acceptance criteria** (Gherkin):
```
Given a catalog item id that exists
When a client GETs /api/items/:id
Then it receives 200 with the same JSON object shape GET /api/items returns for
  one item — the 04-data-schema.md fields plus photo_url

Given an id that does not exist
When a client GETs or PUTs /api/items/:id
Then it receives 404

Given an existing item and a PUT body carrying the seven tagging fields
  (04-data-schema.md names) plus notes, all taxonomy-valid
When the client PUTs /api/items/:id
Then it receives a 2xx, the mutable fields are persisted, and a subsequent
  GET /api/items/:id reflects the new values

Given a PUT body with an invalid enum value, an invalid category/subcategory
  pair, or a missing required tagging field
When the client PUTs /api/items/:id
Then it receives 400 and the response names the offending field, and the item
  is left unchanged

Given a PUT body that also carries id, added_date, or photo_path with different
  values
When the client PUTs /api/items/:id
Then those values do not change: the stored id, added_date, and photo_path are
  unchanged and the photo file is untouched

Given the corrected record
When it is validated
Then it validates against the same 03-taxonomy.md enums as a model output,
  reusing internal/tagging's taxonomy tables (ParseTaggingResult) rather than a
  second enum copy

Given the route surface
When routes are inspected
Then the approved write routes GET /api/items/:id and PUT /api/items/:id are
  registered, and the existing read routes are unchanged
```

**Spec reference:** `07-architecture.md` "Backend" → "Catalog write API

- `cmd/server/main.go` untouched (constructor deps unchanged).

**Approach:**
- GET returns the same `itemResponse` shape as `GET /api/items` for one item
  (04 fields + `photo_url`); unknown id → 404 via
  `errors.Is(err, store.ErrNotFound)`.
- PUT binds only the seven tagging fields + `notes`; `id`, `added_date`,
  `photo_path` are never decoded, so they cannot reach the store.
- Validation reuses `tagging.ParseTaggingResult` (re-marshaling the embedded
  `tagging.TaggingResult`) — no second enum copy. Invalid enum / invalid
  category-subcategory pair / missing required field → 400 with
  `{"error": "<message naming the field>"}` before any write.
- Unknown id checked before body validation → 404 wins.
- Valid → `store.Update` + 200 with the updated item.

**Assumptions:**
1. Lookup-before-body order: unknown id → 404 regardless of body validity (no
   AC covers unknown id + bad body).
2. 400 field naming: the offending field name appears inside the `"error"`
   message (from `tagging.ValidationError` detail), not as a separate JSON key
   — a structured `field` key would require touching `internal/tagging`.
3. `notes` omitted/null → `""` (PUT replaces mutable fields; notes is
   optional free text).
4. Malformed JSON body → 400 (`invalid JSON body: ...`), natural guard, not
   in ACs.

## Review

Reviewed against `07-architecture.md` "Catalog write API", `04-data-schema.md`
"Write-path rules (interactive create/edit)", `05-vlm-tagging-spec.md`
"Interactive tagging (web UI)", `03-taxonomy.md`, and `00-overview.md`'s hard

**Spec intent, not just AC wording**
- `getItem`/`updateItem` reuse the existing `itemResponse`/`toResponse`, so
  `GET /api/items/:id` is the identical object shape as a list element — not a
  parallel one that could silently drift (`07-architecture.md` "one item, for
  the edit form").
- PUT persists exactly the seven tagging fields + `notes`. The photo path is
  never written, matching `04-data-schema.md` "the photo and `photo_path` are
  not replaced in Phase 1". `store.Update` independently re-fetches the row and
  rewrites only mutable fields, so immutability holds at two layers.
- Validation delegates to `tagging.ParseTaggingResult` — the corrected record
  goes through the same enums as a model output
  (`05-vlm-tagging-spec.md` "Interactive tagging"). A grep of `internal/api/`
  for category/subcategory/color/pattern literals found none; there is no
  second enum copy.

**Structural immutability** `updateItemRequest` embeds `tagging.TaggingResult`
(7 fields) plus `notes` only. `id`, `added_date`, and `photo_path` are not
decoded at all, so a body carrying them cannot reach the store — stronger than
binding then filtering.

**Error/status semantics** Unknown id → 404 on both methods, checked before the
body is read, so it wins over any body problem. Invalid enum / invalid
category-subcategory pair / missing required field → 400 whose `error` string
names the offending field (from `tagging.ValidationError`). No 4xx path writes
to the store. Every store/validation error branches to an explicit response —
no silent swallowing.

**Hard constraints** Handlers touch only the store (no model/network call); no
fine-tuning; one-garment-per-photo input is untouched by this route. `go.mod`/
`go.sum` unchanged (no new dependency). No protected file (`0*.md`,
`agents/*.md`, `AGENTS.md`) appears in the diff.

**Scope** Route surface is exactly the five approved routes; no delete, no POST
(ING-031/032), no re-tagging or photo replacement. `cmd/server/main.go`
untouched.

**Non-blocking notes (no action required)**
1. `TestING019_AC7_OnlyReadOnlyRoutes` now asserts the approved mixed-method
   route set, so its name no longer describes what it checks. Its assertion is
   correct, and the ticket's test note required converting it in place; a rename
   (`..._ApprovedRouteSet`) would be cosmetic.
2. The 400 message names the field inside the text rather than via a structured
   key (Coder assumption 2). This satisfies "names the offending field"; a
   machine-readable `field` key would require changing `internal/tagging` and is
   out of this ticket's scope.
3. Omitted `secondary_colors` is 400 while `[]` is accepted — inherited from the
   existing `ParseTaggingResult` contract and consistent with the
   required-field rule, not new behavior introduced here.
