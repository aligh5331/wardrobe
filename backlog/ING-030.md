### [ING-030] API: `GET /api/items/:id` and `PUT /api/items/:id` (edit)

**As a** wardrobe owner
**I want** the catalog API to return one item and to accept corrections to its
mutable fields
**So that** the edit form can load an item and save corrected tags without
re-running the model or touching the photo

**Acceptance criteria** (Gherkin):
```
Given a catalog item id that exists
When a client GETs /api/items/:id
Then it receives 200 with the same JSON object shape GET /api/items returns for
  one item — the 04-data-schema.md fields plus photo_url

Given an id that does not exist
When a client GETs or PUTs /api/items/:id
Then it receives 404

Given an existing item and a PUT body carrying the seven tagging fields
  (04-data-schema.md names) plus notes, all taxonomy-valid
When the client PUTs /api/items/:id
Then it receives a 2xx, the mutable fields are persisted, and a subsequent
  GET /api/items/:id reflects the new values

Given a PUT body with an invalid enum value, an invalid category/subcategory
  pair, or a missing required tagging field
When the client PUTs /api/items/:id
Then it receives 400 and the response names the offending field, and the item
  is left unchanged

Given a PUT body that also carries id, added_date, or photo_path with different
  values
When the client PUTs /api/items/:id
Then those values do not change: the stored id, added_date, and photo_path are
  unchanged and the photo file is untouched

Given the corrected record
When it is validated
Then it validates against the same 03-taxonomy.md enums as a model output,
  reusing internal/tagging's taxonomy tables (ParseTaggingResult) rather than a
  second enum copy

Given the route surface
When routes are inspected
Then the approved write routes GET /api/items/:id and PUT /api/items/:id are
  registered, and the existing read routes are unchanged
```

**Spec reference:** `07-architecture.md` "Backend" → "Catalog write API
(interactive create/edit)" (the `GET`/`PUT /api/items/:id` rows; "an invalid
field is 400 with the field named, an unknown id is 404"; "`id`, `added_date`,
and the photo are immutable via `PUT`"; validation reuses `internal/tagging`);
`04-data-schema.md` "Write-path rules (interactive create/edit)";
`05-vlm-tagging-spec.md` "Interactive tagging (web UI)" (a corrected record is
validated against the same enums); `03-taxonomy.md`.

**Status:** Ready

**Context:** The read API (ING-019) exposes only `GET /api/items` and
`GET /api/photos/:filename`. The edit path needs a single-item read and a
mutable-field write. Both go through `internal/store`'s new `Get`/`Update`
(ING-029); neither re-tags nor replaces the photo.

**Routing:** Ready → Coder. Touches `internal/api/`, `cmd/server/` (if the
constructor's dependencies change), and tests. ING-033 (frontend edit form)
depends on this.

**Depends on:** ING-029.

**Test note:** `tests/ing_019_api_test.go`'s `TestING019_AC7_OnlyReadOnlyRoutes`
currently asserts exactly two read-only routes. Now that write routes are
approved (`07-architecture.md` "Catalog write API"), that assertion must be
updated to the approved route set (still excluding any delete route). This
applies to every API ticket adding a route; whichever of ING-030/031/032 lands
first should convert it, and the others extend it.

**Note (validation reuse):** `PUT` rejects only the tagging fields; `notes` is
free text with no enum. A 400 for a corrected record is the API-layer guard for
a value the UI should not have offered — see ING-033's taxonomy-source blocker.

**Out of scope:** create/upload routes (ING-031, ING-032); frontend changes
(ING-033/034); delete (none in Phase 1); re-tagging or photo replacement.
