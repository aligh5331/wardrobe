### [ING-050] Frontend: recommendation panel

**As a** wardrobe owner
**I want** a "Suggest outfits" panel with formality and a note
**So that** I can ask for today's outfits and see them as garment photos

**Acceptance criteria** (Gherkin):
```
Given the app loads
When it renders
Then a recommendation panel shows under the weather panel with a formality select
  (any, casual, smart-casual, formal), a note text box, and a "Suggest outfits" button
And POST /api/recommendations is NOT called on load

Given the user picks "formal", types "wedding", and clicks "Suggest outfits"
When the request is sent
Then it POSTs /api/recommendations with {"formality":"formal","note":"wedding"}
And with "any" selected and an empty note, the body omits formality and note (or sends them empty)

Given a request is in flight
When the panel renders
Then the button is disabled and a loading message shows

Given a 200 response with 3 outfits
When it renders
Then 3 outfit rows show, each with one photo per item (in response order) and the reason
And an item photo that fails to load shows the same placeholder the catalog grid uses

Given a 400, 422, or 502 response with {"error": "..."}
When it renders
Then that server message is shown, and the weather panel and catalog grid are unchanged

Given the request fails with no response (network error)
When it renders
Then a generic error message is shown, and weather panel and catalog are unchanged

Given results are shown and the user clicks "Suggest outfits" again
When the new response arrives
Then the new outfits replace the old ones
```

**Spec reference:** `07-architecture.md` "Recommender (Phase 3)" (UI paragraph,
request body, response shape, error table); `06-decisions.md` "Testing tooling"
(Vitest + Testing Library, `vi.stubGlobal('fetch')`).

**Status:** Review

**Depends on:** ING-049.

**Routing:** Ready → Coder. New component under `frontend/src/` rendered from
`App.jsx` under `WeatherPanel`, Tailwind v4 classes, one co-located vitest file.
No new dependency.

**Notes from the ING-049 review** (implementation constraints, acceptance
criteria unchanged):
- The browser fetch must not time out before about 240 s. Worst case is two LLM
  calls at 120 s each, and the server sets no `WriteTimeout`. Use no client
  timeout, or one of at least 240 s.
- The UI shows the busy state (disabled button, loading message) for the whole
  wait.

**Out of scope:** outfit log / "I wore this", ratings, image generation,
saving recommendations, auto-run on load.

## Implementation notes

`frontend/src/RecommendationPanel.jsx` (new): the default export
`RecommendationPanel` and a local `Photo` component. The panel holds its own
state (formality, note, busy, error, outfits), so a failure never touches the
weather panel or the catalog. On mount it reads the formality choices from
`GET /api/taxonomy`. The "Suggest outfits" button is the only trigger for
`POST /api/recommendations`.

`frontend/src/App.jsx`: imports the panel and renders it in a `mb-6` wrapper
directly under `WeatherPanel`.

`frontend/src/ing_050_recommend.test.jsx` (new): one test per acceptance
criterion, `fetch` stubbed with `vi.stubGlobal` and routed by "METHOD url".

`frontend/src/App.test.jsx`: one assertion narrowed (see Assumptions).

No new dependency. No backend, spec or taxonomy file touched.

**Notes from the ING-049 review**

- No client timeout. `fetch` has no `AbortController` or timeout, so the
  browser waits as long as the server (worst case 240 s). A `ponytail:` comment
  in the code records this.
- Busy state for the whole wait. `busy` is set before the request and cleared
  only after the response, the error or the parse, so the button stays disabled
  and the loading message stays up for the full wait. `AC3` covers it with a
  pending promise.

**Assumptions**

- The taxonomy list is used only when `formality` in the `/api/taxonomy`
  response is an array. On a failed fetch, a non-OK status or any other shape,
  the select shows "any" only and the panel still works.
- An empty or whitespace-only note is omitted from the body, and a non-empty
  note is trimmed before it is sent. The server trims too, so this only keeps
  the request clean.
- A 200 response whose body is not JSON or has no `outfits` array shows "Could
  not get recommendations."
- A non-OK response with no `error` field (or a non-JSON body) shows "Could not
  get recommendations (HTTP <status>)."
- The placeholder markup is a local copy in `RecommendationPanel.jsx`. The
  catalog's placeholder lives inside `ItemCard`, and moving it out would
  refactor Phase 1 code outside this ticket.
- A new click clears the old outfits and the old error before the request is
  sent, so nothing stale shows while the new request runs.
- The network-error message is "Could not reach the server." The ticket asks
  for a generic message and names no text.

the only `input` and `select` elements are `rec-formality` and `rec-note`. The
intent (no catalog write form on load) still holds.

**Spec check**

No spec discrepancy found. The request body, the response use, the error
handling and the busy state match `07-architecture.md` "Recommender (Phase 3)"
(UI paragraph, request body, response shape, error table). Formality values
come from the server taxonomy, so no enum is invented.

## Review

**Decision: APPROVED**

Reviewed `git diff` for `frontend/src/App.jsx` and `frontend/src/App.test.jsx`,
the untracked `frontend/src/RecommendationPanel.jsx`,
`frontend/src/ing_050_recommend.test.jsx` and `frontend/src/ing_050_tester.test.jsx`,
and the Implementation notes and Test results above. Checked against the ticket
ACs, `07-architecture.md` "Recommender (Phase 3)" (UI paragraph, request body,
response shape, error table), `06-decisions.md` "Taxonomy exported to the
browser via `GET /api/taxonomy`" and "Testing tooling", `00-overview.md` hard
constraints, `internal/api/recommend.go` and `AGENTS.md`. The review agent did
not run `npm test` or the build. Ali ran `npm test` before this review (8 files,
65 tests, all passing) and Tester recorded the same. I read the code and the
tests directly.

Blocking findings: none.

- **Spec intent.** The panel sits directly under `WeatherPanel` in `App.jsx`
  (`mb-6` wrapper, 5 added lines). It has a formality select, a note input and
  the "Suggest outfits" button. The only `POST /api/recommendations` is inside
  `suggest`, called from the button `onClick`. Nothing calls it on load. The
  body carries `formality` only when one is chosen and `note` only when the
  trimmed note is non-empty, which the ticket allows and the server accepts
  (empty body and `{}` are valid).
- **Formality from the server taxonomy.** The options come from
  `data.formality` of `GET /api/taxonomy`, plus a fixed "any" with an empty
  value. No formality value list exists in the component, so this follows the
  06-decisions rule against a bundled copy. `TaxonomyTables()` is the same
  source the server validates the request against, so a client value cannot be
  rejected as unknown.
- **Error shapes match `recommend.go`.** Every error path there writes
  `gin.H{"error": ...}`. The panel shows `data.error` in a `role="alert"`
  paragraph for any non-OK status (400, 422, 502, and also 500 and 503), so the
  server message reaches the user. Fallbacks for a non-JSON body or a missing
  `error` field show a message with the HTTP status. A 200 without an `outfits`
  array shows a generic message. A rejected `fetch` shows "Could not reach the
  server." No path leaves the UI blank or crashes (Tester covers null body,
  string `outfits`, missing `items`).
- **Isolation.** State (formality, note, busy, error, outfits) is local to the
  panel, so a failure cannot touch the weather panel or the catalog. AC5 and AC6
  check the weather text and the catalog card through `App`.
- **ING-049 review notes honored.** No `AbortController`, no timeout and no
  `signal` in the `fetch` options (a test asserts `signal` is undefined), with
  a `ponytail:` comment stating why. `busy` is set before the request and
  cleared only after the response and the body read (or the network error), so
  the disabled button and the `role="status"` message cover the whole wait.
  The Tester case where `fetch` has resolved but `res.json()` is still pending
  proves the second half. The loading text tells the user it can take a couple
  of minutes, which fits the 240 s worst case.
- **`App.test.jsx` narrowing is the minimum.** The old assertion, zero `form`,
  `input`, `select` and `textarea` on load, cannot hold once the criterion puts
  a select and a note box on load. The new assertion keeps zero `form` and zero
  `textarea`, and requires the `input` and `select` ids to equal exactly
  `['rec-formality', 'rec-note']` in order. Any catalog write form, extra input
  or file input on load still fails it, and the "Edit" button assertion stays.
  The comment explains the change. Not weakened further than needed.
- **Taxonomy fetch catch: accepted.** `.catch(() => {})` on the taxonomy read is
  a deliberate fallback and the comment says so. On failure the select keeps
  "any" only and the panel still works, which is a safe degradation, and the
  alternative (a hardcoded list) would break the 06-decisions rule. Tests cover
  reject, non-OK and wrong shape. It is silent to the user, though. See note 1.
- **No new dependency.** `git status` shows no `package.json` or lockfile
  change. Only React (`useEffect`, `useState`) is imported.
- **No protected file or dist change.** Changed files are `App.jsx`,
  `App.test.jsx`, `backlog/ING-050.md` and the three new frontend files. No `0*.md`,
  `agents/*.md`, `AGENTS.md`, `frontend/dist`, `.env` or `data/` change, and
  `git diff --stat` on `frontend/dist` and the package files is empty.
- **Hard constraints clean.** The only new requests are same-origin relative
  URLs (`/api/taxonomy`, `/api/recommendations`). No cloud call, no external
  service, no fine-tuning, no multi-garment or outfit-photo assumption. One
  photo per garment, rendered from `photo_url`.
- **Scope.** No outfit log, "I wore this", ratings, saving, image generation or
  auto-run on load. The panel only renders what the server returns.
- **Ponytail.** One component plus a small local `Photo`, both needed. No new
  hook, context or state library. The local placeholder copy avoids refactoring
  Phase 1 code, as the Coder noted. The `GENERIC_ERROR` constant is used once,
  a trivial cost.
- **Style.** No em dashes and no banned vocabulary in `RecommendationPanel.jsx`,
  the two new test files or the Coder and Tester ticket sections. Comments use
  plain hyphens and periods. The ellipsis in the loading text matches the
  catalog's own "Loading…".
