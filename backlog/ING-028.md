### [ING-028] Extract shared persistence to `internal/catalog` with rollback-safe create

**As a** wardrobe owner
**I want** the photo-copy + row-insert logic extracted into one shared
`internal/catalog` package used by both `cmd/ingest` and the API, and a create
that leaves no orphan photo and no dangling row when either write fails
**So that** the CLI and the new interactive writer cannot drift, and
`data/photos/` and `data/wardrobe.db` cannot silently disagree

**Acceptance criteria** (Gherkin):
```
Given the inline photo-copy + row-insert logic currently in
  cmd/ingest/main.go's persist
When the shared persistence is extracted
Then exactly one implementation lives in a new internal/catalog package, and
  both cmd/ingest and the API call it — there is no second copy of the logic

Given a non-flagged tagging outcome (item id, source photo, seven tagging
  fields)
When the shared create succeeds
Then data/photos/<item_id>.<ext> holds the source bytes and exactly one catalog
  row exists with that id, the seven fields, added_date at create time, empty
  notes, and photo_path pointing at the copy (ING-018's happy path, unchanged)

Given the catalog row insert fails after the photo copy succeeded
When create returns
Then the error is returned to the caller, the copied photo is removed from
  data/photos/ (no orphan), and no row for that id exists (no dangling row)

Given the photo copy fails
When create returns
Then no catalog row is inserted for that id

Given a create failed and left no row
When the item is processed again (the tagging pipeline generates a fresh item
  id, so the retry is a new create)
Then the catalog holds exactly one row and data/photos/ holds exactly one photo
  for the item, with no residue from the failed attempt

Given the create is invoked from cmd/ingest
When the CLI runs
Then its ING-012 stdout JSON record, its exit behavior, and ING-018's existing
  behavior are unchanged, and the original source photo is never deleted
```

**Status:** Ready

**Re-triage (Planner) — the behavior ING-028 was missing is now decided; this
ticket is its implementation.**
The original ticket correctly parked itself at Backlog because no approved spec
defined the partial-failure behavior. The new decision "Catalog writes must not
leave orphan photos or dangling rows" settles it: a failed create leaves no
orphan photo and no row pointing at a missing photo, and a retry (fresh item id)
cannot leave duplicate state. Because that cleanup belongs in the one shared
persistence function rather than in the soon-to-be-duplicated inline copy, this
ticket also performs the extraction the decision "Second catalog writer exists"
calls for. Implementation mechanism (which step commits first, staging location,
cleanup on each failure branch) remains a ticket-level detail per the decision;
the ACs above fix only the observable behavior. The original ticket text is
preserved below.

**Context (original, preserved):** `cmd/ingest/main.go`'s `persist` copies the
photo into `data/photos/<item_id>.<ext>` and then calls `st.Insert`. If the copy
succeeds and the insert fails, the copied photo is left behind as an orphan; the
process exits nonzero and the catalog has no record of it. The function's own
comment says "retry/rollback/cleanup is deliberately out of scope for this
sprint." Observed while surveying the Phase 1 pipeline; not a failure of any
merged ticket. Raised by Ali in the Phase 1 state survey (2026-09-20) after the
comment was surfaced.

**Routing:** Ready → Coder. Touches `internal/catalog/` (new),
`cmd/ingest/main.go`, and tests. ING-032 (API persist) and the frontend add flow
(ING-034) call this package and depend on it.

**Do not:** widen the store API beyond what this needs (store `Get`/`Update` is
ING-029); change ING-005's retry/flag policy; add a queue/worker/service
abstraction (`06-decisions.md` rejected it); delete or mutate the source photo;
add a runtime dependency.

**Testability note (non-binding):** the insert-failure branch can be induced
with a real store by pre-inserting a row with the same item id (primary-key
conflict), then calling create with that id and asserting the copied photo is
removed and the pre-existing row is untouched — no interface or mock needed.
