### [ING-028] Extract shared persistence to `internal/catalog` with rollback-safe create

**As a** wardrobe owner
**I want** the photo-copy + row-insert logic extracted into one shared
`internal/catalog` package used by both `cmd/ingest` and the API, and a create
that leaves no orphan photo and no dangling row when either write fails
**So that** the CLI and the new interactive writer cannot drift, and
`data/photos/` and `data/wardrobe.db` cannot silently disagree

**Acceptance criteria** (Gherkin):
```
Given the inline photo-copy + row-insert logic currently in
  cmd/ingest/main.go's persist
When the shared persistence is extracted
Then exactly one implementation lives in a new internal/catalog package, and
  both cmd/ingest and the API call it — there is no second copy of the logic

Given a non-flagged tagging outcome (item id, source photo, seven tagging
  fields)
When the shared create succeeds
Then data/photos/<item_id>.<ext> holds the source bytes and exactly one catalog
  row exists with that id, the seven fields, added_date at create time, empty
  notes, and photo_path pointing at the copy (ING-018's happy path, unchanged)

Given the catalog row insert fails after the photo copy succeeded
When create returns
Then the error is returned to the caller, the copied photo is removed from
  data/photos/ (no orphan), and no row for that id exists (no dangling row)

Given the photo copy fails
When create returns
Then no catalog row is inserted for that id

Given a create failed and left no row
When the item is processed again (the tagging pipeline generates a fresh item
  id, so the retry is a new create)
Then the catalog holds exactly one row and data/photos/ holds exactly one photo
  for the item, with no residue from the failed attempt

Given the create is invoked from cmd/ingest
When the CLI runs
Then its ING-012 stdout JSON record, its exit behavior, and ING-018's existing
  behavior are unchanged, and the original source photo is never deleted
```

**Spec reference:** `06-decisions.md` "Second catalog writer exists: extract

**Re-triage (Planner) — the behavior ING-028 was missing is now decided; this

The original ticket correctly parked itself at Backlog because no approved spec
defined the partial-failure behavior. The new decision "Catalog writes must not
leave orphan photos or dangling rows" settles it: a failed create leaves no
orphan photo and no row pointing at a missing photo, and a retry (fresh item id)
cannot leave duplicate state. Because that cleanup belongs in the one shared
persistence function rather than in the soon-to-be-duplicated inline copy, this
ticket also performs the extraction the decision "Second catalog writer exists"
calls for. Implementation mechanism (which step commits first, staging location,
cleanup on each failure branch) remains a ticket-level detail per the decision;
the ACs above fix only the observable behavior. The original ticket text is
preserved below.

**Context (original, preserved):** `cmd/ingest/main.go`'s `persist` copies the
photo into `data/photos/<item_id>.<ext>` and then calls `st.Insert`. If the copy
succeeds and the insert fails, the copied photo is left behind as an orphan; the
process exits nonzero and the catalog has no record of it. The function's own
comment says "retry/rollback/cleanup is deliberately out of scope for this
sprint." Observed while surveying the Phase 1 pipeline; not a failure of any
merged ticket. Raised by Ali in the Phase 1 state survey (2026-09-20) after the
comment was surfaced.

**Routing:** Ready → Coder. Touches `internal/catalog/` (new),
`cmd/ingest/main.go`, and tests. ING-032 (API persist) and the frontend add flow
(ING-034) call this package and depend on it.

**Do not:** widen the store API beyond what this needs (store `Get`/`Update` is
ING-029); change ING-005's retry/flag policy; add a queue/worker/service
abstraction (`06-decisions.md` rejected it); delete or mutate the source photo;
add a runtime dependency.

**Testability note (non-binding):** the insert-failure branch can be induced
with a real store by pre-inserting a row with the same item id (primary-key
conflict), then calling create with that id and asserting the copied photo is
removed and the pre-existing row is untouched — no interface or mock needed.

**Design**

- Exported surface is one function, no interface/service/queue
  (`06-decisions.md` rejected a queue/service abstraction):
  `func Create(st *store.Store, photosDir, id, sourcePhoto string, result
  tagging.TaggingResult, notes string) (store.Item, error)`.
  It returns the created `store.Item` so ING-032 can build its response
  without re-deriving the `<id><ext>` copy-naming rule — keeping that rule in
  this one place is the point of the ticket.
- `photosDir` is a parameter (same testability precedent as
  `api.New(st, photosDir)`); `catalog.PhotosDir = "data/photos"` is exported
  and passed by the CLI, so tests pass an isolated temp dir and never touch
  the repo's real `data/`.
- Write order is unchanged from the old `persist` (MkdirAll → ReadFile →
  WriteFile → Insert), so ING-018's lazy `data/photos/` creation (flagged-only
  batches create nothing) and source-extension preservation still hold.
- Rollback (`06-decisions.md` "Catalog writes must not leave orphan photos or
  dangling rows"): a `WriteFile` failure or an `Insert` failure calls
  `rollback(dest, err)`, which removes the copy and returns the original cause;
  a removal failure is `errors.Join`ed in (never swallowed), and `ErrNotExist`
  (copy never created) is not treated as an error. A `ReadFile`/`MkdirAll`
  failure happens before any copy exists, so it inserts nothing.
- `added_date` = `time.Now()` inside `Create` (set once at create,
  `04-data-schema.md` write-path rules). `notes` is a parameter: the CLI
  passes `""` (ING-018); ING-032 will pass the optional body notes.
- CLI call site keeps the exact failure style: `persist <path>: <err>` on
  stderr + exit 1. Per-photo order (Process → stdout JSON → create only when
  `!Flagged`) is untouched; the source photo is only ever `ReadFile`.
- `internal/store` is untouched (Get/Update remains ING-029); `go.mod` is
  untouched (no new dependencies, not even indirect); no new env var; no
  taxonomy/schema value added — the seven fields are copied straight from the
  already-validated `TaggingResult`.

**Assumptions (for Tester/Reviewer)**

1. **AC1 "both cmd/ingest and the API call it":** the API has no create path
   today (its surface is read-only; `POST /api/items` is ING-032, which lists
   this ticket as a dependency). This ticket therefore makes
   `internal/catalog` the sole implementation and wires the CLI as its first
   caller; there is **no second copy** of the logic anywhere in the tree, and
   ING-032 will add the API as a second *caller* of this same function. Wiring
   an API route here would duplicate ING-032's scope.
2. On insert failure the copy is removed even if a row with that id already
   existed (the PK-conflict fixture): that is exactly AC3's wording ("the
   copied photo is removed … no row for that id exists" — the fixture row is
   the test's own pre-existing data, not something create wrote). The decision
   assumes retries always carry a fresh id, so this cannot orphan a
   legitimately cataloged photo in supported flows.
3. A `WriteFile` failure also best-effort-removes its partial copy — slightly
   beyond the two named AC branches, because the decision says a failed
   *create* (any branch) leaves no orphan photo.
4. `Create` takes `tagging.TaggingResult` (the seven validated fields) rather
   than `tagging.Outcome`: `Outcome` carries CLI-pipeline state (`Flagged`,
   `Attempts`) the API draft path has no use for; both callers already hold a
   `TaggingResult`.

### Spec intent (not just literal AC wording)

- **`06-decisions.md` "Second catalog writer exists":** the extraction is
  real — `internal/catalog.Create` is the sole production site of
  photo-copy + `st.Insert` (repo-wide: only other `WriteFile`/`Insert` hits
  are tests and fixtures); `cmd/ingest`'s inline `persist` is gone and now
  calls `catalog.Create`. No second copy exists anywhere. The API is not
  wired here because it has no create path yet (`POST /api/items` is
  ING-032, which **Depends on:** ING-028); wiring it would duplicate
  ING-032's scope. That is the ticket's own documented assumption 1 and
  matches the decision's "second *caller*, not a second copy" intent —
  when ING-032 lands, it calls this same function. Not a send-back.
- **`06-decisions.md` "Catalog writes must not leave orphan photos or
  dangling rows":** write order MkdirAll → ReadFile → WriteFile → Insert;
  `Insert` failure → `rollback(dest, err)` removes the copy; `WriteFile`
  failure also rollbacks the partial copy; `ReadFile`/`MkdirAll` failure
  returns before any copy or row exists. Removal failure is `errors.Join`ed,
  never swallowed; `ErrNotExist` (copy never created) is correctly ignored.
  Fresh-id retry leaves no residue (AC5). Mechanism matches the decision's
  "ticket-level detail" latitude; observable behavior matches the contract.
- **`07-architecture.md`:** `internal/catalog/` exists at the path the
  "Full project structure" tree already specifies ("shared photo+row
  persistence (CLI + API)").
- **`04-data-schema.md` write-path rules:** `id` fixed at create; `added_date`
  = `time.Now()` once inside `Create`; `notes` optional (CLI passes `""`);
  `photo_path` is the copy under `data/photos/`, never the source.
- **ING-018/ING-012 preservation:** per-photo order (Process → stdout JSON →
  create only when `!Flagged`), failure style `persist <path>: <err>` + exit
  1, and source-photo-only-read behavior are unchanged in `cmd/ingest/main.go`.
