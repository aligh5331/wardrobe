### [ING-027] Run govulncheck against the Go module tree and triage findings

**As a** wardrobe owner
**I want** `govulncheck` run over the Go module tree, with every reported
vulnerability either fixed or explicitly triaged
**So that** the known-CVE scan `06-decisions.md` accepted is actually executed
against the large Gin/pure-Go-SQLite dependency tree, instead of being an
accepted-but-never-run tool

**Acceptance criteria** (Gherkin):
```
Given the Go module tree after the Gin/GORM/SQLite additions
When `govulncheck ./...` runs from the module root
Then it completes without setup error and reports, per finding, the
  vulnerability ID, the affected module/package, and whether an affected
  symbol is reachable from this project's code

Given one or more findings that affect reachable code
When they are triaged in this ticket
Then each is either fixed here (a minimal dependency bump or equivalent
  change) or filed as its own follow-up backlog ticket naming the
  vulnerability ID and the affected package — none is silently ignored or
  blanket-dismissed, and no fix is invented beyond what the advisory requires

Given findings that affect only unreachable code
When the scan completes
Then they are recorded on this ticket with the "not reachable" evidence

Given the scan produces no findings at all
When the ticket is finished
Then the exact command and its output are recorded on the ticket, no
  implementation code is changed (same outcome shape as ING-009), and the
  ticket is not padded with speculative hardening

Given the scan tooling
When the change set is reviewed
Then govulncheck is used as a dev/build-time tool only — no runtime
  dependency is added to the shipped single binary, no network path is
  introduced into runtime behavior, and the fully-local constraint in
  00-overview.md is untouched
```

**Spec reference:** `06-decisions.md` "Testing tooling: Vitest + Testing
Library for the frontend, stdlib-first for Go" (the `govulncheck` clause:
"the one non-stdlib Go tool accepted, to scan the (large) Gin/pure-Go-SQLite
indirect dependency tree for known CVEs"); `07-architecture.md` "Backend"
(the Gin/GORM/SQLite stack that pulls the indirect tree); `backlog/ING-019.md`
non-blocking note 1 (the dependency-surface observation this scan addresses)

**Status:** Ready

**Context:** `go.mod` pulls a large indirect tree through Gin v1.12.0
(`quic-go`, `go.mongodb.org/mongo-driver/v2`, `bytedance/sonic`, …) and nothing
has ever scanned it. `06-decisions.md` accepted `govulncheck` as the one
non-stdlib Go tool for exactly this; `golangci-lint` and a coverage gate were
explicitly deferred and are **not** part of this ticket. This is an audit:
the deliverable is a recorded scan plus fixes/triage, not new features.

**Routing:** Ready → Coder — it may require dependency changes; if it finds
nothing, the outcome is a recorded report with no code change.

**Do not:** add a CI service (none exists, and that is a separate infra
decision for Ali); add `govulncheck` as a runtime dependency; widen the scan
into a general lint/coverage tooling pass.
