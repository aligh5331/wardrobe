### [ING-008] Guard floatEnv() against NaN, Inf, and out-of-range temperature values

**As a** wardrobe owner
**I want** `floatEnv()` to reject `"NaN"`, `"Inf"`, and temperature
values outside the acceptable range
**So that** a non-finite or out-of-range temperature cannot propagate
to the VLM client and break llama.cpp (flagged as non-blocking
follow-up in ING-006)

**Acceptance criteria** (Gherkin):
```
Given VLM_TEMPERATURE is set to "NaN"
When the server starts
Then it exits with a startup error naming VLM_TEMPERATURE as invalid

Given VLM_TEMPERATURE is set to "Inf" or "-Inf"
When the server starts
Then it exits with a startup error naming VLM_TEMPERATURE as invalid

Given VLM_TEMPERATURE is set to a negative value (e.g. "-1")
When the server starts
Then it exits with a startup error naming VLM_TEMPERATURE as invalid

Given VLM_TEMPERATURE is set to a value exceeding 1.0 (e.g. "1.5" or
  "100")
When the server starts
Then it exits with a startup error naming VLM_TEMPERATURE as invalid

Given VLM_TEMPERATURE is set to "0"
When the server starts
Then startup proceeds normally — 0 is a valid value (deliberate
  deterministic runs are allowed), it is simply not the default

Given VLM_TEMPERATURE is set to a valid finite value within 0.0–1.0
  inclusive (e.g. "0", "0.4", "0.7", "1.0")
When the server starts
Then startup proceeds normally and the value is available to the VLM
  client
```

## Root cause

`floatEnv()` in `internal/config/config.go` uses `strconv.ParseFloat`,
which accepts `"NaN"`, `"Inf"`, and `"-Inf"` as valid `float64` values,
plus any finite float including negative values and values far outside
what the VLM tagging pipeline expects. These invalid values would
reach `Config.VLMTemperature` and get sent to the VLM client (ING-007),
where they could crash llama.cpp or produce garbage output.

## Implementation plan (one Coder pass)

1. **`internal/config/config.go`**: Add `math` import.
   - Inside `floatEnv()` itself: after `strconv.ParseFloat` succeeds,
     reject `math.IsNaN(v)` and `math.IsInf(v, 0)` unconditionally —
     no float env var should ever be non-finite, this belongs in the
     shared helper.
   - **Do not** hardcode the `0–1` range bound inside `floatEnv()`.
     That range is specific to temperature's meaning, not a property
     every future float env var shares. Instead, extend the helper's
     signature to accept optional `min`/`max` bounds (e.g.
     `floatEnv(key, def string, min, max *float64)`), and pass `0.0`/
     `1.0` only at the `VLM_TEMPERATURE` call site. A future float env
     var with no natural range, or a different one, isn't silently
     constrained by this one's bounds.
   - Error message format: `"invalid %s %q: must be a finite number"`
     for NaN/Inf; `"invalid %s %q: must be between %v and %v"` for
     out-of-range.

2. **`internal/config/config_test.go`**: Add test cases to the
   `TestLoad` table:
   - `"NaN VLM_TEMPERATURE errors naming it"`
   - `"Inf VLM_TEMPERATURE errors naming it"`
   - `"negative VLM_TEMPERATURE errors naming it"` (e.g. `"-1"`)
   - `"out-of-range VLM_TEMPERATURE errors naming it"` (e.g. `"1.5"`)
   - `"zero VLM_TEMPERATURE is accepted"` (e.g. `"0"`) — must pass,
     not error
   - Confirm any *other* float env var added later that doesn't pass
     `min`/`max` to `floatEnv()` still only gets the NaN/Inf guard, not
     an unrelated numeric bound

3. **`tests/ing_006_config_test.go`** (naming: this validation belongs
   to ING-006's `VLM_TEMPERATURE` var specifically, not ING-001's
   general env loading — confirm which test file your team is
   actually using for config tests before assuming the name; adjust to
   match your existing convention): black-box test parameterized over
   `"NaN"`, `"Inf"`, `"-1"`, `"1.5"` (invalid) and `"0"`, `"1.0"`
   (valid), verifying `config.Load()` errors or succeeds accordingly.

4. **Integration test**: process-level test verifying the server exits
   with code 1 and output contains both `"startup"` and
   `"VLM_TEMPERATURE"` for invalid values.

5. **`.env` / `.env.example`**: no changes needed — current value
   `0.4` is within range.

## Spec-implied edge cases

- `strconv.ParseFloat("NaN"/"Inf"/"-Inf", 64)` all parse successfully
  with no error → must be explicitly rejected
- Negative finite values are parseable but invalid for temperature
- Values above `1.0` are parseable but outside the range settled in
  `06-decisions.md`
- `0` is a **valid** value — it is the range floor, not an excluded
  case. Only the *default* is nonzero (`0.4`); the value itself is
  allowed to be `0` for deliberate deterministic debugging
- All valid finite values in `0.0–1.0` inclusive must continue to work
