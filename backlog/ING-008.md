### [ING-008] Guard floatEnv() against NaN, Inf, and out-of-range temperature values

**As a** wardrobe owner
**I want** `floatEnv()` to reject `"NaN"`, `"Inf"`, and temperature
values outside what the VLM model accepts
**So that** a non-finite or out-of-range temperature cannot propagate
to the VLM client and break llama.cpp (flagged as non-blocking
follow-up in ING-006)

**Acceptance criteria** (Gherkin):
```
Given VLM_TEMPERATURE is set to "NaN"
When the server starts
Then it exits with a startup error naming VLM_TEMPERATURE as invalid

Given VLM_TEMPERATURE is set to "Inf"
When the server starts
Then it exits with a startup error naming VLM_TEMPERATURE as invalid

Given VLM_TEMPERATURE is set to a negative value (e.g. "-1")
When the server starts
Then it exits with a startup error naming VLM_TEMPERATURE as invalid

Given VLM_TEMPERATURE is set to a value exceeding the VLM model's
  maximum (e.g. "100")
When the server starts
Then it exits with a startup error naming VLM_TEMPERATURE as invalid

Given VLM_TEMPERATURE is set to a valid finite value within the
  acceptable range (e.g. "0.4", "0.7", "1.0")
When the server starts
Then startup proceeds normally and the value is available to the VLM client
```

**Spec reference:** `07-architecture.md` "Env var contract" (VLM_TEMPERATURE row, extend validation to reject non-finite and out-of-range values); `06-decisions.md` "Malformed VLM output: retry once at nonzero temperature, then flag" (temperature must be a valid finite value to ensure independent retry samples); flagged as non-blocking follow-up in `backlog/ING-006.md`

## Root cause

`floatEnv()` in `internal/config/config.go` uses `strconv.ParseFloat` which
accepts the strings `"NaN"`, `"Inf"`, and `"-Inf"` as valid `float64` values.
Additionally, it accepts any finite float including negative values and values
far exceeding what any VLM model supports (e.g., `100`, `-5`). These invalid
values would be stored in `Config.VLMTemperature` and passed to the VLM client
(ING-007), where they could crash llama.cpp or produce garbage output.

The fix applies to `floatEnv()` generically — all optional float env vars
(currently just `VLM_TEMPERATURE`) benefit from the guard.

## Implementation plan (one Coder pass)

1. **`internal/config/config.go`**: Add `math` import. In `floatEnv()`, after
   `strconv.ParseFloat` succeeds:
   - Check `math.IsNaN(v)` and `math.IsInf(v, 0)` → reject with
     `"invalid %s %q: must be a finite number"`
   - Check `v < 0 || v > 2` (or whatever range Ali confirms) → reject with
     `"invalid %s %q: must be between 0 and 2"`
   The range bound `[0, 2]` is a proposal pending Ali's confirmation.

2. **`internal/config/config_test.go`**: Add test cases to the `TestLoad`
   table:
   - `"NaN VLM_TEMPERATURE errors naming it"`
   - `"Inf VLM_TEMPERATURE errors naming it"`
   - `"negative VLM_TEMPERATURE errors naming it"` (e.g. `"-1"`)
   - `"out-of-range VLM_TEMPERATURE errors naming it"` (e.g. `"100"`)

3. **`tests/ing_001_config_test.go`**: Add black-box test
   `TestING006_NaNInf_InvalidTemperatureErrors` parameterized over
   `"NaN"`, `"Inf"`, `"-1"`, `"100"` values, verifying `config.Load()` returns
   an error containing `VLM_TEMPERATURE`.

4. **`tests/ing_001_server_integration_test.go`**: Add process-level integration
   test `TestING006_Integration_InvalidTemperatureExits` verifying the server
   process exits with code 1 and output contains both `"startup"` and
   `"VLM_TEMPERATURE"` for invalid values.

5. **`.env` and `.env.example`**: No changes needed — current value `0.4`
   is within the proposed range.

## Spec-implied edge cases

- `strconv.ParseFloat("NaN", 64)` returns `0 NaN` with no error → currently accepted, must reject
- `strconv.ParseFloat("Inf", 64)` returns `+Inf` with no error → currently accepted, must reject
- `strconv.ParseFloat("-Inf", 64)` returns `-Inf` with no error → currently accepted, must reject
- Negative finite values (e.g., `-1`, `-0.5`) are technically parseable but semantically invalid for temperature
- Values exceeding the model's maximum (e.g., `100`, `1000`) are technically parseable but would produce nonsensical VLM output
- `math.IsInf(v, 0)` catches both positive and negative infinity
- `06-decisions.md` says temperature must be "nonzero" to ensure independent retries — a value of `0` should be rejected (not just negative)
- All valid finite values in the accepted range (e.g., `0.1`, `0.4`, `0.7`, `1.0`, `2.0`) must continue to work
