### [ING-056] `internal/weather`: one log line per Open-Meteo attempt (forecast and geocoding)

**As a** wardrobe owner
**I want** every Open-Meteo call (forecast and city search) logged with its HTTP status,
elapsed time, response size and outcome, without the saved location's coordinates in
the default log
**So that** a weather failure is visible in local logs without a manual curl, and my
location does not end up in `logs/app.log` at the default level

**Acceptance criteria** (Gherkin):
```
Given a Client whose fake forecast server answers 200 with a valid body
When Forecast runs with a logger in the context
Then exactly one attempt record is logged
And it has message "weather attempt", endpoint "forecast", attempt=1, status=200,
  outcome "ok"
And it carries elapsed_ms, body_bytes (the response body length in bytes), host and path
And its level is info

Given a Client whose fake geocoding server answers 200 with valid results
When SearchCities runs with a logger in the context
Then exactly one attempt record is logged with endpoint "geocoding", attempt=1,
  status=200, outcome "ok", and the same attribute set

Given a forecast call to a URL with latitude 12.3456 and longitude 65.4321
When the attempt record is logged at level info, for each outcome (ok, http_error,
  unreachable, timeout, bad_body, read_error)
Then the log output contains no query string, and neither "12.3456" nor "65.4321"
And the record carries host and path only (for example host "127.0.0.1:PORT" and path
  "/v1/forecast")
And the error attribute of a transport failure does not contain the request URL
  (the *url.Error prefix "Get \"<url>\"" is stripped)
And for the "ok" and "bad_body" outcomes (fake 200 body beginning
  {"latitude":12.3456,"longitude":65.4321,...; the bad_body variant is valid JSON that
  lacks "current") the record carries body_bytes and no snippet attribute
And for the "http_error" outcome (for example 503 with {"error":true,"reason":"..."})
  the record carries a snippet of the body, at most 300 bytes
And unreachable and timeout attempts, which have no body, carry no snippet and still
  carry their error attribute

Given the same call with the logger at level debug
When the attempt is logged
Then the full request URL and the full response body appear in the log output, in a
  debug-level record or attribute

Given a search call whose text is a sentinel ("SENTINEL-CITY-51ab")
When SearchCities runs with the logger at level info
Then the sentinel does not appear in the log output
And at level debug the full URL (which carries it) may appear

Given a fake server that answers a non-2xx status (for example 503)
When Forecast or SearchCities runs
Then exactly one attempt record is logged (no retry exists and none is added)
And it has status=503, outcome "http_error", attempt=1, and is at warn level

Given a fake server that answers 200 with a body that is not valid JSON
When Forecast or SearchCities runs
Then the record has outcome "bad_body" and is at warn level

Given a fake forecast server that answers 200 with valid JSON that lacks "current" or
  has empty "daily" arrays (Forecast's malformed-response check)
When Forecast runs
Then exactly one attempt record is logged, with outcome "bad_body", not "ok"

Given a server that is not listening
When Forecast runs
Then exactly one attempt record is logged with status=0, body_bytes=0, outcome
  "unreachable", at warn level

Given a fake server that does not answer within the Client's timeout
When Forecast runs
Then exactly one attempt record is logged with status=0 and outcome "timeout"
And it is distinguishable from "unreachable"

Given a fake server that sends headers and then drops the connection mid-body
When Forecast runs
Then the record has outcome "read_error" (or "timeout" if the failure is a timeout)

Given the logger comes from the context (logging.WithLogger(ctx, l))
When Forecast or SearchCities runs
Then the records go to l
And with a ctx that carries no logger they go to slog.Default() without panicking
And weather.New's signature and the Client's exported methods are unchanged

Given a request through the api engine built with api.WithLogger
When GET /api/weather, GET /api/weather/cities?q=..., or POST /api/recommendations
  makes an Open-Meteo call
Then the attempt record's request_id equals the X-Request-ID response header and the
  request_id of the access-log record

Given every existing error path of Forecast and SearchCities
When the change is compared with the pre-change behavior
Then every error string is byte-for-byte unchanged (unreachable, unreachable or timed
  out, status <code>, unparseable body, missing current or daily values)
And the browser-facing 502 messages ("weather service unavailable: ...",
  "city search unavailable: ...") are unchanged
And the existing internal/weather tests and tests/ing_043 tests still pass

Given the change
When the diff is compared with the contract
Then the outbound requests are unchanged (same URLs, no new header, no API key)
And no retry, cache or new env var is added
And go.mod and go.sum are unchanged
```

**Spec reference:** `07-architecture.md` "## Logging", bullet "Outbound attempt logging
(LLM recommender and Open-Meteo)": "one log line per attempt with attempt number, HTTP
status, elapsed time, response body length, outcome and a 300-byte body snippet. The
full response body is logged only at `debug`... Open-Meteo exception: a successful
forecast body begins with the saved location's coordinates, so weather attempts include
the snippet only when the attempt failed (non-2xx or unreachable); `ok` and `bad_body`
outcomes log the length only, and request URLs with coordinates appear only at
`debug`. Error strings returned to the browser are unchanged"; and the "Request-scoped
logger" bullet (the weather client retrieves it from the context, falling back to
`slog.Default()`); `07-architecture.md` "### Weather (Phase 2)" (endpoints, "Outbound
HTTP timeout: 10 s", Open-Meteo unreachable, non-2xx or unparseable is `502`, "No API
key"); `06-decisions.md` "Structured logging: stdlib `log/slog`, local stderr + file,
env-configurable level/format", bullet "Outbound attempt logging (LLM and Open-Meteo)"
including its "Open-Meteo exception" ("LLM and weather attempts go to `app.log` under
their own message names"); `06-decisions.md` "Weather provider: Open-Meteo,
backend-proxied, no API key". Option A of the earlier open question (Ali) is what the
amended spec text records. The host-and-path-only rule for the request URL at `info` is
the implementation of "request URLs with coordinates appear only at `debug`".

**Status:** Done

**Context:** `internal/weather/weather.go` already threads `ctx` end to end:
`Forecast(ctx, lat, lon)` and `SearchCities(ctx, text)` both call the private
`(*Client).get(ctx, url, out)`, and `internal/api` passes `c.Request.Context()`
(`fetchWeather` in `api.go`, `searchCities` in `api.go`; `postRecommendations` reaches
it through `fetchWeather`). **No signature change and no change to `internal/api` is
needed** for the logger to arrive. The only Phase 2 edit is inside `internal/weather`
(this ticket touches Phase 2 code, explicitly): `get` gains the logging, takes an
endpoint label (`"forecast"` / `"geocoding"`) from its two callers, and
`internal/weather` imports `internal/logging` (`logging.FromContext(ctx)`; no
`Client` logger field, as in ING-055). Keep `get`'s decode-into-`out` behavior and
every returned error unchanged.

There is exactly one attempt per call: no retry exists and none is added, so
`attempt` is always `1`. Log it after the outcome is known. `Forecast` has a
post-decode check (missing `current` or empty `daily`) that returns an error after
`get` succeeded; that must be an outcome `bad_body`, still one record per call, so log
from a place that sees that result (Coder's choice: `Forecast` logs after its check,
or `get` accepts a validator).

Attribute names match ING-055 so the two tickets read alike: message
`"weather attempt"`; `endpoint`, `attempt` (int), `status` (int, 0 when no response),
`elapsed_ms` (int64), `body_bytes` (int), `outcome` (string), `host`, `path`, plus
`error` for non-`ok` outcomes. Outcomes: `ok`, `http_error`, `unreachable` (transport
failure that is not a timeout), `timeout`, `read_error`, `bad_body`. `ok` is `info`;
every other outcome is `warn`. `snippet` (first 300 bytes of the body) is logged only
for failed attempts that have a body, that is `http_error`; for `ok` and `bad_body` (and
`read_error`, where the body is partial and unreliable) log `body_bytes` only, never a
snippet, because a successful forecast body starts with the saved location's
coordinates (spec: Open-Meteo exception). `unreachable` and `timeout` have no body, so
there is nothing to snippet. The full URL and full body are logged only when
`logger.Enabled(ctx, slog.LevelDebug)`.

Privacy: the request URL carries the coordinates (`latitude=`, `longitude=`) or the
search text (`name=`). Log `req.URL.Host` and `req.URL.Path` only. Also do not log
the raw transport error: `http.Client.Do` returns a `*url.Error` whose text embeds
the full URL, so unwrap it (`errors.As` to `*url.Error`, log `.Err`). The error
returned to the caller (and so the browser's 502 text) is not changed, per the spec.
Discrepancy noted: the existing browser-facing 502 text ("weather service unavailable:
...", "city search unavailable: ...") embeds the request URL, coordinates included. The
spec says browser strings stay unchanged, so this ticket leaves them as they are; only
the server log is kept URL-free at `info`.

The levels above (`info` ok, `warn` failure) are this ticket's choice, in line with
the access log's status classes; the spec does not state them.

**Test note:** unit tests in `internal/weather` use `httptest.NewServer`, a
`bytes.Buffer` behind `slog.NewJSONHandler` at level info and at level debug, and
`logging.WithLogger(ctx, l)`. Timeout: `weather.New(url, url, 50*time.Millisecond)`.
Unreachable: close the server first. Mid-body drop: headers plus a larger
`Content-Length`, then `panic(http.ErrAbortHandler)`. Privacy AC: assert on the whole
log buffer, for every outcome, that `12.3456`, `65.4321`, `latitude=` and `?` (query

`"latitude":12.3456,"longitude":65.4321`, also as the `bad_body` variant), assert no
coordinates and no `snippet` attribute in the info-level record, only `body_bytes`. For
a failed call (503 with an error-text body), assert the `snippet` attribute is present

so build the engine directly). No `0*.md`, `agents/*.md`, or `AGENTS.md` edits;
`go.mod`/`go.sum` unchanged.

## Implementation notes

**What changed.** `internal/weather/weather.go` only (no signature change, no `internal/api` change). `get(ctx, endpoint, url, out, check)` logs exactly one `"weather attempt"` record per call from a deferred `logAttempt`, using `logging.FromContext(ctx)`. `Forecast` passes its missing-`current`/empty-`daily` check as `check`, so that case is `bad_body`, not `ok`. Every returned error string and the outbound request are unchanged.

| Record | Level | Attributes |
|---|---|---|
| `"weather attempt"`, `ok` | info | `endpoint` (`forecast`/`geocoding`), `attempt`=1, `status`, `elapsed_ms`, `body_bytes`, `outcome`, `host`, `path` |
| `"weather attempt"`, other outcome | warn | the same, plus `error` (with the `*url.Error` URL prefix stripped); `snippet` (300 bytes) only for `http_error` |
| `"weather response"` | debug, only when enabled | `endpoint`, `url` (full, with coordinates/search text), `body` |

Outcomes: `ok`, `http_error`, `unreachable`, `timeout`, `read_error`, `bad_body`. No snippet for `ok`, `bad_body`, `read_error` (coordinates), nor for body-less attempts.

**Tests.** `internal/weather/weather_log_test.go` (ok, geocoding + search-text sentinel, all six failure outcomes with coordinate/`?`/`latitude=` absence at info, debug URL and body, no logger in context). `tests/ing_056_weather_attempt_log_test.go` (`request_id` equality with the access record for `/api/weather`, `/api/weather/cities`, `/api/recommendations`).

**Existing test touched.** `ing053One` in `tests/ing_053_access_log_test.go` now selects the `"http request"` record instead of requiring a single record overall; the "dead upstream" route-table cases correctly emit a `weather attempt` record too. Assertions are otherwise unchanged.

**Verification.** `go vet ./...` clean, `go test -count=1 ./...` ok, `go.mod`/`go.sum` unchanged.

**Gap.** As with ING-055, error strings were not pinned as literals; the code is byte-identical and the existing weather and ING-043 tests pass.

**Review follow-up.** Added outcome `canceled` (caller context cancelled; was mislabelled `unreachable`), logged at warn. `isTimeout`/`snippet` moved to `logging.Outcome`/`logging.Snippet`, shared with the weather client. `elapsed_ms` now stops after the body read.
The `weather response` debug record is only written when a body was received.
