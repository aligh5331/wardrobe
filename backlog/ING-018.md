### [ING-018] Persist successfully tagged ingest outcomes to the catalog

**As a** wardrobe owner
**I want** `cmd/ingest` to write a non-flagged `Processor.Outcome` to
`internal/store` and copy the tagged photo into `data/photos/`, with the row's
`photo_path` pointing at that copy
**So that** a photo tagged end to end becomes a catalog row the grid UI can show,
without inventing a service layer this sprint

**Acceptance criteria** (Gherkin):
```
Given a photo whose tagging outcome is not flagged (Outcome.Flagged == false)
When cmd/ingest processes it
Then it writes exactly one catalog row via internal/store whose id is
  Outcome.ItemID and whose seven tagging fields equal Outcome.Result, with
  added_date set to the cataloging date and notes empty
And it copies the tagged photo into data/photos/ and stores that copy's path in
  the row's photo_path — not the original ingestion source path

Given a photo whose tagging outcome is flagged (Outcome.Flagged == true)
When cmd/ingest processes it
Then no catalog row is written and nothing is copied into data/photos/ for it,
  and its reporting is unchanged (the existing stdout JSON record plus the
  logs/vlm-attempts.jsonl trail from ING-012)

Given a successful ingest
When it completes
Then the original source photo is left untouched on disk, and the existing
  stdout JSON records for successful items are still emitted unchanged
  (ING-012 behavior preserved)

Given the CLI has already ingested a photo and is run again on a new one
When it completes
Then the new row is added without overwriting or mutating previously written
  rows or stored photos
```

**Spec reference:** `06-decisions.md` "Ingest→DB wiring: direct call, no
provider/service abstraction yet"; `04-data-schema.md` "Data schema — wardrobe
item" (`photo_path`, `added_date`, `notes`); `07-architecture.md` "Backend"
(image storage under `data/photos/`; path stored in the item's `photo_path`);
`backlog/ING-012.md` (existing CLI reporting behavior to preserve)

**Status:** Done

**Depends on:** ING-017 (the store's `Item`/`Open`/`Insert`). Do not start until
ING-017 is Done.

**Context / implementation notes**
- Direct call, no service/provider interface — `cmd/ingest` is the only writer
  (`06-decisions.md` "Ingest→DB wiring"); `internal/store`'s exported functions
  are the integration surface.
- Reuse `Outcome.ItemID` as the row id — do **not** mint a new uuid. ING-012
  already carries it into stdout for exactly this purpose.
- Copy naming: derive the stored filename from `Outcome.ItemID` and preserve the
  source extension (e.g. `<item-id>.jpg`) so repeated ingests cannot collide.
  `photo_path` is the path to that copy under `data/photos/`, never the original
  argument path.
- Run from the project root, like ING-012, so `data/wardrobe.db` and
  `data/photos/` are reached; both are gitignored (`07-architecture.md`).
- Preserve ING-012's per-photo order: process → emit stdout JSON → (new)
  persist only when `Outcome.Flagged == false`. A flagged item's stdout record
  is emitted exactly as today.
- Non-silent failure: a failed copy/open/insert must surface as an error in the
  existing CLI style rather than silently producing a half-written row. Do not
  design retry/rollback/cleanup behavior for copy failures this sprint — that is
  deferred.

**Out of scope (per Sprint 2 scope):** photo-copy failure handling (retry,
cleanup, rollback), pagination/filtering of the catalog, any edit or
manual-correction path, and any manual-review UI for flagged items.

### Reproducible failure (blocking)

When `cmd/ingest` starts, `main.go:44` calls `store.Open(store.DefaultDBPath)`.
`internal/store/store.go:43` opens GORM with an empty `&gorm.Config{}`, i.e. the
**default GORM logger, which writes to `os.Stdout`**. On a fresh DB,
`AutoMigrate` (`store.go:48`) exceeds GORM's 200 ms `SlowThreshold`, so the
child process writes the following to stdout *before* the JSON record:

```
2026/09/18 14:02:31 /home/ali/projects/go/wardrobe/internal/store/store.go:48 SLOW SQL >= 200ms
[233.972ms] [rows:0] CREATE TABLE `items` (`id` text,`category` text NOT NULL,...)
```

Observed verbatim from `TestING018_AC1_NonFlaggedOutcomePersistsRowAndPhotoCopy`
(stdout captured separately from stderr, so this is unambiguously stdout).
Because it depends on the 200 ms threshold it is intermittent, but it
reproduces readily under load and any slow query has the same effect.

**Why this fails the ticket:** AC3 requires "the existing stdout JSON records
for successful items are still emitted unchanged (ING-012 behavior preserved)"
and AC2 requires the flagged item's reporting to be unchanged. ING-012's
contract is one JSON object per line on stdout with warnings/errors on stderr
(its Review explicitly states: "stdout carries only one JSON object per emitted
photo … warnings and errors go to stderr via the standard logger, so the JSON
stream is not polluted"). A downstream JSON consumer (`ingest | jq`, the grid
UI) now breaks. The persistence *logic* is not at fault — only the store's log
destination is.

**Suggested fix (Coder's call):** in `internal/store/store.go`, give
`gorm.Open` a logger whose writer is `os.Stderr` instead of the default
`os.Stdout` (or `logger.Discard`); do not change the store's schema/behavior.
If Coder instead argues this is an ING-017 concern, it still must be fixed
before ING-018 can pass, because ING-018 is the ticket that introduces the
stdout-sensitive CLI call.

## Implementation notes (round 2 — fixes Tester's stdout-pollution FAIL)

**Issue addressed:** Tester's blocking failure — `store.Open` used GORM's
default logger, which writes to `os.Stdout`, so `AutoMigrate`'s

**Change — `internal/store/store.go` only (the root cause Tester identified):**
- `gorm.Open(sqlite.Open(path), &gorm.Config{})` now receives an explicit
  logger whose writer is `os.Stderr` instead of GORM's default `os.Stdout`:
  ```go
  gormLogger := logger.New(
      log.New(os.Stderr, "\r\n", log.LstdFlags),
      logger.Config{
          SlowThreshold: 200 * time.Millisecond,
          LogLevel:      logger.Warn,
      },
  )
  db, err := gorm.Open(sqlite.Open(path), &gorm.Config{Logger: gormLogger})
  ```
- Kept diagnostics rather than `logger.Discard`: slow SQL and GORM warnings
  still surface, just on stderr, matching the CLI's own `log` output and
  keeping stdout JSON-only. `SlowThreshold` (200ms) and `LogLevel` (`Warn`)
  match GORM's defaults, so only the destination changed.
- No schema, field, query, or return-value behavior changed. `internal/store`'s
  exported surface is untouched (no new env var, no new error path).

**Why here and not in `cmd/ingest`:** the writer is chosen when the GORM
connection is opened, inside `store.Open`; redirecting stdout in the CLI would
be a workaround and would also affect `log.Printf`-style output. Tester's
suggested fix named this exact location.
