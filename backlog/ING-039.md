### [ING-039] `internal/api`: Gin access-log middleware + `WithLogger` option

**As a** wardrobe owner
**I want** every HTTP request logged with method, matched route, status,
latency, size, client IP, and a generated `request_id`, at a level chosen from
the status class, with `request_id`/`item_id` joining server-side error logs
**So that** a local API request is observable and can be correlated with the
`logs/vlm-attempts.jsonl` trail, without adding any logger dependency

**Acceptance criteria** (Gherkin):
```
Given the Gin engine built by internal/api
When any request is served
Then exactly one access-log record is emitted for it
And that record carries the request method, the matched route, the response
  status, the latency, the response size, and the client IP
And it carries a generated request_id

Given a request whose response status is 2xx or 3xx
When the access log is emitted
Then its level is info
Given a request whose response status is 4xx
Then its level is warn
Given a request whose response status is 5xx
Then its level is error

Given any request
When the response is written
Then the response carries an X-Request-ID header equal to the request_id in
  the access-log record
And two different requests receive different request_ids

Given a request that results in a 5xx on a route where an item id is known
When the error-level access log is emitted
Then the record carries the request_id and the item_id
Given a 5xx on a request with no known item id
Then the record carries the request_id and no item_id

Given existing callers that call api.New(st, photosDir, ...) without a logger
When the engine serves a request
Then their behavior is unchanged and access logs go to slog.Default()
Given api.New is called with the new logger option
Then access-log records go to that logger

Given the middleware
When it is reviewed against the project's constraints
Then it is local only (no network/telemetry), adds no runtime dependency
  (stdlib log/slog), and the existing route set and handlers are unchanged
```

**Spec reference:** `07-architecture.md` "## Logging" — "HTTP access log: every
request to the Gin engine logs method, matched route, status, latency, response
size, client IP, and a generated `request_id`. The id is also returned to the
client as an `X-Request-ID` response header. Level follows the status class:
2xx/3xx `info`, 4xx `warn`, 5xx `error`", and "Correlation: server-side error
logs carry the access log's `request_id` and, where one exists, the tagged
`item_id` — so an API request can be joined to its `logs/vlm-attempts.jsonl`
records"; `06-decisions.md` "Structured logging: stdlib `log/slog`, local stderr
+ file, env-configurable level/format" (access logging; rejects `gin.Logger()`
as-is because its unstructured stdout line carries none of the correlation
fields).

**Status:** Ready

**Context:** The middleware takes a `*slog.Logger` (stdlib), so `internal/api`
does not need to import `internal/logging`; the default when the option is
absent is `slog.Default()`, keeping every existing caller — including the
`api.New(st, photosDir)` calls in `tests/` — behaviorally unchanged. The
`request_id` format is not pinned by the spec; reusing the codebase's existing
id generator (or an equivalent) is a Coder choice. Gin's `c.FullPath()` is the
"matched route" (empty on the `NoRoute` 404 path, which is acceptable); response
size is the Gin writer's byte count.

**Open point (do not guess past it):** `07-architecture.md` says the `item_id`
is attached "where one exists" without naming which routes know one or how a
handler conveys it. This ticket pins the clear case — a request carrying an item
id on its route (for example `/api/items/:id`) attaches it to a 5xx error
record, and a request without one omits it. If the Coder wants to also attach
the upload route's generated `item_id` or a `POST /api/items` body `item_id`,
that is a documented assumption to surface, not an invented requirement.

**Routing:** Ready → Coder. Touches `internal/api/` and its tests, plus one
`api.New(...)` call site in `cmd/server` to pass the logger option (default
`slog.Default()` for now; ING-040 points it at the configured logger).

**Depends on:** nothing new; stdlib `log/slog` only. Independent of ING-037/038.

**Out of scope:** building the logger from config (ING-038); replacing stdlib
`log` in `cmd/ingest`/`cmd/server` and passing the configured logger (ING-040);
any new route or handler change.

**Test note:** add engine-level tests using `httptest` and
`api.New(st, photosDir, api.WithLogger(slog.New(slog.NewJSONHandler(buf))))`,
asserting the field set, the level per status class, the `X-Request-ID`
round-trip, and the `item_id` presence/absence on a 5xx. Confirm the existing
route-set assertion (`TestING019_AC7_OnlyReadOnlyRoutes`) is unaffected — adding
middleware does not change `engine.Routes()`. No `0*.md`, `agents/*.md`, or
`AGENTS.md` edits; `go.mod`/`go.sum` unchanged.
