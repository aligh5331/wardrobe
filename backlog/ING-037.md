### [ING-037] Config: parse and validate `LOG_LEVEL` and `LOG_FORMAT`

**As a** wardrobe owner
**I want** `LOG_LEVEL` and `LOG_FORMAT` validated at startup like the other
`VLM_*` vars
**So that** a typo in a logging setting fails fast naming the variable instead
of silently choosing the wrong level or format

**Acceptance criteria** (Gherkin):
```
Given LOG_LEVEL and LOG_FORMAT are both unset (or empty)
When config.Load runs
Then the resolved config carries LogLevel "info" and LogFormat "text"
And no warning is produced for either

Given LOG_LEVEL is one of debug, info, warn, error in any letter case
When config.Load runs
Then the value is accepted and resolves to that level (case-insensitively)
And Load returns no error

Given LOG_FORMAT is one of text, json in any letter case
When config.Load runs
Then the value is accepted and resolves to that format (case-insensitively)
And Load returns no error

Given LOG_LEVEL is an unrecognized value (for example "verbose")
When config.Load runs
Then Load returns a startup error naming LOG_LEVEL
And no fallback level is silently used

Given LOG_FORMAT is an unrecognized value (for example "yaml")
When config.Load runs
Then Load returns a startup error naming LOG_FORMAT
And no fallback format is silently used

Given the existing VLM_* and LLM_* contract
When the two logging vars are added
Then Load still validates VLM_URL and the other VLM vars exactly as before
And the existing config tests still pass
```

**Spec reference:** `07-architecture.md` "### Env var contract" — the
`LOG_LEVEL` row ("one of `debug`, `info`, `warn`, `error` (case-insensitive) …
Anything else is a startup error naming the variable", default `info`) and the
`LOG_FORMAT` row ("one of `text`, `json` (case-insensitive)", default `text`);
`07-architecture.md` "## Logging" ("Level and format: `LOG_LEVEL` sets the
minimum level; `LOG_FORMAT` selects a text handler … or a JSON handler");
`06-decisions.md` "Structured logging: stdlib `log/slog`, local stderr + file,
env-configurable level/format" (validated at startup in the same strict style as
the other `VLM_*` vars; an unrecognized value is a startup error naming the
variable, not a silent fallback).

**Status:** Ready

**Context:** `internal/config/config.go` already has the strict helpers
`boolEnv` / `intEnv` / `floatEnv` and the pattern of returning a startup error
naming the variable. This ticket adds `LogLevel` and `LogFormat` to `Config`
and resolves them in `Load` using the same style. It is self-contained; the
logger that consumes these values is ING-038.

**Routing:** Ready → Coder. Touches `internal/config/` and its tests.

**Depends on:** nothing new.

**Out of scope:** constructing the `slog` handler (ING-038); the Gin access-log
middleware (ING-039); replacing stdlib `log` in the entrypoints (ING-040).

`setEnv` helper currently lists a fixed var set; add `LOG_LEVEL` and
