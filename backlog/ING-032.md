### [ING-032] API: `POST /api/items` — persist a confirmed draft

**As a** wardrobe owner
**I want** to save my corrected draft so the staged photo moves into the catalog
and one row is written
**So that** a confirmed item is cataloged exactly once, with no stray files

**Acceptance criteria** (Gherkin):
```
Given a valid staged draft — an item id whose staged photo exists under
  data/ingest-staging/ — and a body carrying the seven tagging fields
  (04-data-schema.md names) plus optional notes, all taxonomy-valid
When the client POSTs /api/items
Then it receives a 2xx, the staged photo ends up at
  data/photos/<item_id>.<ext>, exactly one catalog row is inserted with that id
  and photo_path, and the response is the created item in the same shape
  GET /api/items/:id returns

Given the create succeeds
When it completes
Then the staged file is gone from data/ingest-staging/ and there is no duplicate
  row or photo for that id

Given a body with an invalid enum value, an invalid category/subcategory pair,
  or a missing required tagging field
When the client POSTs /api/items
Then it receives 400 naming the offending field, no row is inserted, and no file
  is placed in data/photos/
And the staged upload is kept so the draft remains correctable — a
  field-validation 400 is not a failed create (confirmed by Ali; see the
  staged-file lifetime note below)

Given a body that is rejected by field validation (400)
When the create is not performed
Then the staged upload is kept intact, and no row is inserted and no file is
  placed in data/photos/

Given an item id whose staged photo does not exist
When the client POSTs /api/items
Then it receives 404 and no row is inserted

Given a create failure at either write (photo move or row insert)
When the create returns an error
Then no orphan photo remains in data/photos/ and no row points at a missing
  photo (06-decisions.md "Catalog writes must not leave orphan photos or
  dangling rows"), and the staged upload is removed (failed create)

Given the create path
When it writes the row and the photo
Then both go through the shared internal/catalog package (ING-028) — the API is
  a second caller, not a second implementation
```

**Spec reference:** `07-architecture.md` "Backend" → "Catalog write API
(interactive create/edit)" (`POST /api/items` — persist a confirmed draft; move
the staged photo into `data/photos/`; insert the row; invalid field 400 naming
the field; unknown id 404; staged uploads removed on save or failed create);
`06-decisions.md` "Interactive catalog create/edit UI" (save = move photo +
insert row; `id`, `added_date`, and the photo immutable) and "Catalog writes
must not leave orphan photos or dangling rows"; `06-decisions.md` "Second
catalog writer exists" (shared persistence); `04-data-schema.md` "Write-path
rules"; `05-vlm-tagging-spec.md` "Interactive tagging (web UI)" (the corrected
record is validated against the same enums).

**Status:** Done

**Context:** Persist is the second half of create: the upload (ING-031) produced
a staged file and a draft; this endpoint consumes them after the human confirms.
It performs no tagging and replaces no photo. The row write and the photo move
reuse the shared, rollback-safe create from ING-028, so the no-orphan /
no-dangling contract has one implementation.

**Routing:** Ready → Coder. Touches `internal/api/`, `cmd/server/`, and tests.
ING-034 (frontend add flow) depends on this.

**Depends on:** ING-028 (shared `internal/catalog` create), ING-031 (the
staged-draft contract this consumes).

**Test note:** the route-set assertion in
`tests/ing_019_api_test.go` (`TestING019_AC7_OnlyReadOnlyRoutes`) must include
the approved write routes (see ING-030's test note).

**Staged-file lifetime (confirmed by Ali):** a **field-validation 400** is *not*
a "failed create" — the staged upload is kept so the draft remains correctable
and the user can resubmit without re-uploading and re-running the model. The
staged file is removed on a successful save, on a tagging/upload failure
(ING-031), and on a persistence failure at either write. Staging is not
`data/photos/`, so keeping it on a validation rejection does not weaken the
no-orphan contract.

**Out of scope:** re-tagging or replacing the photo; accepting `id`,
`added_date`, or `photo_path` as changed values; delete; accepting a
client-supplied file path or filename (server-derived naming only).

**Approach**

- Body: `item_id`, optional `photo_ref`, the seven `04-data-schema.md`
  tagging fields, optional `notes`. `id`/`added_date`/`photo_path` are not
  decoded, so a body carrying them cannot reach the store.
- `item_id` is re-validated as a plain basename (`validPhotoName`).
  `photo_ref`, when present, must also be a plain basename naming the item
  id; otherwise 400. The staging path is joined from the validated id/ext,
  never from a raw client string (ING-031 review note; symmetry with
  `validPhotoName`).
- Staged existence is checked before field validation, mirroring PUT's
  id-before-body order; a missing staged photo is 404 with no row.
- Field validation reuses `tagging.ParseTaggingResult` (no second enum
  copy): invalid enum / invalid category-subcategory pair / missing
  required field → 400 naming the field, no row, no `data/photos/` file,
  and the staged upload is **kept** (validation is not a failed create).
- Persistence goes through the shared `internal/catalog.Create` (ING-028):
  a second caller, not a second implementation. The handler removes the
  staged upload on success and on a create failure; `catalog.Create` rolls
  back any photo copy on a failed insert, so no orphan/dangling state.
- Success is `201 Created` with the created item in the GET
  `/api/items/:id` shape (`toResponse`).

**Assumptions / deviations**

1. **Body field names.** The ticket names "the item id"; ING-034 says the
   client posts the item id and the ING-031 review note says `photo_ref`
   becomes client-supplied on the persist call. To satisfy both readings,
   the body is `{"item_id", "photo_ref", <7 fields>, "notes"}`: `item_id`
   is required, `photo_ref` is optional. When `photo_ref` is present it is
   re-validated; when omitted the server locates its own server-named
   `<item_id>.<ext>` in staging. Server-derived naming is preserved either
   way.
2. **Lookup order.** Malformed JSON → 400, then `item_id`/`photo_ref`
   trust-boundary 400, then staged-missing 404, then field-validation 400.
   PUT already resolves the id before the body, and the ticket's missing-
   staged criterion presupposes the id is located before field validation.
3. **Success status.** `201 Created` (the AC only requires 2xx); the body
   is the full read shape.
4. Trust-boundary 400s (`invalid item_id`/`invalid photo_ref`) remove
   nothing; only a create attempt (success or failure) touches staging.

**Decision: APPROVED**

Reviewed the uncommitted ING-032 diff (`internal/api/api.go`,
`tests/ing_019_api_test.go`, new `tests/ing_032_create_item_test.go`,
`tests/ing_032_tester_test.go`) against `07-architecture.md` "Catalog write
API" (`POST /api/items`), `06-decisions.md` "Interactive catalog create/edit
UI", "Second catalog writer exists", "Catalog writes must not leave orphan
photos or dangling rows", "Photo upload trust boundary", `04-data-schema.md`
"Write-path rules", `05-vlm-tagging-spec.md` "Interactive tagging (web UI)",
and `00-overview.md`'s hard constraints. Tester's evidence is taken as
standing; tests were not re-run.

### Findings

- **Spec intent met.** `createItem` consumes the ING-031 staged draft,
  validates the corrected record through the same `tagging.ParseTaggingResult`
  tables, then moves the photo and inserts the row in one
  `internal/catalog.Create` call. No second persistence implementation:
  `internal/api/api.go` contains no `st.Insert`/`os.WriteFile` of its own (only
  ING-031's staging I/O in `saveUpload`), so the API is a second caller, not a
  second copy ("Second catalog writer exists").
- **No-orphan / no-dangling holds on both failure branches.** `catalog.Create`
  rolls back its photo copy on a failed insert (`rollback`); the handler
  removes the staged upload on any `Create` error. The handled failure modes
  (`MkdirAll`, `ReadFile`, `WriteFile`, `Insert`) all leave no `data/photos/`
  residue and no new row. Field-validation 400 returns before `Create` and
  keeps the staged upload, per the Ali-confirmed lifetime note; success removes
  it. The 400/404 paths perform no writes.
- **Trust boundary sound.** `item_id` is re-validated with `validPhotoName`.
  A supplied `photo_ref` is re-validated as a plain basename that must
  prefix-match `item_id`, and only its (accepted-set) extension is used — the
  joined path is always `stagingDir/<id><ext>`, never the raw ref. Traversal,
  subdir, backslash, and mismatched refs are 400 with a canary outside staging
  untouched (`TestING032_Edge_TraversalReferencesRejected`).
- **Validation reuses `internal/tagging`.** Invalid enum, invalid
  category/subcategory pair, and missing required field all route through
  `tagging.ParseTaggingResult`; no second enum copy or invented values.
- **Status codes and no silent swallow.** 400 malformed JSON / invalid ref /
  field validation (field named), 404 missing staged photo, 500 create
  failure, 201 + GET `/api/items/:id` shape on success. `ParseTaggingResult`
  errors are surfaced, not swallowed.
- **Hard constraints — no violation.** Fully local (this route makes no
  model/network call), no new dependency (`go.mod`/`go.sum` unchanged), one
  photo per garment, no fine-tuning. No protected spec/agent file touched; the
  registered route set is exactly the 7 approved routes, no delete.
- **Scope discipline.** No drive-by changes; `cmd/server/` needed no edit
  because `New` already receives `photosDir` and `WithTagging` already carries
  `stagingDir`.

### Non-blocking notes

1. Optional client-supplied `photo_ref` sits in slight tension with the
   ticket's out-of-scope wording "accepting a client-supplied file path or
   filename". It is Ali-sanctioned by ING-031's review note, acts only as an
   extension selector, and never becomes the stored path, so server-derived
   naming holds. Documented as the ticket's assumption #1.
2. `_ = os.Remove(stagedPath)` (both branches) ignores a cleanup failure; a
   rare remove failure on the success path would leave staged residue while
   returning 201. Consistent with ING-031's existing pattern and not a
   contract breach in this local single-user context; a log line would be
   tidier if revisited later.
3. The duplicate-PK behavior in `catalog.Create` (overwrite-then-rollback of an
   id whose stored photo already existed) is inherited from ING-028, not
   introduced here; ids are pipeline-generated UUIDs, so a collision is not
   reachable through the API. Flagged for awareness only.

No hard-constraint violation, no spec-intent mismatch, no unmet acceptance
criterion. Status left at `Review` for Ali's final review and merge.
