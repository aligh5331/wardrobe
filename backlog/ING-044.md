### [ING-044] Frontend: weather panel (current + today, WMO code label)

**As a** wardrobe owner
**I want** a small weather panel in the web UI
**So that** I see today's weather for my location next to my wardrobe

**Acceptance criteria** (Gherkin):
```
Given GET /api/weather returns 200
When the app loads
Then a weather panel shows the location name, current temperature, apparent
  temperature, condition, today's min/max temperature, and today's
  precipitation chance

Given a weather_code in the response
When the panel renders the condition
Then the label comes from a frontend-only WMO code → label map (the backend
  sends only the raw code)

Given a weather_code not in the map
When the panel renders
Then it still renders the other values without crashing

Given any value in the /api/weather response is null (missing data)
When the panel renders
Then that value shows as "-" with its unit ("- °C", "- %"), a null weather_code
  shows condition "-", and every non-null value still renders (never "0" for null)

Given GET /api/weather returns 502 (or the request fails)
When the app loads
Then the panel shows a weather error message, and the catalog grid and
  "Add garment" flow load and work unchanged

Given the frontend code
When it is inspected
Then it calls only localhost /api/weather (no Open-Meteo origin in the bundle)
```

**Spec reference:** `07-architecture.md` "Backend" → "Weather (Phase 2)" (UI
paragraph: panel fields; "`weather_code` is the raw WMO code; mapping it to a
label/icon is a frontend concern"; null = missing data shown as `-`; weather
failures never affect catalog);
`06-decisions.md` "Weather provider: Open-Meteo, backend-proxied, no API key"
(browser only talks to localhost).

**Status:** Done

**Depends on:** ING-043 (`GET /api/weather`).

**Routing:** Ready → Coder. New component under `frontend/src/` rendered from
`App.jsx`, Tailwind v4 classes, one vitest test file mocking `fetch`.

## Implementation notes

**Changes**
- `frontend/src/WeatherPanel.jsx` (new): fetches `GET /api/weather` on mount,
  independently of `App`'s `/api/items` fetch (own `useEffect`, own
  loading/ready/error state — a weather failure cannot affect the grid or
  add flow, since they don't share state).
  - `WMO_LABELS`: frontend-only `code → label` map covering the code ranges
    the ticket/spec list (0 clear; 1–3 cloud; 45/48 fog; 51–67 drizzle/rain;
    71–77 snow; 80–82 showers; 95–99 thunderstorm). An unmapped code falls
    back to `` `Code ${code}` `` (AC3: "still renders … without crashing";
    spec allows "label omitted or generic" for unmapped — chose generic over
    omitted so the condition slot is never blank for a non-null code).
  - `conditionLabel`: `null`/`undefined` code → `"-"`.
  - `withUnit(value, unit)`: `null`/`undefined` → `` `- ${unit}` `` (literal
    `"- °C"` / `"- %"` per the ticket text), otherwise `` `${value}${unit}` ``
    — never `"0"` for null.
  - Renders location name, current temp/apparent temp/condition, today
    min/max, today precipitation chance. Tailwind v4 utility classes only,
    same conventions as `ItemCard`.
- `frontend/src/App.jsx`: import + render `<WeatherPanel />` in a wrapper div
  right under the header, above the add form and grid. No change to the
  `/api/items` fetch, `edit`, or add-flow state.
- `frontend/src/WeatherPanel.test.jsx` (new): 5 tests, one per AC —
  success render (AC1), known code → label (AC2), unmapped code doesn't
  crash and still renders other values (AC3), null fields render
  `"- °C"`/`"- %"`/condition `"-"` while non-null values still render, never
  `"0"` (AC4), 502 shows the weather error while `<App />`'s catalog grid and
  "Add garment" button load/work unaffected (AC5). Fetch stubbed per-URL with
  `vi.stubGlobal`, matching `App.test.jsx`/`ing_034_add.test.jsx`.
- `frontend/src/App.test.jsx`: the existing "loads read-only … exactly one
  call" assertion was stale once `WeatherPanel` added its own independent
  fetch. Changed `toHaveBeenCalledTimes(1)` to assert every call in that test
  (`/api/items` and `/api/weather`, both from the shared stub) has no
  `RequestInit` — preserves the original intent ("no write request") without
  hardcoding a call count that ING-044 legitimately changes. No other
  existing test file needed a change; the shared items-payload stub
  satisfies `WeatherPanel`'s fetch harmlessly via optional chaining.

**Assumptions**
- Panel placement: its own block between the header and the add
  form/grid, not inside the header flex row — ticket says "above or near the
  header" and doesn't specify inline vs. stacked; stacked keeps the header's
  existing layout untouched (smaller diff).
- Unmapped-code fallback is `Code <n>` (generic, visible) rather than
  omitting the label entirely — AC3 only requires "renders … without
  crashing," and a visible fallback is easier to eyeball in the UI than an
  empty condition slot.
- No new dependency, no icon library, per ticket. `weather_code` mapping
  lives only in `WeatherPanel.jsx`, not shared with any backend code (backend
  intentionally sends only the raw code, per `07-architecture.md`).

## Review (Reviewer)

Read ticket, diff (`WeatherPanel.jsx`, `WeatherPanel.test.jsx`, `App.jsx`,
`App.test.jsx`), `07-architecture.md` "Weather (Phase 2)" UI paragraph
(L53-97), `06-decisions.md` "Weather provider" (L17-36) and "Testing
tooling" (L133-157), AGENTS.md. Confirmed each required check directly
against source, not just Tester's report:

- **null-vs-0:** `withUnit`/`conditionLabel` (`WeatherPanel.jsx` L40-48) use
  `=== null || === undefined`, not a falsy check — `0` and `null` are
  distinguishable. Matches spec L79-82 exactly ("field is `null` … never
  `0`, UI shows `-`"). `AC4` test asserts absence of literal `0°C`/`0%`
  alongside the `-` cases, not just presence of `-`.
- **No Open-Meteo origin:** `git grep -in "open-meteo\|openmeteo"` under
  `frontend/src` → no matches. `WeatherPanel.jsx` calls only
  `fetch('/api/weather')` (relative, same-origin). Matches
  `06-decisions.md` L21-22 "browser only talks to localhost."
- **Weather failure isolation:** `WeatherPanel` owns its own `useEffect`/
  `status` state (L54-73), never reads or writes `App`'s `items`/`status`
  state. `App.jsx` diff is additive only (import + one wrapper `<div>` at
  L215-217) — no change to the `/api/items` effect, add-form, or edit
  state. `AC5`/`AC5b` tests render `<App />` and assert the empty-state
  text and enabled "Add garment" button simultaneously with the weather
  error text, for both the 502 case and the raw-rejection case. Matches
  spec L85-87 "weather failures never affect catalog routes."
- **No new dependency:** `git diff --stat -- frontend/package.json
  frontend/package-lock.json` → empty. No icon library imported anywhere
  in `WeatherPanel.jsx` (plain Tailwind `<span>`s, text only, consistent
  with `ItemCard`'s existing convention).
- **Testing conventions:** `WeatherPanel.test.jsx` uses `vi.stubGlobal`
  fetch routed per-URL, Testing Library `render`/`screen`/`within`, jsdom
  env from the shared `vite.config.js` — same pattern as
  `ing_033_edit.test.jsx`/`ing_034_add.test.jsx`. No mock-server
  dependency added. Matches `06-decisions.md` L142-154.
- **`App.test.jsx` edit not weakened:** old assertion was
  `toHaveBeenCalledTimes(1)`; new version loops every recorded fetch call
  and asserts `options` is `undefined` on each, plus keeps
  `toHaveBeenCalledWith('/api/items')`. Since `WeatherPanel` legitimately
  adds a second independent fetch, a literal call-count of 1 is now false
  regardless of correctness — the replacement still fails on any write
  (`POST`/`PUT`/`PATCH`/`DELETE` would show up as a non-`undefined`
  `options`), so the original "no write request on load" intent is
  preserved, not diluted.
- **Malformed weather_code:** unmapped code falls back to `` `Code ${code}` ``
  (visible, not blank) — spec L77-78 only requires the mapping be a
  frontend concern and AC3 only requires "without crashing"; spec text
  elsewhere (echoed in ticket L67-68) explicitly allows "generic" as one
  of the two acceptable options. Not a taxonomy/enum violation since
  `weather_code` isn't a `03-taxonomy.md` enum — it's WMO's own numeric
  code space, mapped 1:1 as documented.
- **No hard-constraint violations:** no cloud inference, no fine-tuning,
  no multi-garment assumption (N/A to this ticket), no Phase-3
  `LLM_URL`/`LLM_API_KEY` wiring, no outfit-recommender scope creep — all

- **Over-engineering check:** none found. Single component file, no
