### [ING-033] Frontend: edit an existing catalog item

**As a** wardrobe owner
**I want** to open an item from the grid, change its tags or notes, and save
**So that** I can fix a wrong label without re-running inference or touching the
photo

**Acceptance criteria** (Gherkin):
```
Given the catalog grid
When the user activates an edit control on an item's card
Then the client GETs /api/items/:id and opens a form pre-filled with the item's
  mutable fields (the seven tagging fields plus notes), with id, added_date, and
  the photo shown read-only

Given the edit form
When it needs the valid values for a field
Then it loads them from GET /api/taxonomy (ING-036) rather than a bundled
  client-side copy, so the choices match the enums the server validates against

Given the edit form
When the user changes fields and submits
Then the client PUTs /api/items/:id with the mutable fields, and on a 2xx the
  grid shows the updated values for that item

Given the server returns 400 naming a field
When the user submits
Then the named field is surfaced to the user and the error is not silently
  swallowed

Given the update
When it is sent
Then it never sends id, added_date, or photo_path as changed values, the photo
  is not replaced, and no re-tagging is triggered

Given the change
When it is reviewed against the project's constraints
Then it uses only the local API, adds no runtime dependency, and is covered by
  Vitest + Testing Library tests under frontend/ (npm test)
```

**Spec reference:** `07-architecture.md` "Backend" → "Catalog write API
(interactive create/edit)" (`GET`/`PUT /api/items/:id`) and "Taxonomy read route
(create/edit forms)" (`GET /api/taxonomy`, the enum source the form loads) plus
"Frontend" (React / Vite / Tailwind v4; tests via Vitest + Testing Library under
`frontend/`); `06-decisions.md` "Taxonomy exported to the browser via
`GET /api/taxonomy`, not a bundled copy"; `04-data-schema.md` "Write-path rules
(interactive create/edit)"; `05-vlm-tagging-spec.md` "Interactive tagging (web
UI)" (corrections validated against the same enums; no re-tagging).

  DOM (routed fetch stub, no new dependency).
- `frontend/src/App.test.jsx` — revised the ING-024 "read-only: no write
  controls" assertion, as the ticket named this as the first frontend ticket's
  job: loading still only GETs `/api/items` and renders no write form; the edit
  entry point now exists.

**Approach**
- Activating Edit calls `GET /api/items/:id` and `GET /api/taxonomy` in
  parallel, then opens the form. The taxonomy is never bundled into the JS.
- Select options come from that response: `categories` keys,
  `categories[category]` for subcategory, `colors`, `patterns`,
  `warmth_tiers`, `formality`; secondary colors are per-color checkboxes.
- Submit builds the body from the eight mutable values only and `PUT`s
  `/api/items/:id`; `id`/`added_date`/`photo_path` are never keys in it.
- On 2xx the returned item replaces the matching grid row and the form closes;
  the grid shows the updated values. On non-2xx the JSON body's `error` string
  is rendered in a `role="alert"` and the form stays open with the user's input.

**Assumptions**
1. The AC's "seven tagging fields plus notes" is sent as exactly `category,
   subcategory, dominant_color, secondary_colors, pattern, warmth_tier,
   formality, notes`.
2. `secondary_colors` is edited as a checkbox per palette color (native, no
   dependency); the palette is the taxonomy response, so it matches the server
   enum by construction.
3. Changing category clears the subcategory when the old value is not valid for
   the new category, so the form cannot knowingly submit an invalid pair (the
   server still validates).
4. After a successful save the grid is updated from the PUT response body (the
   same read shape as `GET /api/items/:id`) rather than refetching the list.
5. No new runtime dependency, no bundled taxonomy copy, local `/api` only.

**Decision: APPROVED**

**Reviewer** — 2026-09-24, on `sprint/ingestion-create-edit`. Reviewed the
uncommitted working tree (`git status --porcelain`: `M backlog/ING-033.md`,
`M frontend/src/App.jsx`, `M frontend/src/App.test.jsx`,
`?? frontend/src/ItemEditForm.jsx`, `?? frontend/src/ing_033_edit.test.jsx`)
against the ticket ACs, `07-architecture.md` ("Catalog write API",
"Taxonomy read route", "Frontend"), `06-decisions.md` ("Taxonomy exported to
the browser…", "Interactive catalog create/edit UI…"), `04-data-schema.md`
("Write-path rules"), `05-vlm-tagging-spec.md` ("Interactive tagging (web
UI)"), and `00-overview.md` constraints. Tester evidence not re-run per role.

**Findings — spec intent (not just AC wording)**

- **Field set is the contract field set.** `ItemEditForm.jsx` edits exactly
  `category, subcategory, dominant_color, secondary_colors, pattern,
  warmth_tier, formality, notes` — the seven tagging fields + notes that
  `04-data-schema.md` "Write-path rules" call editable. No extra field, no
  schema value invented.
- **Choices are genuinely server-derived, not a bundled copy.** Every option
  list comes from the fetched taxonomy (`Object.keys(taxonomy.categories)`,
  `categories[category]` for subcategory, `colors`, `patterns`,
  `warmth_tiers`, `formality`). No enum literal exists in `App.jsx` /
  `ItemEditForm.jsx` (only the empty `—` placeholder). The wire keys match
  ING-036's documented shape (`test`/`internal/api/api.go`), so a future
  taxonomy change reaches the form without a frontend edit —
  `06-decisions.md`'s stated intent, not merely the AC's wording.
- **Immutable fields are immutable by construction.** `handleSubmit`
  constructs the body explicitly from the eight mutable values only, so
  `id`/`added_date`/`photo_path` can never be keys. `id`, `added_date`, and
  the photo render as text/`img`, not as inputs. `App.submitEdit` sends one
  `PUT /api/items/:id` — no `POST /api/items/photo` re-tag, no create, no
  photo replacement. (Backend independently ignores those keys —
  `updateItemRequest`, `internal/api/api.go:212`.)
- **400 is surfaced, not swallowed.** Non-2xx path reads `body.error` and
  sets it into state, rendered in `role="alert"`; the form stays open with
  the user's input and the grid is not falsely updated. Matches the real
  server shape `{"error": "<field-naming message>"}`.
- **Success path updates the grid from the same read shape.** PUT returns
  `toResponse(updated)` (`internal/api/api.go:267`) — identical shape to
  `GET /api/items` elements — and the row is replaced by `updated.id`, so
  `photo_url`/`added_date`/`id` survive. Consistent with `04-data-schema.md`
  editable-field intent.

**Hard constraints** — clean

- Fully local: every request is a relative `/api/...` URL; no cloud/hosted
  host anywhere.
- No model / no fine-tuning: frontend only; no inference surface touched.
- No runtime dependency: `frontend/package.json` and `package-lock.json`
  `git diff` empty; no new import beyond the in-repo component.
- One photo per garment: the edit path never handles photos.
- No protected files: `git status` lists only the ticket and the four
  `frontend/src/` files; `0*.md`, `agents/*.md`, `AGENTS.md`, `go.mod`/`go.sum`,
  `frontend/dist/` placeholder untouched.

**Standards** — no swallowed errors; `openEdit`/`submitEdit` both surface a
user-facing message, and the non-2xx JSON parse is guarded. Form controls are
label-associated (`htmlFor`/`id`, `fieldset`+`legend`), the error is
`role="alert"`, and the form has an accessible name — accessible error
surfacing holds.

**Scope discipline** — the only touched test outside the new file is the
ING-033-assigned revision of `App.test.jsx`'s ING-024 "no write controls"
assertion (the ticket's Context names this as the first frontend ticket's
duty). It still asserts one `GET /api/items` and no `form`/`input`/`select`/
`textarea` on load; only the always-present Edit entry point was added. No
drive-by refactor, no visual redesign beyond the Edit button.

**Tester evidence stands:** `npm test` 3 files / 19 tests green, including
the ING-026 production-build test; per-AC table and the two added edge tests
(empty `secondary_colors`, no re-tag/upload request) are convincing.

**Non-blocking notes (no action required for merge)**

1. `submitEdit` wraps network and non-2xx parsing but not the 2xx
   `await res.json()` (`App.jsx:169`); a malformed 2xx body would leave the
   form stuck in `saving`. Not reachable with the current API (always returns
   the item JSON); worth a guard only if the response contract loosens.
2. Rapidly activating Edit on two different cards resolves last-writer-wins;
   negligible for a single-user localhost app.
3. All card Edit buttons share the accessible name "Edit" without per-item
   context; not required by the ACs.
4. The empty `—` option permits clearing a required field; the server's 400
   is surfaced (correct — the server stays the validator).
