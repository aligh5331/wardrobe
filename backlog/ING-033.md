### [ING-033] Frontend: edit an existing catalog item

**As a** wardrobe owner
**I want** to open an item from the grid, change its tags or notes, and save
**So that** I can fix a wrong label without re-running inference or touching the
photo

**Acceptance criteria** (Gherkin):
```
Given the catalog grid
When the user activates an edit control on an item's card
Then the client GETs /api/items/:id and opens a form pre-filled with the item's
  mutable fields (the seven tagging fields plus notes), with id, added_date, and
  the photo shown read-only

Given the edit form
When it needs the valid values for a field
Then it loads them from GET /api/taxonomy (ING-036) rather than a bundled
  client-side copy, so the choices match the enums the server validates against

Given the edit form
When the user changes fields and submits
Then the client PUTs /api/items/:id with the mutable fields, and on a 2xx the
  grid shows the updated values for that item

Given the server returns 400 naming a field
When the user submits
Then the named field is surfaced to the user and the error is not silently
  swallowed

Given the update
When it is sent
Then it never sends id, added_date, or photo_path as changed values, the photo
  is not replaced, and no re-tagging is triggered

Given the change
When it is reviewed against the project's constraints
Then it uses only the local API, adds no runtime dependency, and is covered by
  Vitest + Testing Library tests under frontend/ (npm test)
```

**Spec reference:** `07-architecture.md` "Backend" → "Catalog write API
(interactive create/edit)" (`GET`/`PUT /api/items/:id`) and "Taxonomy read route
(create/edit forms)" (`GET /api/taxonomy`, the enum source the form loads) plus
"Frontend" (React / Vite / Tailwind v4; tests via Vitest + Testing Library under
`frontend/`); `06-decisions.md` "Taxonomy exported to the browser via
`GET /api/taxonomy`, not a bundled copy"; `04-data-schema.md` "Write-path rules
(interactive create/edit)"; `05-vlm-tagging-spec.md` "Interactive tagging (web
UI)" (corrections validated against the same enums; no re-tagging).

**Status:** Ready

**Resolved (was blocked on the taxonomy source):** the edit form needs the
approved enum values so a corrected field can only be set to a valid one. This
is now decided: the backend serves them via `GET /api/taxonomy`
(`06-decisions.md` "Taxonomy exported to the browser via `GET /api/taxonomy`,
not a bundled copy"; `07-architecture.md` "Taxonomy read route (create/edit
forms)"), ticketed as ING-036. The form loads its choices from that route
instead of a bundled copy, so the client and server cannot drift.

**Context:** The grid (`App.jsx`) is deliberately read-only; this is the first
write control. `frontend/src/App.test.jsx` currently asserts the app renders no
write controls and only GETs `/api/items` — that assertion must be revised by
whichever frontend ticket lands first. The item card already renders every
schema field, so the edit form's field set is known; the taxonomy source is now
`GET /api/taxonomy` (ING-036).

**Routing:** Ready → Coder. Touches `frontend/src/` and its tests.

**Depends on:** ING-029, ING-030, ING-036.

**Out of scope:** creating items (ING-034); changing the grid's read behavior or
visual design beyond adding the edit entry point; re-tagging; photo replacement;
delete.
