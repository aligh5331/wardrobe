### [ING-040] `cmd/ingest` + `cmd/server`: use the configured slog logger; keep ingest stdout JSON-only

**As a** wardrobe owner
**I want** both entrypoints to log through the configured `slog` logger built
from `LOG_LEVEL`/`LOG_FORMAT`
**So that** level/format/sinks apply everywhere and `cmd/ingest`'s stdout stays
a strict one-JSON-object-per-line channel for the next pipeline stage

**Acceptance criteria** (Gherkin):
```
Given config and the internal/logging logger are built
When cmd/server starts
Then its startup warnings, startup errors, and "listening" line go through the
  configured slog logger (stderr + logs/app.log)
And no stdlib log.Printf/log.Fatalf call remains in cmd/server

Given cmd/ingest runs
When it loads config, warns, processes photos, or reports a hard error
Then every diagnostic goes to stderr and logs/app.log
And none of it is written to stdout

Given a photo and a reachable VLM
When cmd/ingest runs with LOG_FORMAT=json and LOG_LEVEL=debug
Then stdout contains exactly one JSON object per processed photo, and every
  stdout line parses as JSON with no log record mixed in
And the same holds with LOG_FORMAT=text and LOG_LEVEL=debug

Given LOG_FORMAT=json
When cmd/server logs a startup warning
Then the server log line is a JSON object

Given a startup config error (for example a missing VLM_URL)
When cmd/ingest runs
Then it exits nonzero with the error logged via the configured logger
And stdout remains empty

Given logs/app.log cannot be opened
When either entrypoint starts
Then startup still proceeds with stderr-only logging (ING-038's fallback)
And cmd/ingest's stdout stream is unaffected
```

**Spec reference:** `07-architecture.md` "## Logging" — "Sinks: process stderr
and `logs/app.log` (append/create)" with "Level and format … Both apply to
stderr and `logs/app.log` alike", and "Failure to open `logs/app.log`: startup
