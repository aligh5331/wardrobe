### [ING-003] Opt-in VLM request serialization workaround

**As a** wardrobe owner
**I want** an opt-in global one-at-a-time request queue for the VLM
client
**So that** I can work around known VLM concurrency bugs (e.g.
llama.cpp #17200) without paying the serialization cost by default

**Acceptance criteria** (Gherkin):
```
Given VLM_SERIALIZE_REQUESTS=true
When multiple tagging requests are submitted concurrently
Then they are processed one at a time through a single global
  queue/mutex — no two VLM requests are ever in flight simultaneously

Given VLM_SERIALIZE_REQUESTS=true and VLM_REQUEST_DELAY_MS=15
When one VLM request completes
Then the client waits 15ms before sending the next queued request

Given VLM_SERIALIZE_REQUESTS=false (default)
When multiple tagging requests are submitted
Then this queue is not engaged at all — behavior falls through to
  ING-002's concurrent default
```

**Spec reference:** `07-architecture.md` "VLM request behavior";
`06-decisions.md` "VLM request concurrency: concurrent by default,
serialize as opt-in workaround"

**Status:** Done

## Implementation notes

Implemented the opt-in serialization workaround in the VLM client
(`internal/tagging/client.go`), reusing the config values ING-001 already
parses (`VLMSerializeRequests`, `VLMRequestDelayMS`).

**Files**
- `internal/tagging/client.go`
  - `Client` gained `serialize bool`, `mu sync.Mutex`, and
    `delay time.Duration`.
  - New functional option `WithSerialization(delayMS int) Option` enables
    the queue and sets the post-response delay; without it behavior is
    unchanged.
  - `NewClient(vlmURL, apiKey string, opts ...Option)` is variadic, so all
    existing call sites (ING-002 tests, live test) compile unchanged.
  - `Tag` begins with `release := c.acquire(); defer release()`. When
    serialization is off `acquire` returns a no-op — the mutex is never
    touched, preserving ING-002's concurrent default. When on, it holds
    `mu` for the whole request and, on release, sleeps `delay` **before**
    unlocking so the next queued request cannot start until the delay has
    elapsed.
- `internal/tagging/client_test.go` — added `TestTag_Serialized`
  (overlap detector sees max in-flight == 1) and
  `TestTag_SerializedDelayBetweenRequests` (consecutive request starts
  spaced >= delay). Tester still owns the acceptance suite under `tests/`.

**Spec check vs `07-architecture.md` "VLM request behavior"**
- Default concurrent: no option → `serialize` false → no lock taken. Pass.
- Opt-in one-at-a-time: `serialize` true → single mutex around all `Tag`
  calls on the client. Pass.
- Delay only with serialization: `delay` is only read inside the
  serialized release path. Pass.
- Misconfig (`VLM_REQUEST_DELAY_MS>0`, serialize off) is already ING-001's
  startup warning; the option simply isn't passed, so no delay applies.
  Pass.

**Assumptions / deviations (for Tester + Reviewer)**
1. **"Global" interpreted per-`Client` instance.** The app is built around
   one `Client`, so a per-client mutex is the global queue; two separate
   `Client` values would serialize independently. Documented on the type.
2. **Delay is applied on every serialized `Tag` return**, not only when
   another request is already queued. Simplest correct implementation of
   "wait after each VLM response"; the last request in a burst pays one
   extra delay. Local pre-request failures (e.g. missing image) also sleep
   before releasing — a deliberate rate-limit, not a correctness issue.
3. **No config→client wiring in this ticket.** No handler constructs a
   `Client` yet (ING-002 note #3), so nothing reads `VLM_SERIALIZE_REQUESTS`
   in production. The mapping is:
   `if cfg.VLMSerializeRequests { opts = append(opts, tagging.WithSerialization(cfg.VLMRequestDelayMS)) }`.
   The future handler/route ticket should do this when it builds the client.
4. Negative `VLM_REQUEST_DELAY_MS` (ING-001 open item) is treated as no
   delay (`delayMS <= 0` never sets a sleep), so it cannot panic
   `time.Sleep`.

**Spec-implied edge cases checked**

  `delayMS` = `0` and `-5` the client still serializes (peak in-flight
  exactly 1, all requests sent, no panic from `time.Sleep`). This closes
  ING-001's open question about a negative delay. At the client API a
  delay cannot be set without enabling serialization, so the "delay set
  while serialize off → warning" case stays ING-001's config-side test
  (`TestING001_AC3_DelayWithoutSerializeWarns`).
- The wait is tied to the configured value, not to serialization itself:
  `TestING003_Edge_DelayIsConfigurable` (0 vs 150ms contrast).

**Observations / follow-ups for Planner (non-blocking, no AC failure)**
1. **"Global" is per-`Client` instance.** Two `Client`s each built with
   `WithSerialization` can overlap (verified with a throwaway probe:
   peak in-flight = 2). The spec says "global one-at-a-time queue/mutex";
   the app constructs a single client, so production behavior is
   equivalent, but if a second client is ever created it will not share
   the queue. Consistent with Coder assumption #1 — flag for Reviewer.
2. **The queue wait is not context-aware.** `acquire()` uses a plain
   `sync.Mutex.Lock()`, so a caller blocked behind a long request will
   not return early if its `ctx` is cancelled; it waits for the lock then
   proceeds. The spec does not require cancellation of queued waiters,
   but the future handler ticket should be aware when setting deadlines.
3. Delay is applied on every serialized `Tag` return, including the last
   request of a burst and local pre-request failures (missing image) —
   Coder assumption #2; harmless rate-limiting, not a spec violation.

**Spec intent (not just AC wording)**
- **Default concurrent preserved.** `acquire()` returns a no-op when
  `serialize` is false, so no mutex is ever taken on the default path —
  matches "Default: concurrent requests … no artificial bottleneck".
- **Opt-in one-at-a-time.** The mutex spans the whole `Tag` call, so at
  most one VLM request is in flight; the Tester's server-side overlap
  detector confirms peak == 1, and the live run with a 2000ms delay shows
  request endings spaced by the configured delay beyond inference time.
- **Delay only with serialization.** `delay` is read solely inside the
  serialized release path; the option is the only way to set it, so the
  "delay set while serialize off → startup warning" case remains
  ING-001's config concern. Correct separation.
- **Release on every path.** `release` is deferred before any I/O, so the
  mutex is released on the local-error, transport-error, non-2xx, bad
  envelope, and success paths alike. No deadlock/lock-leak path.
- **No new dependency, no request-shape change.** `go.mod` untouched; the
  single-image request and `ErrVLMUnreachable` classification are
  unchanged, so this ticket does not regress ING-002.
