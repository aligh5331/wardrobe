### [ING-001] Load and validate VLM/LLM env var contract at startup

**As a** wardrobe owner
**I want** the server to load and validate `VLM_URL`, `VLM_API_KEY`,
`VLM_SERIALIZE_REQUESTS`, and `VLM_REQUEST_DELAY_MS` at startup
**So that** misconfiguration fails fast and loudly instead of causing
confusing errors mid-ingestion

**Acceptance criteria** (Gherkin):
```
Given VLM_URL is unset or empty
When the server starts
Then it exits with a startup error naming VLM_URL as the missing
  required variable

Given VLM_API_KEY is unset
When the server starts
Then startup proceeds normally and no Authorization header is sent on
  VLM requests

Given VLM_REQUEST_DELAY_MS is set to a nonzero value and
  VLM_SERIALIZE_REQUESTS is false or unset
When the server starts
Then it logs a startup warning that the delay will not be applied, and
  proceeds without a hard error

Given VLM_SERIALIZE_REQUESTS is unset
When the server starts
Then it defaults to false (concurrent VLM requests, no artificial
  bottleneck)

Given LLM_URL is unset
When the server starts
Then startup proceeds normally — LLM_URL validation is NOT enforced in
  Phase 1, since there is no Phase 1 consumer of it yet
```

**Spec reference:** `07-architecture.md` "Env var contract" and "VLM
request behavior" sections; `06-decisions.md` "VLM request concurrency"
and "`LLM_URL`/`LLM_API_KEY` provisioned ahead of use" entries

**Status:** Review

## Implementation notes

Implemented the env var contract as a small `internal/config` package plus
the server entrypoint that consumes it.

**Files**
- `internal/config/config.go` — `Config` struct + `Load()` (reads
  `VLM_URL`, `VLM_API_KEY`, `VLM_SERIALIZE_REQUESTS`,
  `VLM_REQUEST_DELAY_MS`, `LLM_URL`, `LLM_API_KEY`) and `Warnings()`.
- `internal/config/config_test.go` — unit self-check of the loading /
  validation rules below (Tester still owns the acceptance suite).
- `cmd/server/main.go` — calls `config.Load()`, logs any warnings, then
  serves. Removed the now-redundant `cmd/server/.gitkeep`.

**Behavior**
- `VLM_URL` empty/unset → `Load()` returns an error
  `missing required environment variable: VLM_URL`; main logs
  `startup: ...` to stderr and exits 1.
- `VLM_API_KEY` optional, stored as-is (empty allowed). Startup proceeds.
- `VLM_SERIALIZE_REQUESTS` defaults to `false`; `VLM_REQUEST_DELAY_MS`
  defaults to `0`.
- Delay > 0 with serialization off → `Warnings()` returns one warning;
  main logs it as `startup warning: ...` and continues.
- `LLM_URL` / `LLM_API_KEY` are read but deliberately **not** validated —
  no Phase 1 consumer.

**Assumptions / deviations (for Tester + Reviewer)**
1. New `internal/config` package — `07-architecture.md`'s file tree lists
   only `internal/tagging`, `internal/store`, `internal/api`. Config is
   shared by `cmd/server` and (later) the VLM client, so a package is the
   right home rather than burying it in `main`.
2. `cmd/server` uses stdlib `net/http` on a hardcoded `:8080`, not Gin.
   Gin is mandated by `07-architecture.md` but this ticket has no routes,
   so pulling in the dependency now would serve nothing. Wire Gin in the
   first route-bearing ticket. Flagging so it isn't mistaken for an
   oversight.
3. Only the **process environment** is read; `.env` is not auto-loaded
   (no dotenv dependency added). Local runs need the vars exported (or a
   future ticket can add `.env` loading). Note the default run with an
   unset `VLM_URL` intentionally fails fast.
4. The "no Authorization header on VLM requests" clause is **not fully
   exercisable here** — there is no VLM client until a later ticket. This
   ticket guarantees the contract side: `VLM_API_KEY` may be empty and
   startup proceeds; the client will gate the header on
   `cfg.VLMAPIKey != ""`.
5. Beyond the literal ACs: an unparseable `VLM_SERIALIZE_REQUESTS` or
   `VLM_REQUEST_DELAY_MS` is a startup error naming the variable (chosen
   over silently defaulting, to match "fails fast and loudly"). A
   negative delay is treated as no delay (only `>0` warns).

### Follow-ups flagged (not failures; none block this ticket)

1. **Whitespace-only `VLM_URL` is accepted** (`"   "` passes `!= ""`).
   Contradicts the ticket's "fail fast and loudly" intent. Recommend a
   small follow-up: `strings.TrimSpace` before the emptiness check —
   Planner to ticket.
2. **Negative `VLM_REQUEST_DELAY_MS` is accepted** and stored as-is with
   no warning. Spec only defines `>0`; behavior is harmless but
   undefined. Flag for the VLM-client ticket to decide (reject, or treat
   as 0).
3. **"No Authorization header sent" is not exercised anywhere** because
   no VLM client exists yet. Whichever ticket implements the VLM client
   MUST gate the header on `cfg.VLMAPIKey != ""` and cover it with a
   test; otherwise this half of AC2 is unverified. Planner to ensure a
   ticket owns it.
4. Observations for Reviewer only (not test failures): `internal/config`
   is a new package not in `07-architecture.md`'s tree, and
   `cmd/server` uses stdlib `net/http` rather than Gin. Both are

Reviewed: the Coder diff (`internal/config/config.go`,
`cmd/server/main.go`, `internal/config/config_test.go`), Tester's
`tests/` suite and reported results, the cited spec sections
(`07-architecture.md` "Env var contract" / "VLM request behavior",
`06-decisions.md` "VLM request concurrency" / "LLM_URL/LLM_API_KEY
provisioned ahead of use"), and `00-overview.md`'s hard constraints.

### Hard constraints (`00-overview.md`) — PASS, no violations

- **Fully local:** the only imports are stdlib (`os`, `errors`, `fmt`,
  `strconv`, `log`, `net/http`). No cloud SDK, no hosted-inference
  client, no network call at all in this diff. `VLM_URL` is read as an
  opaque string; nothing dials it yet. Default `.env` target is a LAN
  address (`192.168.0.100`), consistent with local serving.
- **No fine-tuning:** no training/eval code, no model artifacts.
- **One photo per garment:** untouched; no image-handling code added.
- **No secret leakage:** `VLM_API_KEY`/`LLM_API_KEY` are stored but never
  logged; the startup warning prints only the delay integer.

### Spec intent (not just literal ACs) — matches

- Required/optional flags and defaults match the contract table exactly:
  `VLM_URL` errors when empty; `VLM_API_KEY`/`LLM_API_KEY` optional;
  `LLM_URL` deliberately unvalidated in Phase 1 (no consumer);
  `VLM_SERIALIZE_REQUESTS` defaults `false`; `VLM_REQUEST_DELAY_MS`
  defaults `0`.
- Misconfiguration handling matches `06-decisions.md`: delay `>0` with
  serialization off is a **warning + proceed**, not a hard error — the
  warning text names both vars and states the delay won't apply.
- The ticket is correctly scoped to the config contract. The actual
  serialized-queue/delay mechanics belong to the VLM client and are not
  pretended to be implemented here.

### General standards — PASS

- **Error handling:** missing required var and unparseable optional
  values both return named errors; `main` fails fast via `log.Fatalf`
  and exits 1. No swallowed errors.
- **No silent swallowing:** warnings are surfaced through
  `Config.Warnings()` and logged; the empty API-key case is explicit,
  not defaulted-over.
- Taxonomy/schema enum validation and the malformed-VLM-output cases in
  `05-vlm-tagging-spec.md` are **not applicable** to this ticket (no
  tagging/parsing code yet).

### Accepted deviations (Coder-documented, not blockers)

- New `internal/config` package not shown in `07-architecture.md`'s
  illustrative tree — reasonable shared home for the contract; the tree
  is descriptive, not exclusive.
- stdlib `net/http` instead of Gin, and a hardcoded `:8080`. This
  ticket's cited spec sections don't cover the router, and there are no
  routes to register. **Condition of approval:** the first
  route-bearing ticket must wire Gin and make the listen address
  configurable; the empty-mux placeholder must not survive into it.
- Only the process environment is read; `.env` is not parsed. This is
  unspecified in the spec, not a contract violation.

3. **AC2's "no Authorization header" half is unverified** until a VLM
