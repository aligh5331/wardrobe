### [ING-010] Negative VLM_REQUEST_DELAY_MS clamps to 0 with a startup warning

**As a** wardrobe owner
**I want** a negative `VLM_REQUEST_DELAY_MS` treated as `0` and surfaced as
a startup warning
**So that** a typo can't be silently reinterpreted as "wait a negative
amount of time", and a bad value doesn't hard-fail startup either

**Acceptance criteria** (Gherkin):
```
Given VLM_REQUEST_DELAY_MS is set to a negative value (e.g. "-100")
When the server starts
Then startup proceeds normally, VLMRequestDelayMS is 0, and a startup
  warning is logged naming VLM_REQUEST_DELAY_MS as negative and stating
  it was treated as 0

Given VLM_REQUEST_DELAY_MS is unset or set to "0"
When the server starts
Then no warning is logged and the value is 0

Given VLM_REQUEST_DELAY_MS is set to a positive value and
  VLM_SERIALIZE_REQUESTS is unset or false
When the server starts
Then the existing misconfiguration warning still fires and the delay
  value is unchanged (not clamped)

Given VLM_REQUEST_DELAY_MS is set to a non-numeric value
When the server starts
Then it exits with a startup error naming VLM_REQUEST_DELAY_MS as
  invalid (unchanged from ING-001)
```

**Spec reference:** `07-architecture.md` "Env var contract"
(`VLM_REQUEST_DELAY_MS` row); `07-architecture.md` "VLM request behavior"
("Delay on top of serialization", "Misconfiguration handling");
`06-decisions.md` "Env var bounds" entry

**Prerequisite:** the `07-architecture.md` / `06-decisions.md` update
stating negative-delay behavior must land before Coder starts.

**Status:** Review

**Decision:** Ali, settling ING-009 decision 3 — a negative delay defaults
to `0` with a warning (not a startup error, not stored as-is). Follow-up

## Implementation notes

Implemented the clamp in `Load` at the `VLM_REQUEST_DELAY_MS` call site
rather than inside the shared `intEnv` helper, mirroring ING-008's "bounds
live at the call site, not in the shared helper" decision.

**Files changed**
- `internal/config/config.go`
  - Added unexported `Config.delayWasNegative bool` to remember that the
    raw value was negative after the clamp discards it — `Warnings()` only
    sees the clamped `0`, so it needs that bit to decide whether to warn.
  - In `Load`, after `intEnv("VLM_REQUEST_DELAY_MS", 0)` succeeds:
    `if delayMS < 0 { cfg.delayWasNegative = true; delayMS = 0 }`, then
    store. Non-numeric still returns `intEnv`'s
    `invalid VLM_REQUEST_DELAY_MS %q: must be an integer` unchanged.
  - `Warnings()` now builds a slice (initialized empty, not nil) and
    prepends `"VLM_REQUEST_DELAY_MS is negative; treated as 0"` when
    `delayWasNegative`, then keeps the existing positive-delay /
    serialize-off warning unchanged.
- `internal/config/config_test.go`
  - `TestLoad` cases: `-100` → delay `0`, 1 warning; `-5` with
    `VLM_SERIALIZE_REQUESTS=true` → delay `0`, 1 warning; `0` → 0
    warnings.
  - `TestWarnings_NegativeDelayContent`: asserts the warning text
    contains `VLM_REQUEST_DELAY_MS`, `negative`, and `0` (the AC requires
    the warning to name the var and state the treated value, not merely
    exist).
