### [ING-031] API: `POST /api/items/photo` — upload, tag locally, return a non-persisted draft

**As a** wardrobe owner
**I want** to upload one garment photo and get back the local VLM's tagging as a
draft that is not saved yet
**So that** I can review and correct the tags in the browser before anything is
written to the catalog

**Acceptance criteria** (Gherkin):
```
Given a multipart upload of one garment photo with an accepted extension
  (.jpg / .jpeg / .png / .webp)
When the client POSTs /api/items/photo
Then the backend runs the existing local tagging pipeline
  (internal/tagging, 05-vlm-tagging-spec.md) against the upload and returns a
  non-persisted draft: the seven tagging fields (04-data-schema.md) plus the
  generated item id and a reference the client posts back to persist
And no catalog row is written and no file is placed in data/photos/

Given a valid uploaded photo
When the draft is produced
Then the staged file is server-named <item_id>.<ext> under the gitignored
  data/ingest-staging/ staging directory, and the client-supplied filename is
  never used as a path — a traversal filename cannot escape the staging dir

Given an upload whose extension is not one of .jpg / .jpeg / .png / .webp
When the client POSTs /api/items/photo
Then it receives 400, no VLM call is made, and nothing is staged

Given an upload larger than 20 MiB
When the client POSTs /api/items/photo
Then it is rejected with a 4xx, no VLM call is made, and nothing is staged

Given a model response that fails validation
When the existing retry-once policy also fails (05-vlm-tagging-spec.md
  "Output validation")
Then the failure is surfaced to the client as a non-2xx error, nothing is
  persisted, and the staged upload is removed so no residue accumulates

Given the VLM is unreachable (tagging.ErrVLMUnreachable)
When the client POSTs /api/items/photo
Then the error surfaces without a retry (05-vlm-tagging-spec.md,
  06-decisions.md) and no row is written

Given the route surface
When routes are inspected
Then the approved write route POST /api/items/photo is registered, and the
  existing read routes are unchanged
```

**Spec reference:** `07-architecture.md` "Backend" → "Catalog write API
(interactive create/edit)" (`POST /api/items/photo` — multipart upload, stage,
run the local VLM, return a non-persisted draft) and "Full project structure"
(`data/ingest-staging/`); `06-decisions.md` "Interactive catalog create/edit UI:
local VLM draft, human confirm, shared persistence" (create returns an
unpersisted draft; no re-tagging of existing items); `06-decisions.md` "Photo
upload trust boundary: fixed types, size cap, server-derived filename" (the
`.jpg/.jpeg/.png/.webp` set, 20 MiB cap, server-derived `<item_id>.<ext>`,
staging removed on save/failure); `05-vlm-tagging-spec.md` "Interactive tagging
(web UI)" and "Output validation"; `04-data-schema.md`.

**Status:** Ready

**Context:** The upload endpoint is the first client-supplied file surface. It
reuses the same model, prompt, and retry-once policy as `cmd/ingest` (no new
model, no fine-tuning); the only difference from the CLI is that the result is a
draft the human confirms before persist. Serving already rejects path traversal
via `validPhotoName` (`internal/api/api.go`); this ticket must extend the same
discipline to the write side.

**Routing:** Ready → Coder. Touches `internal/api/`, `cmd/server/` (the server
must build a tagging `Processor` from config like `cmd/ingest` does; `VLM_URL`
is already required at startup by `config.Load`), and tests. ING-032 (persist)
and ING-034 (frontend add flow) depend on this.

**Depends on:** the existing `internal/tagging` pipeline; no dependency on the
store.

**Test note:** the route-set assertion in
`tests/ing_019_api_test.go` (`TestING019_AC7_OnlyReadOnlyRoutes`) must be
updated to include the approved write routes (see ING-030's test note).

**Note (staged lifetime across upload/persist):** a failed or abandoned tagging
removes the staged upload here; the successful-save and failed-persist cleanup
belongs to ING-032. Whether a field-validation 400 at persist keeps or removes
the staged file is addressed on ING-032.

**Out of scope:** persisting the draft (ING-032); the frontend upload UI
(ING-034); multi-photo/bulk upload (not in Phase 1); outfit-photo detection;
delete.
