### [ING-031] API: `POST /api/items/photo` — upload, tag locally, return a non-persisted draft

**As a** wardrobe owner
**I want** to upload one garment photo and get back the local VLM's tagging as a
draft that is not saved yet
**So that** I can review and correct the tags in the browser before anything is
written to the catalog

**Acceptance criteria** (Gherkin):
```
Given a multipart upload of one garment photo with an accepted extension
  (.jpg / .jpeg / .png / .webp)
When the client POSTs /api/items/photo
Then the backend runs the existing local tagging pipeline
  (internal/tagging, 05-vlm-tagging-spec.md) against the upload and returns a
  non-persisted draft: the seven tagging fields (04-data-schema.md) plus the
  generated item id and a reference the client posts back to persist
And no catalog row is written and no file is placed in data/photos/

Given a valid uploaded photo
When the draft is produced
Then the staged file is server-named <item_id>.<ext> under the gitignored
  data/ingest-staging/ staging directory, and the client-supplied filename is
  never used as a path — a traversal filename cannot escape the staging dir

Given an upload whose extension is not one of .jpg / .jpeg / .png / .webp
When the client POSTs /api/items/photo
Then it receives 400, no VLM call is made, and nothing is staged

Given an upload larger than 20 MiB
When the client POSTs /api/items/photo
Then it is rejected with a 4xx, no VLM call is made, and nothing is staged

Given a model response that fails validation
When the existing retry-once policy also fails (05-vlm-tagging-spec.md
  "Output validation")
Then the failure is surfaced to the client as a non-2xx error, nothing is
  persisted, and the staged upload is removed so no residue accumulates

Given the VLM is unreachable (tagging.ErrVLMUnreachable)
When the client POSTs /api/items/photo
Then the error surfaces without a retry (05-vlm-tagging-spec.md,
  06-decisions.md) and no row is written

Given the route surface
When routes are inspected
Then the approved write route POST /api/items/photo is registered, and the
  existing read routes are unchanged
```

**Approach:**
- Body bounded with `http.MaxBytesReader`; missing/malformed part → 400;
  oversize → 413; bad extension → 400 (no VLM call, nothing staged).
- Fresh item id generated; staged server-named `<item_id>.<ext>` under
  `data/ingest-staging/`; client filename never used as a path.
- `ProcessWithID` runs the existing tagging + retry-once policy; stage removed
  on error or flagged outcome; `ErrVLMUnreachable` surfaces without retry.
- Draft (non-persisted) response carries `item_id`, `photo_ref`, and the seven
  flattened tagging fields; no row, no `data/photos/` write.

**Assumptions:**
1. Multipart field name is `"photo"`.
2. Draft reference field is `"photo_ref"` (basename only, no path separators);
   `photo_ref == <item_id><ext>`.
3. `ProcessWithID`/`NewItemID` added to `internal/tagging` so the staged
   filename and draft id stay identical per `06-decisions.md` ("id comes from
   the tagging pipeline").
4. Status codes: 400 bad ext/missing part, 413 oversize, 422 validation
   failure after retry, 502 VLM unreachable, 503 unconfigured.
5. `data/ingest-staging/` is already covered by the repo's `data/` `.gitignore`
   rule.

**Spec intent (beyond the literal AC wording)**

- **Trust boundary is genuinely enforced, not just asserted.**
  `acceptedPhotoExts` is the fixed `.jpg/.jpeg/.png/.webp` set
  (`06-decisions.md` "Photo upload trust boundary"), checked on the
  lowercased `filepath.Ext` *before* staging or the VLM call
  (`api.go:317-321`). The cap is `20 << 20` with an envelope check plus an
  explicit `FileHeader.Size` check (`api.go:300-315`). The stored name is
  `itemID + ext` where `itemID` is a UUID from `tagging.NewItemID()`
  (`api.go:323-333`); the client filename is used only for its extension and
  never as a path, so `../../..`, `..\..`, and subdir names reduce to an
  allowlisted suffix and cannot escape `stagingDir`. Reviewed
  `saveUpload`/`stagedPath`: no `filepath.Join` with client input.
- **Draft is truly non-persisted.** `uploadPhoto` never touches `st.Store`
  and never writes `DefaultPhotosDir`; the only filesystem write is under
  `stagingDir`. `draftResponse` embeds `tagging.TaggingResult`, which has
  exactly the seven schema fields, plus `item_id`/`photo_ref`
  (`04-data-schema.md`; `07-architecture.md` "Catalog write API").
- **Retry-once and unreachable semantics are preserved.** `ProcessWithID`
  is byte-for-byte the old loop moved verbatim; `Process` now just mints the
  id and delegates. `ErrVLMUnreachable` still returns immediately and is
  mapped to 502 without a retry (`api.go:341-349`;
  `05-vlm-tagging-spec.md` "Output validation"). A post-retry validation
  failure (`outcome.Flagged`) is surfaced as 422 and *not* persisted —
  exactly `05-vlm-tagging-spec.md` "Interactive tagging (web UI)": surfaced
  for retry/other photo, not flagged-and-persisted.
- **Validation reuses the existing pipeline.** No second enum copy; the
  handler delegates to `ParseTaggingResult` via `ProcessWithID`. No invented
  taxonomy/schema value.
- **Staged cleanup on every failure branch:** bad extension / oversize /
  missing part stage nothing (checks precede staging); a save error, a
  `ProcessWithID` hard error, and a flagged outcome each `os.Remove` the
  staged file (`api.go:334-354`).
