### [ING-004] Parse and validate VLM output against taxonomy and schema

**As a** wardrobe owner
**I want** the raw VLM response parsed as JSON and every field
validated against `03-taxonomy.md`'s enums and `04-data-schema.md`'s
required fields
**So that** only taxonomy-compliant tagging results ever reach the
catalog

**Acceptance criteria** (Gherkin):
```
Given a raw VLM response that is valid JSON matching the expected
  schema
When it is validated
Then a typed tagging result is produced with category, subcategory,
  dominant_color, secondary_colors, pattern, warmth_tier, and
  formality all populated

Given a response where subcategory is not one of the values listed
  under its category in 03-taxonomy.md (e.g. category=top,
  subcategory=jeans)
When it is validated
Then validation fails with a specific error naming the invalid
  category/subcategory pair

Given a response missing subcategory, or with subcategory: null
When it is validated
Then validation fails — subcategory is required and must not be null

Given a response missing pattern, or with pattern: null
When it is validated
Then validation fails — pattern is required and must not be null

Given a response with a dominant_color or secondary_colors value
  outside the 16-color palette (e.g. "gold")
When it is validated
Then validation fails with a specific error naming the out-of-palette
  value — do not silently coerce or drop it (known gap, see
  later-ideas.md; not to be worked around in this ticket)
```

**Spec reference:** `03-taxonomy.md` (all sections); `04-data-schema.md`;
`05-vlm-tagging-spec.md` "Output validation"

**Status:** Done

## Implementation notes

Implemented parsing + taxonomy/schema validation as a new file in the
existing `internal/tagging` package (alongside the VLM client).

**Files**
- `internal/tagging/validate.go` — `TaggingResult` (the 7 tagging
  fields), `ParseTaggingResult(raw string) (TaggingResult, error)`, and
  the taxonomy tables transcribed from `03-taxonomy.md` (categories,
  per-category subcategories, 16-color palette, patterns, warmth tiers,
  formalities). Also adds sentinel `ErrInvalidTaggingResult`.
- `internal/tagging/validate_test.go` — table-driven self-checks for
  AC1–AC5 plus edge cases, and `TestTaxonomyTablesMatchSpec`, which reads
  `03-taxonomy.md` and asserts the Go tables match the spec exactly in
  both directions (no invented value, none missing).

**Behavior**
- Valid JSON with all 7 fields → `TaggingResult` populated.
- `subcategory` not valid for its `category` (e.g. `top`/`jeans`) →
  error naming the pair: `invalid category/subcategory pair "top"/"jeans"`.
- `subcategory` / `pattern` missing, `null`, or `""` → "missing required
  field … (must not be null or omitted)".
- `dominant_color` or any `secondary_colors` entry outside the palette
  (e.g. `gold`) → error naming the value; never coerced or dropped.
- Malformed JSON → error wrapping `ErrInvalidTaggingResult`; all
  validation failures wrap the same sentinel, so callers can
  `errors.Is(err, tagging.ErrInvalidTaggingResult)` to distinguish bad
  output from `ErrVLMUnreachable` (ING-002) and choose retry vs. manual
  review.

**Assumptions / deviations (for Tester + Reviewer)**
1. **`TaggingResult` is only the 7 tagging fields.** Catalog-only fields
   (`id`, `photo_path`, `added_date`, `notes`) from `04-data-schema.md`
   are not produced here — the ticket's AC enumerates exactly the 7
   tagging fields, and those extra fields aren't VLM output.
2. **All 7 tagging fields treated as required**, not just
   `subcategory`/`pattern`. The spec says "every field must validate"
   and `04-data-schema.md` marks only `notes` optional. I read "missing
   required field (`subcategory` and `pattern` included …)" as those two
   being examples within a required set. `secondary_colors` must be
   present but may be `[]`; `null`/omitted is rejected. Easy to relax if
   Tester/Reviewer read the spec otherwise.
3. **New sentinel `ErrInvalidTaggingResult`.** Not literally demanded by
   the AC, but the spec's "reject and retry (or flag for manual review)"
   needs to be distinguishable from connectivity failure, mirroring the
   existing `ErrVLMUnreachable`. Small and additive.
4. **Strict, exact enum matching** — no trimming, case-folding, or
   coercion. Consistent with AC5's "do not silently coerce". The
   `gold`/`silver` palette gap from `later-ideas.md` is deliberately left
   unresolved.
5. **Unknown extra JSON fields are tolerated**; they aren't in the
   spec's rejection list. Malformed JSON is rejected as-is — no
   markdown-fence extraction or repair (the spec says reject malformed
   JSON).
6. **Not wired into `Client`/handler.** `Client.Tag` still returns raw
   text; this ticket only adds the parse/validate step. No route ticket
   exists yet.

**Validation performed**
- `gofmt -l internal/ tests/` and `go vet ./...` → clean.
- `go test -race -count=1 -timeout 180s ./...` → `internal/config`,
  `internal/tagging`, `tests` all ok.
- Spec check is automated: `TestTaxonomyTablesMatchSpec` parses
  `03-taxonomy.md` at runtime and compares every enum table (both
  directions), so drift from the spec fails a test rather than relying on
  eyeballing.
- Live E2E: scratch probe (`temp/`, removed after) called the real VLM at
  `http://192.168.0.100:2525` with the `temp/` sample image; raw response
  parsed and validated to
  `{bottom dress-pants navy [] solid medium formal}` — all fields
  populated, empty `secondary_colors` accepted. No API key used.

**Spec-implied edge cases checked (no failures)**
- **Spec is the source of truth, both directions.** Every `03-taxonomy.md`
  enum value is accepted (validator is not stricter than the spec), and
  off-spec values for each enum field are rejected naming field + value
  (`TestING004_InvalidEnumAndMissingFieldRejected`).
- **Malformed JSON** (`05-vlm-tagging-spec.md` "Output validation"):
  empty, prose, truncated object, top-level array, scalar, and a
  markdown-fenced block all fail with a `malformed json` error wrapping
  `ErrInvalidTaggingResult` (`TestING004_MalformedJSONRejected`).
- **Missing required fields:** all 7 tagging fields rejected when
  omitted/null; `secondary_colors` may be `[]` but not `null`/omitted.
- **Unknown extra JSON keys** are tolerated — they are not in the spec's
  rejection list (`TestING004_EmptySecondaryColorsAndUnknownFieldsAccepted`).
- **Failure-mode separation:** every validation error satisfies
  `errors.Is(err, ErrInvalidTaggingResult)` and is **not**
  `ErrVLMUnreachable`, preserving ING-002's connectivity-vs-bad-output
  distinction (asserted inside `assertInvalid`).

**Observations / follow-ups for Planner (non-blocking, no AC failure)**
1. **`secondary_colors` omitted/null is rejected as required**, only `[]`
   is accepted. `04-data-schema.md` says "0 or more" and
   `05-vlm-tagging-spec.md` lists required fields as "(`subcategory` and
   `pattern` included …)", which is ambiguous about the list field. This
   matches Coder assumption #2 and is safe/strict; if the intent is to
   treat an omitted list as empty, it's a one-line relaxation. Flag for
   Reviewer to confirm — not a test failure.
2. **Exact enum matching, no normalization.** A case/whitespace variant
   (`"Navy"`, `" navy "`) is rejected rather than trimmed/lowercased.
   Consistent with AC5's "do not silently coerce", but worth a conscious
   decision before any future prompt-tuning ticket adds normalization.
3. **Top-level JSON `null`** is rejected by the required-field path rather
   than the malformed-JSON path (Go treats `null` into a struct as a
   no-op). Still fails closed with `ErrInvalidTaggingResult`; only the
   error classification differs. No behavioral gap.
4. **Catalog-only fields** (`id`, `photo_path`, `added_date`, `notes`)
   remain outside this function by design — they are not VLM output. The
   store/write ticket owns them.

**Flake note:** none observed. `-race` clean; the AC suite is
deterministic and network-free, and the only network test is the
build-tagged live E2E.

**Spec intent (not just AC wording)**
- This parser is the only gate keeping a non-taxonomy record out of the
  catalog, and it covers all three cases `05` "Output validation" lists:
  invalid enum (including subcategory-not-in-category), malformed JSON,
  and missing required field. Nothing is coerced, defaulted, or dropped.
- The enum tables are transcribed from the spec and pinned by a test that
  parses `03-taxonomy.md` at runtime in both directions, so a taxonomy
  change cannot silently drift from validation.
- Strict exact matching is the correct reading of "do not silently
  coerce" and of the deliberately-unresolved gold/silver gap.
- Failures return a zero result and wrap a sentinel, enabling the spec's
  "reject and retry (or flag for manual review)" without forcing a retry
  policy in this ticket.
- Not wiring into the client is correct here: `Client.Tag` still returns
  raw text and this is the parse/validate step only.

**Hard constraints (`00-overview.md`) — no violations**
- **Fully local:** `validate.go` imports only stdlib (`encoding/json`,
  `errors`, `fmt`, `strings`); no network, no cloud, no new dependency.
  The only network path is the live test against the configured LAN VLM.
- **No fine-tuning:** pure parsing/validation; no training path.
- **One photo per garment:** one record per call; no multi-item handling.
- **No secret leakage:** no config or API key touched.

**Standards / non-silent failure**
- Every failure path returns an error; none is swallowed. Malformed JSON
  keeps the underlying `json` error via `%w`.
- Validation errors are distinct from ING-002's `ErrVLMUnreachable`
  (asserted in the black-box suite), so retry-vs-manual-review callers
  are not conflated.
- No panic path: `validSubcategories[r.Category]` is only reached after
  the category is validated, so the map lookup is always on a known key.
- Every enum is checked against the spec's closed vocabulary, and missing
  required fields are rejected; no invented taxonomy values.

**Judgment call reviewed — `secondary_colors` presence requirement**
`04-data-schema.md` types it as a list with "0 or more" and marks only
`notes` optional; `05` says "missing required field (`subcategory` and
`pattern` included …)". Requiring the field to be present (empty list
allowed, `null`/omitted rejected) is the safer reading and keeps an
incomplete record out of the catalog. Documented as Coder assumption #2
and Tester follow-up #1. Accepted.

**Non-blocking notes carried forward** (do not gate merge)
1. `secondary_colors` omitted vs `[]` — if a future intent is "treat
   omitted as empty", it is a one-line relaxation; not needed now.
2. Exact-match enums reject case/whitespace variants; revisit only if a
   prompt-tuning ticket decides to normalize.
3. Top-level JSON `null` fails via the required-field path (still
   `ErrInvalidTaggingResult`); classification only, no behavioral gap.
4. `TaggingResult` fields are validated strings rather than distinct Go
   enum types; sufficient for the AC and for the eventual store mapping.
