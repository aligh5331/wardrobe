### [ING-007] Send VLM_TEMPERATURE on every tagging request

**As a** wardrobe owner
**I want** the VLM client to include `"temperature": VLM_TEMPERATURE`
in every tagging request, read fresh each call
**So that** ING-005's two attempts for the same photo are independent
samples, not a deterministic repeat of the same answer

**Acceptance criteria** (Gherkin):
```
Given a tagging request is sent
When the request payload is built
Then it includes "temperature": VLM_TEMPERATURE

Given the client is called twice in a row for the same photo (ING-005's
  retry case)
When each request is built
Then the temperature value is read from config on each call, not
  cached or reused from the first request — so both calls genuinely
  hit the model at the configured temperature
```

**Spec reference:** `05-vlm-tagging-spec.md` "Prompt" section (request
shape); `06-decisions.md` "Malformed VLM output: retry once at nonzero
temperature, then flag"

**Status:** Done

**Note:** Follow-up to already-`Done` ING-002, not an amendment to it
— ING-002's original scope (single request/response, VLM-unreachable
error handling, concurrent-by-default) stays as built. This ticket
only adds the one payload field.

## Implementation notes

Implemented the one payload field plus the mechanism to read it fresh
per call. `NewClient`'s signature is unchanged, so ING-002/ING-003
callers and tests keep working.

**Files**
- `internal/tagging/client.go`
  - `chatRequest.Temperature` changed `int` → `float64` (JSON field
    `"temperature"`, no `omitempty` — sent on every request).
  - `Tag` builds the payload with `c.temperature()` instead of the
    hardcoded `0`.
  - Added `Client.temperature func() float64`, invoked afresh on every
    `Tag`.
  - Added exported option `WithTemperature(get func() float64)`.
  - `NewClient` defaults the source to `defaultTemperature = 0.4`,
    mirroring the `VLM_TEMPERATURE` config default
    (`07-architecture.md`).
- `internal/tagging/client_test.go`
  - Added `TestTag_SendsTemperature`: asserts the default is sent, and
    that changing the source between two consecutive calls changes the
    value the second request carries (the ING-005 retry-independence
    case).

**Design choice / assumption (for Tester + Reviewer)**
- The AC requires the value be read from config per call, "not cached
  or reused from the first request". The client does **not** hold a
  `*config.Config`, and the constructor is not changed. Instead the
  caller supplies a getter via `WithTemperature`, and `Tag` invokes it
  for each request. Wiring therefore reads config fresh every time:
  ```go
  client := tagging.NewClient(cfg.VLMURL, cfg.VLMAPIKey,
      tagging.WithTemperature(func() float64 { return cfg.VLMTemperature }))
  ```
  A plain `float64` option was rejected because it snapshots the value
  at construction and would fail the second AC. `tagging` does not import
  `internal/config`; the getter is the seam.
- Standalone default is `0.4` (the config default) so a client built
  without the option still samples non-deterministically for ING-005.
- The client is still **not** wired into `cmd/server` — no consumer
  exists yet (ING-002 deferred this) and this ticket asks only for the
  payload field. No production wiring was added.
- No range / NaN / Inf validation is added here; that is ING-008's
  scope. The client sends whatever the configured source returns.

### AC1: Given a tagging request is sent / When the request payload is built / Then it includes `"temperature": VLM_TEMPERATURE` — **PASS**

- **Black-box test**: `TestING007_AC1_TemperatureSentOnEveryRequest` (3
  subtests): the client default sends `0.4`; an explicit `0.0` is still
  serialized (proves the field is not dropped by `omitempty`); an explicit
  `0.7` is sent verbatim. The stub fails the test if `"temperature"` is
  absent or not a JSON number, so a dropped field cannot pass silently.
- **Unit test**: `TestTag_SendsTemperature` asserts the default equals
  `defaultTemperature`.
- **Spec cross-check**: `07-architecture.md` `VLM_TEMPERATURE` row requires
  the sampling temperature on each tagging request — the payload carries it,
  and `05-vlm-tagging-spec.md`'s request shape is otherwise unchanged ✓.

### AC2: Given the client is called twice in a row for the same photo / When each request is built / Then the temperature is read from config on each call, not cached — **PASS**

- **Black-box test**: `TestING007_AC2_TemperatureReadFreshPerCall` mutates
  the source between two consecutive `Tag` calls (`0.2` → `0.9`); request 2
  carries `0.9`, so the value is not snapshotted at construction.
- **Black-box test (config seam)**: `TestING007_AC2_ConfigBackedValueReadFresh`
  builds the client with the documented config seam
  (`func() float64 { return cfg.VLMTemperature }`) and mutates
  `cfg.VLMTemperature` between calls (`0.7` → `0.3`); the second payload
  tracks the current config value.
- **Spec cross-check**: `06-decisions.md` "Malformed VLM output: retry once
  at nonzero temperature, then flag" requires attempt 2 to be an independent
  sample — reading the value afresh per call (not cached) is what makes that
  true ✓.

### Spec-implied edge cases found (not explicitly covered by ticket ACs)

1. **Explicit `0.0` still sent**: the `omitempty` trap — `0.0` is a valid
   configured value (`07-architecture.md`, `06-decisions.md`) and the field
   must remain present; AC1's zero subtest confirms it is.
2. **Missing/non-numeric field fails fast**: the stub reports a missing
   `"temperature"` key or a non-number as a test failure, so a request that
   dropped the field cannot pass silently.
3. **NaN/Inf/out-of-range values are not this ticket's job**: the client
   sends whatever the source returns; startup range validation is ING-006,
   and the `floatEnv()` NaN/Inf gap is ING-008. No range check was added
   here (Coder note).
