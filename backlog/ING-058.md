### [ING-058] `internal/api`: `item_id` on error access logs for upload and create (non-`:id` routes)

**As a** wardrobe owner
**I want** a 5xx on `POST /api/items/photo` or `POST /api/items` to log the item id
the request was working on
**So that** a failed upload or create can be joined to its `logs/vlm-attempts.jsonl`
records, which are keyed by `item_id`, even though these routes have no `:id` path
parameter

**Acceptance criteria** (Gherkin):

```
Given POST /api/items/photo where the handler has generated an item id and a
  later step fails with a 5xx (for example the VLM is unreachable, 502)
When the error-level access log is emitted
Then the record carries the request_id and the generated item_id
And the upload handler makes that id available with c.Set("item_id", itemID)
  right after tagging.NewItemID() succeeds

Given POST /api/items whose body carries a valid item_id and the create fails
  with a 5xx (for example catalog.Create fails, 500)
When the error-level access log is emitted
Then the record carries the request_id and the body's item_id
And the create handler makes that id available with c.Set("item_id", body.ItemID)
  right after validPhotoName(body.ItemID) passes

Given a 5xx on a request with no known item id (for example GET /api/weather
  returning 503)
When the error-level access log is emitted
Then the record carries the request_id and no item_id

Given the change
When existing route, response-body, and status behavior is compared
Then registered routes are unchanged (still 12), no response body or status
  changes, and the only edits to handler bodies are the two c.Set("item_id", ...)
  calls in uploadPhoto and createItem
And it is local only (no network/telemetry) and adds no dependency
  (stdlib only; go.mod and go.sum unchanged)
```

**Spec reference:** `07-architecture.md` "## Logging", "Correlation: error logs carry
`request_id` and, where one exists, the `item_id`, so an API request can be joined to
its `logs/vlm-attempts.jsonl` records, which are already keyed by `item_id`", and
"HTTP access log" (level follows the status class: 5xx `error`); `06-decisions.md`
"Structured logging: stdlib `log/slog`, local stderr + file, env-configurable
level/format" (Correlation bullet).

**Status:** Done

**Context:** ING-053 adds the access-log middleware. It reads `c.Param("id")` on `:id`
routes and falls back to `c.GetString("item_id")` (empty until this ticket sets it).
This ticket only sets that value in the two handlers that have an item id but no `:id`
path parameter. No middleware change is needed here.

Blocking findings: none.

- **Handler diff is exactly the two lines the ticket names.** The diff is `+2 -0`. In
  `createItem`, `c.Set("item_id", body.ItemID)` sits at line 493, after the
  `validPhotoName(body.ItemID)` branch returns 400 and before `stagedPhotoPath`. In
  `uploadPhoto`, `c.Set("item_id", itemID)` sits at line 628, after the
  `tagging.NewItemID()` error return and before `MkdirAll`. Both run before any response
  write, so no route, body or status can change. I found no other hunk in `api.go`.
- **The middleware already reads the key.** `accesslog.go` lines 55-61 take `c.Param("id")`
  first, then `c.GetString("item_id")`, and add the attribute only on 5xx when the value is
  non-empty. That matches the spec ("error logs carry `request_id` and, where one exists,
  the `item_id`"). `accesslog.go` is not modified, as the ticket requires.
- **Routes and dependencies.** `api.go` still registers 12 routes. `git status` shows

- **Hard constraints clean.** No cloud service, no telemetry, no fine-tuning, no change to
  the one-photo-per-garment assumption. No enum, schema or taxonomy value touched. No
  `0*.md`, `agents/*.md` or `AGENTS.md` edit.
- **The tests fail without the lines, and the assertions are strong enough.**
    - The upload test needs `item_id` to be a string that matches the UUIDv4 pattern. An
      absent key gives `nil`, so the type assertion yields `""`, which fails the pattern. The

      pattern.

      showed the failure.
    - The no-item-id test checks that the `item_id` key is absent (`_, ok := rec["item_id"]`),
      not that the value is empty. This is the right check. It is a negative control, so it
      passes with or without the lines, which is correct for that criterion.
    - Each 5xx test also asserts the status, the level `ERROR`, the message `http request`,
      the route, and a `request_id` equal to the `X-Request-ID` response header.
- **Helper reuse.** The tests add no helper. They reuse `newING031HarnessFor`,
  `ing031Processor`, `ing031Upload`, `ing031UUIDv4`, `newING032Harness`, `ing032Stage`,
  `ing032ValidBody`, `ing032Post`, `sampleItem`, `ing053Engine`, `ing053Do` and
  `ing053One`.
- **Dependency on `ing053One` from another test file: acceptable.** The `tests` package is
  one Go package, and the ING-032, ING-035 and ING-053 files already share helpers this
  way. Copying the helper would duplicate code.
- **Ticket dependency met.** ING-053 is Done, so the `c.GetString("item_id")` fallback
  exists.
