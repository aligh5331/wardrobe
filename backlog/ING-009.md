### [ING-009] Audit VLM_* env vars for unstated bounds on parseable-but-invalid input

**As a** wardrobe owner
**I want** every `VLM_*` env var checked for the same class of gap
found in `VLM_TEMPERATURE` (ING-008) — a value that's syntactically
parseable but semantically invalid, silently accepted because no
bound was ever stated
**So that** the next bad config value gets caught at startup instead
of surfacing mid-implementation the way temperature did

**Background:** `VLM_TEMPERATURE` accepted `"NaN"`, `"Inf"`, negative
values, and anything up to `float64`'s range because `07-architecture.md`
never stated an acceptable range — `strconv.ParseFloat` happily parsed
all of it. That gap wasn't caught until Coder built against the spec
as literally written. This ticket looks for the same shape of gap
elsewhere before it does the same thing again.

**In scope:** `VLM_URL`, `VLM_API_KEY`, `VLM_SERIALIZE_REQUESTS`,
`VLM_REQUEST_DELAY_MS`. `VLM_TEMPERATURE` is excluded — already fixed
in ING-008.

**Out of scope:** `LLM_URL`/`LLM_API_KEY` — no Phase 1 consumer, so
there's no way to verify a bound is even correct yet. Revisit when
Phase 3 wires up a real consumer.

**Acceptance criteria** (Gherkin) — behavior below is settled by Ali (see
"Decisions applied"); the ticket verifies actual behavior matches:
```
Given VLM_URL is set to a malformed/non-URL string (e.g. "not a url", or
  a bare hostname with no scheme)
When the server starts
Then startup proceeds with no URL-format validation, and the malformed
  value surfaces on use as an "VLM unreachable" error per ING-002
  (implemented and covered by ING-011)

Given VLM_SERIALIZE_REQUESTS is set to an unrecognized boolean string
  (e.g. "yes", "ture")
When the server starts
Then it exits with a startup error naming VLM_SERIALIZE_REQUESTS as
  invalid (strict strconv.ParseBool) — it does not silently evaluate to
  false. "1"/"t"/"T"/"true" are accepted as true; "0"/"f"/"F"/"false" as
  false; unset or empty is false

Given VLM_REQUEST_DELAY_MS is set to a negative value (e.g. "-100")
When the server starts
Then it is clamped to 0 and a startup warning is logged naming
  VLM_REQUEST_DELAY_MS as negative (implemented and covered by ING-010)

Given VLM_REQUEST_DELAY_MS is set to a non-numeric value
When the server starts
Then it exits with a startup error naming VLM_REQUEST_DELAY_MS as
  invalid

Given VLM_API_KEY is set to any non-empty string
When the server starts
Then it is accepted as-is with no format validation (opaque key —
  validity is determined by the VLM server's response); when empty or
  unset, no Authorization header is sent
```

## Decisions applied

Ali settled the four open bounds on 2026-09-14; the spec row needs to
state each (Planner cannot edit `07-architecture.md` / `06-decisions.md`):

1. **`VLM_URL` malformed** — accepted at startup, surfaces on use as
   `ErrVLMUnreachable` per ING-002. Code/behavior follow-up: **ING-011**.
2. **`VLM_SERIALIZE_REQUESTS` unrecognized** — startup error naming the
   variable (strict `strconv.ParseBool`). No code change; verify with a
   test in this ticket.
3. **`VLM_REQUEST_DELAY_MS` negative** — clamped to 0 with a startup
   warning. Code follow-up: **ING-010**. (This replaces the earlier AC
   wording that called for a hard startup error.)
4. **`VLM_API_KEY`** — opaque, no format validation. No code change;
   confirm with a test in this ticket.

**Prerequisite:** the `07-architecture.md` / `06-decisions.md` update
stating these behaviors must land before this ticket's verification is
meaningful. ING-010 and ING-011 implement decisions 1 and 3; their tests
cover those clauses, so this ticket's own test additions need only cover
decisions 2 and 4.

**Spec text required (Ali — protected files, Planner cannot edit):**
`07-architecture.md` env var contract table:
- `VLM_URL`: add "no URL-format validation at startup; a malformed value
  is accepted and surfaces when a request is attempted as a 'VLM
  unreachable' error (ING-002)"
- `VLM_API_KEY`: add "opaque string, no client-side format check — empty
  means no Authorization header; validity is determined by the VLM
  server's response"
- `VLM_SERIALIZE_REQUESTS`: add the accepted values and failure behavior
  ("parsed with `strconv.ParseBool`; unset/empty is `false`; any other
  value is a startup error naming the variable")
- `VLM_REQUEST_DELAY_MS`: add "integer; negative values are clamped to 0
  with a startup warning; non-numeric is a startup error"

`06-decisions.md`: one new entry covering the four bounds above
(malformed URL passes through, unknown boolean errors, negative delay
clamps to 0, API key opaque), with rationale.

**Definition of done for this ticket specifically:** every var in
scope has either (a) a passing test confirming stated behavior matches
actual behavior, or (b) a follow-up ticket filed (ING-010, 011...)
for a gap real enough to need its own Coder pass — same pattern as
ING-006 → ING-008. This ticket should not try to fix everything itself
if a finding turns out to be non-trivial; filing a follow-up is the
correct outcome, not scope creep to avoid.
