### [ING-009] Audit VLM_* env vars for unstated bounds on parseable-but-invalid input

**As a** wardrobe owner
**I want** every `VLM_*` env var checked for the same class of gap
found in `VLM_TEMPERATURE` (ING-008) — a value that's syntactically
parseable but semantically invalid, silently accepted because no
bound was ever stated
**So that** the next bad config value gets caught at startup instead
of surfacing mid-implementation the way temperature did

**Background:** `VLM_TEMPERATURE` accepted `"NaN"`, `"Inf"`, negative
values, and anything up to `float64`'s range because `07-architecture.md`
never stated an acceptable range — `strconv.ParseFloat` happily parsed
all of it. That gap wasn't caught until Coder built against the spec
as literally written. This ticket looks for the same shape of gap
elsewhere before it does the same thing again.

**In scope:** `VLM_URL`, `VLM_API_KEY`, `VLM_SERIALIZE_REQUESTS`,
`VLM_REQUEST_DELAY_MS`. `VLM_TEMPERATURE` is excluded — already fixed
in ING-008.

**Out of scope:** `LLM_URL`/`LLM_API_KEY` — no Phase 1 consumer, so
there's no way to verify a bound is even correct yet. Revisit when
Phase 3 wires up a real consumer.

**Acceptance criteria** (Gherkin):
```
Given VLM_URL is set to a non-URL string (e.g. "not a url", or a bare
  hostname with no scheme)
When the server starts
Then its behavior is explicitly one of: (a) startup error naming
  VLM_URL as malformed, or (b) accepted as-is with the malformed value
  surfacing later as a "VLM unreachable" error per ING-002 — whichever
  is chosen, 07-architecture.md must state it, not leave it implicit

Given VLM_SERIALIZE_REQUESTS is set to a value that isn't a recognized
  boolean string (e.g. "yes", "1", "ture" — a plausible typo of "true")
When the server starts
Then its behavior is explicit: either it errors naming the invalid
  value, or it's parsed via a documented permissive boolean parser
  (state which values are accepted) — it must not silently evaluate
  to false on an unrecognized string without saying so anywhere

Given VLM_REQUEST_DELAY_MS is set to a negative value (e.g. "-100")
When the server starts
Then it exits with a startup error naming VLM_REQUEST_DELAY_MS as
  invalid — a negative delay is not a valid interpretation of "wait
  this long after each response"

Given VLM_REQUEST_DELAY_MS is set to a non-numeric value
When the server starts
Then it exits with a startup error naming VLM_REQUEST_DELAY_MS as
  invalid

Given VLM_API_KEY is set to any non-empty string
When the server starts
Then it is accepted as-is with no format validation — confirm this is
  actually the intent (API keys are opaque, no reasonable client-side
  format check applies) and document that explicitly rather than
  leaving it merely unvalidated with no stated reason
```

**Spec update checklist** — for each var above, once its actual
behavior is settled, `07-architecture.md`'s env var contract table
needs one of:
- An explicit accepted range/format added to the "Behavior" column
  (e.g. `VLM_REQUEST_DELAY_MS`: "integer, >= 0")
- An explicit statement that no format constraint applies, with the
  reason (e.g. `VLM_API_KEY`: "opaque string, no client-side format
  check — validity is determined by the VLM server's response")
- A new `06-decisions.md` entry if the bound reflects a real design
  choice rather than an obvious constraint (same treatment
  `VLM_TEMPERATURE`'s range got) — not every fix needs one; a negative
  delay being invalid doesn't need a decision entry, it's not a
  judgment call, it's just wrong on its face

**Definition of done for this ticket specifically:** every var in
scope has either (a) a passing test confirming stated behavior matches
actual behavior, or (b) a follow-up ticket filed (ING-010, 011...)
for a gap real enough to need its own Coder pass — same pattern as
ING-006 → ING-008. This ticket should not try to fix everything itself
if a finding turns out to be non-trivial; filing a follow-up is the
correct outcome, not scope creep to avoid.

**Spec reference:** `07-architecture.md` "Env var contract"; `06-decisions.md`
"VLM_TEMPERATURE acceptable range" entry (the template this audit
generalizes)
