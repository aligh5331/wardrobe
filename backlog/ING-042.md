### [ING-042] Store: weather location setting (single row, Tehran default, validation)

**As a** wardrobe owner
**I want** my chosen weather location persisted in the local SQLite database
**So that** it survives restarts, and weather always has a location even before I pick one

**Acceptance criteria** (Gherkin):
```
Given a fresh database with no weather location row
When the store reads the weather location
Then it returns the default name "Tehran", country "Iran", latitude 35.69439,
  longitude 51.42151, and no error
And no row is written by the read

Given a valid location {name, country, latitude, longitude}
When the store saves it and then reads the weather location
Then the read returns exactly the saved values

Given a location has already been saved
When a second, different location is saved
Then a read returns the second location and the table holds exactly one row

Given a location with country empty
When it is saved
Then it is accepted (country is optional) and read back with an empty country

Given a location with an empty or whitespace-only name, latitude outside -90..90, or longitude outside -180..180
When the store saves it
Then it returns a validation error whose message names the offending field
  (name, latitude, or longitude), and the previously stored location (or the
  default) is unchanged

Given boundary values latitude -90 / 90 and longitude -180 / 180
When they are saved
Then they are accepted

Given store.Open on an existing Phase 1 database
When it auto-migrates
Then the weather location table is added and existing wardrobe items are untouched
```

**Spec reference:** `04-data-schema.md` "Settings — weather location (Phase 2)"
(single row; fields `name` required, `country` optional, `latitude` -90..90,
`longitude` -180..180; Tehran default when no row); `06-decisions.md`
"Weather location: chosen in the web UI, persisted in SQLite, default Tehran".

**Status:** Review

**Depends on:** nothing.

**Routing:** Ready → Coder. Touches `internal/store/store.go` (new model in
`AutoMigrate`, get/save methods) plus a test. Validation lives here so the API
(ING-043) maps the named-field error to 400 without a second copy.

**Out of scope:** HTTP routes (ING-043), multiple saved locations, env vars
for location, any change to the `Item` model.

## Implementation notes

**Changes**
- `internal/store/store.go` (additive; `Item`, `Insert`, `Get`, `Update`,
  `List`, `Close` untouched):
  - `type WeatherLocation struct { ID uint; Name, Country string; Latitude,
    Longitude float64 }` → table `weather_locations`, columns `id`, `name`,
    `country`, `latitude`, `longitude`. `ID` is always `1` (single row).
  - `var DefaultWeatherLocation` = Tehran, Iran, `35.69439`, `51.42151`
    (`04-data-schema.md` / `06-decisions.md`).
  - `var ErrInvalidLocation` — sentinel wrapped by every validation error
    (`fmt.Errorf("%w: <field> ...")`), so ING-043 maps
    `errors.Is(err, store.ErrInvalidLocation)` → 400 and forwards
    `err.Error()`, which names the field (`name`, `latitude`, `longitude`).
  - `Open` now `AutoMigrate(&Item{}, &WeatherLocation{})`.
  - `func (s *Store) WeatherLocation() (WeatherLocation, error)` — reads row
    id 1 via `Limit(1).Find`; zero rows → `DefaultWeatherLocation, nil`. No
    write. `Find` (not `First`) so the normal no-row case doesn't make GORM
    log "record not found" to stderr on every weather request; real DB
    errors are returned (ING-043 → 500).
  - `func (s *Store) SaveWeatherLocation(loc WeatherLocation) error` —
    validates (name trimmed non-empty; latitude in [-90, 90]; longitude in
    [-180, 180]; checks written in negated form so NaN is rejected too),
    then forces `ID = 1` and upserts (`clause.OnConflict{UpdateAll: true}`).
    Validation returns before any DB call, so nothing is written on error.
- `tests/ing_042_weather_location_test.go` (new) — 5 functions covering
  all 7 ACs.
- `tests/ing_017_store_test.go` — `TestING017_AC1_OpenCreatesDataDirAndColumns`
  asserted "exactly 1 user table", which the new table necessarily breaks.
  Changed it to look up the `items` table by name and check the same
  schema columns. Same assertion otherwise; same approach as ING-043's note
  for the route-count test.

**Absent vs 0 (for ING-043)**
- Chose: **the API checks presence itself**; the store takes plain
  `float64`. Simplest: the store contract is "value in range", and presence
  is an HTTP-body concern. ING-043 can decode into a request struct with
  `*float64` latitude/longitude (nil → 400 "latitude is required"), then
  build a `store.WeatherLocation` and call `SaveWeatherLocation` for
  name/range validation. That way the store needs no pointer fields and its
  callers need no nil-handling. Explicit `0` is valid here
  (Null Island test).

**Assumptions**
- Country is stored as given (not trimmed); name is only *validated*
  trimmed, stored as given. The spec does not say to normalize either.
- Validation order is name, latitude, longitude; the first failure is
  returned (one field named per error). The AC asks for "the offending
  field", not all of them.
- NaN latitude/longitude is rejected as out of range. JSON can't carry NaN,
  but Go callers can.

## Review

**Decision: APPROVED**

Reviewed the uncommitted diff (`internal/store/store.go`,
`tests/ing_042_weather_location_test.go`, `tests/ing_017_store_test.go`)
against the ticket ACs, `04-data-schema.md` "Settings — weather location
(Phase 2)", `07-architecture.md` "Weather (Phase 2)", `06-decisions.md`
(Phase 2 scope, Open-Meteo, weather location entries), and `AGENTS.md`.
ING-041 files were ignored, as instructed.

- **Spec match.** One row (`ID` is forced to 1, upsert with
  `OnConflict{UpdateAll}`). Fields are `name`/`country`/`latitude`/`longitude`,
  as in the `04` table. Name is required and whitespace-only is rejected
  (`07` "PUT location"). Country is optional. Ranges are inclusive
  `-90..90` / `-180..180`. The Tehran default matches the `04`/`06` literals
  exactly, and the read never writes, so `06`'s "no unconfigured state" holds
  without seeding a row.
- **Error handling.** Validation errors wrap `ErrInvalidLocation` and name
  the field, so ING-043 can map them to 400 with one `errors.Is`. Real DB
  errors are returned, not swallowed, so ING-043 can map them to 500 per `07`
  "Local DB read/write failure". `Find` rather than `First` for the normal
  no-row case is correct. A missing row is not an error. The negated range
  check also rejects NaN and ±Inf.
- **Hard constraints clean.** No network, no model, no fine-tuning, and no
  photo or garment impact. No new dependency, because `gorm.io/gorm/clause`
  is in the existing gorm module and `go.mod`/`go.sum` are unmodified per
  `git status`. No protected file touched. No HTTP route, no `LLM_URL`, and
  no `Item` change. Phase 1 ingestion is intact: `Open` only adds a model
  to `AutoMigrate`, and AC7 proves items survive the migration.

**Rulings on open notes**

- **(a) Name validated trimmed, stored untrimmed: acceptable, non-blocking.**
  `04`/`07` only require non-empty and not whitespace-only. Neither
  normalizes. Storing as given round-trips exactly, which is what AC2
  asks for. If Ali wants display names trimmed, the fix is one line
  (`loc.Name = strings.TrimSpace(loc.Name)` before the upsert) and it
  belongs here, not in ING-043, so there is one copy. That needs a ticket
  or AC change first, not a silent change.
- **(b) Plain `float64`, with absent-vs-0 left to ING-043: acceptable
  design.** "Absent is not `0`" (`07`) is a property of the JSON body. The
  store cannot see it, and pointer fields would push nil-handling onto every
  caller for no gain. ING-043 already carries the matching ACs (lines 50 and
  56: absent → 400, explicit 0 → 200), and the store doc comment states the
  contract. **ING-043 Reviewer must confirm** that the request struct uses
  `*float64` (or an equivalent presence check) for latitude and longitude.
- **(c) `ing_017` test edit: in scope, intent preserved.** This is the
  minimum change forced by the second table that the spec requires. The
  "exactly 1 table" count is dropped, and the `items` table is looked up by
  name. Every `schemaColumns` entry is still checked against real
  `PRAGMA table_info`. The dir and file checks are unchanged. It is stricter
  than before because it pins the table name. No other ING-017 assertion
  changed.

**Over-engineering: none of substance.** The sentinel error is justified
because ING-043 consumes it. The exported default var is used by the tests.
Nothing is speculative: no interface, no config, no extra tables. One nit,
non-blocking: `map[bool]int64{false: 0, true: 1}[withSaved]` in the AC5 test
is clever where an `if` would read plainer. It is test code, so leave it.

**Non-blocking notes for ING-043 (no action on this ticket)**

1. `WeatherLocation` has no `json` tags and exposes `ID`. If ING-043
   marshals it directly, the keys come out `ID`/`Name`/… and not the
   `{name, country, latitude, longitude}` from `07`. ING-043 should map it
   to its own response shape.
2. `DefaultWeatherLocation` is a mutable exported var. It is safe today
   because it is returned by value and only tests reference it. Revisit
   only if a caller ever assigns to it.
