### [ING-005] Retry once on malformed/invalid VLM output, then flag

**As a** wardrobe owner
**I want** a malformed or taxonomy-invalid VLM response retried exactly
once at a nonzero temperature, and flagged for manual review only if
the retry also fails
**So that** a one-off model glitch doesn't cost a manual review, while
a genuinely bad tag still gets caught with full diagnostic detail

**Policy** (settled — see `06-decisions.md`):
- Attempt 1: send the tagging request (ING-002), validate the response
  (ING-004).
- If attempt 1 fails validation (malformed JSON, invalid enum, missing
  required field): log attempt 1's full detail, then send attempt 2 —
  same photo, same prompt, `VLM_TEMPERATURE`-sampled, so it's an
  independent draw, not a deterministic repeat.
- If attempt 2 also fails validation: log attempt 2's full detail, and
  flag the item for manual review with **both** attempts' logs
  attached.
- If either attempt passes validation, use that result and stop — no
  need to burn a second call on a success.

**Acceptance criteria** (Gherkin):
```
Given a VLM response on attempt 1 that fails validation (malformed
  JSON, invalid enum, or a missing required field)
When it is processed
Then attempt 1's full detail is logged (see log format below), and a
  second request is sent for the same photo before anything is flagged

Given attempt 2's response passes validation
When it is processed
Then the validated result is used normally — the item is NOT flagged,
  even though attempt 1 failed

Given attempt 2's response also fails validation
When it is processed
Then the item is flagged for manual review, with both attempt 1's and
  attempt 2's logged detail attached — not just the final failure

Given a flagged item
When the ingestion pipeline continues
Then processing of other photos in the same batch is not blocked by
  one bad result

Given the VLM is unreachable (ING-002's distinct error, not a
  validation failure)
When it occurs on either attempt
Then it is NOT treated as a malformed-output case and does NOT count
  toward the two-attempt policy — connectivity failure is a different
  problem and should surface immediately, not be silently retried into
  a flag
```

**Log format** (needed for both diagnosis now and calibration later —
see `later-ideas.md`'s VLM calibration idea, which this incidentally
feeds): append one JSON object per attempt to `logs/vlm-attempts.jsonl`
(under the existing gitignored `logs/` directory, `07-architecture.md`).
Fields:
```json
{
  "item_id": "<shared id linking attempt 1 and attempt 2 for the same photo>",
  "timestamp": "2026-09-13T14:32:01Z",
  "photo_path": "data/photos/xxxxx.jpg",
  "attempt": 1,
  "temperature": 0.4,
  "raw_response": "<full raw text returned by the VLM, unmodified>",
  "parsed_json": null,
  "failure_type": "malformed_json",
  "failure_detail": "response was not valid JSON: unexpected token at position 142"
}
```
For a validation failure (JSON parsed fine, but content is invalid),
`parsed_json` holds the parsed object and `failure_type` is
`"invalid_enum"` or `"missing_required_field"` instead, with
`failure_detail` naming the specific field/value.

`item_id` must be shared across both attempts for the same photo so a
later analysis can join them — that pairing (did attempt 2 agree with
attempt 1, or land somewhere completely different?) is the actual
signal `later-ideas.md`'s calibration idea is after, now collected as
a side effect of normal use instead of needing its own harness.
