### [ING-047] Recommender: weather → warmth rules and candidate filter

**As a** wardrobe owner
**I want** my catalog narrowed to garments that suit today's weather and my chosen formality
**So that** the LLM can only pick from weather-appropriate items

**Acceptance criteria** (Gherkin):
```
Given feels-like 5 °C and min/max 3..8 °C
When rules are computed
Then allowed warmth tiers are {medium, heavy} and outerwear is required

Given feels-like 15 °C and min/max 12..18 °C
When rules are computed
Then allowed tiers are {light, medium} and outerwear is optional

Given feels-like 25 °C and min/max 21..30 °C
When rules are computed
Then allowed tiers are {light} and outerwear is excluded

Given feels-like exactly 10 °C, and separately exactly 20 °C
When rules are computed
Then both fall in the 10–20 band (inclusive)

Given feels-like 15 °C and min/max 8..24 °C (range crosses both thresholds)
When rules are computed
Then allowed tiers are {light, medium, heavy}
And outerwear stays optional (it follows the feels-like band only)

Given feels-like is null and min/max are 2 and 6
When rules are computed
Then the midpoint 4 °C is used (tiers {medium, heavy}, outerwear required)

Given feels-like is null and only one of min/max is present
When rules are computed
Then that one value is used

Given feels-like, min and max are all null
When rules are computed
Then no warmth filter applies, outerwear is optional, and the result marks the temperature as unknown

Given precipitation_probability_max is 50 or more (and separately 49, and null)
When rules are computed
Then a rain hint is set for >= 50 only; it never removes candidates

Given a catalog and rules
When candidates are filtered
Then top/bottom/outerwear/footwear keep only allowed warmth tiers
And headwear and accessory are kept regardless of warmth
And outerwear is dropped entirely when excluded

Given a formality "formal"
When candidates are filtered
Then only items with formality "formal" remain, in every category
And with no formality chosen, formality does not filter

Given candidates with no footwear (and separately none of top, bottom, or required outerwear)
When required slots are checked
Then the check reports every missing slot by name
And with all required slots present, it reports none
```

**Spec reference:** `06-decisions.md` "Weather → warmth thresholds: starting
values, to be tuned from real use" (table, straddle, outerwear follows
feels-like, null fallbacks, rain hint, exempt categories, formality scope);
`07-architecture.md` "Recommender (Phase 3)" flow steps 2–3.

**Status:** Done

**Depends on:** nothing (uses existing `weather.Forecast` and `store.Item`).

**Routing:** Ready → Coder. New package `internal/recommend/` — pure
functions, thresholds as named constants in one place, one table-driven test.
No network, no DB.

**Out of scope:** the LLM call (ING-048), HTTP route (ING-049), any env var
for thresholds.

## Implementation notes

New package `internal/recommend/`, stdlib plus `store` and `weather` types
only. Two files.

`rules.go`: thresholds as constants (`coldBelowC` 10, `hotAboveC` 20,
`rainHintPct` 50). `Outerwear` type with `OuterwearOptional`,
`OuterwearRequired`, `OuterwearExcluded`. `Rules{Tiers, Outerwear,
TempUnknown, RainHint}`. `Tiers` is nil exactly when `TempUnknown` is true,
and `Filter` then skips the warmth filter. `RulesFor(weather.Forecast)`,
`Filter(items, rules, formality)` and `MissingSlots(cands, rules)`.
`Filter` keeps input order, returns a non-nil empty slice when nothing
matches, treats an empty formality as no filter, and drops outerwear when
excluded. Headwear and accessory skip the warmth check only. The formality
check covers every category.

`rules_test.go`: table-driven tests `TestRulesFor`, `TestRainHint`,
`TestFilter` and `TestMissingSlots`. Every AC row maps to at least one case,
including feels-like 10 and 20, the 8..24 straddle, midpoint fallback, single
min or max fallback, all-null, rain 50/49/null, exempt categories, excluded
outerwear, formality "formal" and "no formality", and missing-slot reports.

**Assumptions**

- Range edges use the band table directly. A value below 10 is cold, 10 to 20
  inclusive is mild, above 20 is hot. The range adds every band that its min,
  max or feels-like value falls in. So 5..10 touches cold and mild, 10..18
  touches mild only, 12..20 touches mild only, and 18..30 adds hot. The
  ticket does not name these cases, so this is my reading of the band table.
- The midpoint fallback also feeds the band lookup, so a null feels-like with
  min 0 and max 20 gives midpoint 10 (mild base) and the range adds the cold
  band, giving all three tiers.
- `MissingSlots` returns slots in the fixed order top, bottom, footwear,
  outerwear, matching the order in `07-architecture.md` step 3. It returns
  nil when nothing is missing. Outerwear counts only when the rule is
  required.
- `MissingSlots` looks at the candidates it receives. It does not re-apply
  rules, so the caller passes the output of `Filter`.
- No taxonomy value invented. Tier and category strings match `03-taxonomy.md`.
  `Filter` does not validate enum values on items.

**Edge cases noted (not failures, no AC or spec change requested):**

- Range edges are not named in the ticket or in `06-decisions.md`. The Coder
  reads them straight from the band table, so a range ending at exactly 10
  touches the mild band and a range ending at exactly 20 does not touch the
  hot band. This is consistent with "10-20 inclusive", so I derived the same
  expectation independently. Ali may want to confirm it during tuning.
- With a null feels-like, the midpoint is both the base band and the band
  lookup, and min/max still widen the range. Min 0 and max 20 gives midpoint 10
  and all three tiers. The spec says only "fall back to the midpoint", so this
  follows the layering bullet and is documented in Implementation notes.
- Hot band tiers ({light}) are a subset of mild ({light, medium}), so a range
  reaching into the hot band from a mild feels-like adds no tier. Only the
  cold band ever widens the set. This is a consequence of the table, not a
  defect.
- `Filter` does not validate enum values. An item with an unknown category
  (not in the taxonomy) is treated as exempt from warmth filtering. The Coder
  documented this, and the ticket says the taxonomy is enforced at tagging.
- `MissingSlots` does not re-apply rules, so callers must pass `Filter`
  output. ING-049 should do that.

## Review

**Decision: APPROVED**

Reviewed the uncommitted `internal/recommend/rules.go`,
`internal/recommend/rules_test.go`, `tests/ing_047_rules_test.go` and the Test
results section of this ticket. The review checked the ticket ACs,
`06-decisions.md` "Weather → warmth thresholds" and "Recommender output
validation", `07-architecture.md` "Recommender (Phase 3)" flow steps 2 and 3,
`00-overview.md` hard constraints, and `AGENTS.md`. Tester's evidence is
accepted as recorded. I did not run any tests.

- **Spec match.** Every bullet in the thresholds decision holds in
  `rules.go`. `band()` uses `< 10` cold and `> 20` hot, so 10 and 20 are mild
  (inclusive). Band tiers match the table. The range adds the tiers of every
  band that min, max or the base value falls in, which gives the straddle
  widening. The outerwear rule reads `band(*base)` only, so a wide range never
  moves it. Null feels-like falls back to the midpoint, then to the single
  present value, then to `TempUnknown` with nil `Tiers` and optional outerwear.
  `RainHint` is `>= 50` on a nil-safe pointer, and `Filter` never reads it.
  `warmthFiltered` covers top, bottom, outerwear and footwear, so headwear and
  accessory are exempt. The formality check runs first and applies to every
  category, and an empty formality skips it. Thresholds are named constants in
  one place, with no env var, as `06-decisions.md` requires.
- **Range-edge reading: fine as a documented assumption, no Ali or Planner
  decision needed.** A range ending at exactly 10 touches the mild band, and a
  range ending at exactly 20 does not touch the hot band. Both follow from
  applying the band table to min and max with the same edges as the feels-like
  value. The reading is internally consistent, it is what "10-20 inclusive"
  says, and the coder, the tester and this review derived it independently. The
  cost of a different reading is small, since only the cold band ever adds
  tiers (hot is a subset of mild). The affected case is a range like 5..10 on a
  mild feels-like day, which the code widens to all three tiers. Ali can adjust
  it during tuning. The Implementation notes and the `RulesFor` doc comment
  already record it, and `TestRulesFor` pins the edge cases.
- **Hard constraints clean.** No network call, no DB access, no cloud
  service, no fine-tuning, no photo handling. The package imports only `store`
  and `weather`. `go.mod`, `go.sum` and `.env.example` are unchanged, so there
  is no new dependency or env var. No secret appears in the diff. The only
  modified tracked file is this ticket, and `git status` lists no protected
  file (`0*.md`, `agents/`, `AGENTS.md`). No taxonomy value is invented. Tier
  and category strings match `03-taxonomy.md`.
- **Over-engineering check: none.** Three exported functions, `Rules`, the
  `Outerwear` enum, and two small private helpers (`band`, `warmthFiltered`).
  No interface, no config, no option struct. The `bandTiers` table replaces
  three copied switch arms, which is the shorter form.
- **API for ING-048 and ING-049.** `RulesFor(weather.Forecast) Rules` feeds
  `Filter([]store.Item, Rules, string) []store.Item`, whose output feeds
  `MissingSlots([]store.Item, Rules) []string`. ING-048 can read
  `TempUnknown`, `RainHint` and `Outerwear` for the prompt and for the
  validation rule "outerwear present when required, absent when excluded".
  `MissingSlots` returns top, bottom, footwear, outerwear in that order, which
  is the order in step 3, and it returns nil when nothing is missing. ING-049
  must pass the `Filter` output, as the ticket notes say.
- **Tests.** `rules_test.go` maps each AC to a case. `tests/ing_047_rules_test.go`
  overlaps little. The 9.99 and 20.01 rows repeat the 9.9 and 20.1 boundary
  idea in a few lines. The rest (partial min or max with a present feels-like,
  wide range with outerwear unmoved, the nil-Tiers invariant, rain hint with
  unknown temperature, `Filter` into `MissingSlots`) is not covered in the
  Coder file. No chunk is worth deleting.

Non-blocking notes for Ali or the Coder:
1. `Filter` treats an item with an unknown category as warmth-exempt and does
   not validate enums. This is documented, and taxonomy is enforced at tagging.
2. `Rules.Tiers` is a `map[string]bool`, so ING-048 must sort it if it prints
   the tiers into a prompt. The prompt spec lists no tiers, so this is a
   reminder only.

Status remains `Review`, ready for Ali's final review and merge. Reviewer does
not set Done and did not commit.
