### [ING-023] Match photo extensions case-insensitively when scanning a directory

**As a** wardrobe owner
**I want** `cmd/ingest`'s directory scan to recognize image files regardless of
extension case
**So that** camera-produced `.JPG`/`.PNG` (and mixed-case) files aren't silently
skipped when I ingest a folder

**Acceptance criteria** (Gherkin):
```
Given a directory containing an image named with an uppercase extension
  (e.g. PHOTO.JPG)
When that directory is passed as the ingest argument
Then the file is included and processed exactly as a lowercase .jpg would be —
  not silently skipped

Given a directory containing images with mixed-case extensions
  (.jpg, .JPG, .jpeg, .JPEG, .png, .PNG, .webp, .WEBP)
When it is scanned
Then every one of those image files is included, and non-image files
  (e.g. .txt, .pdf) are not

Given a single file path passed directly (any extension case)
When cmd/ingest processes it
Then it is processed exactly as before — direct-path behavior is unchanged
```

**Spec reference:** `07-architecture.md` "Backend" (image storage under
`data/photos/`); `05-vlm-tagging-spec.md` "Input" (one garment photo);
`backlog/ING-012.md` (introduced `expandPaths`)

**Status:** Ready

**Context / direction:** Ali's decision — the directory scan should be
case-insensitive. Minimal change in `cmd/ingest/main.go`'s `expandPaths`
(currently `:166-168`, comparing lowercase-only literals), e.g. fold the
extension with `strings.EqualFold` (or `strings.ToLower`) before the membership
check. Direct-path input is already unaffected because it never goes through
the extension filter. No new taxonomy/schema/enum value, no new env var, no
spec change.

**Out of scope:** changing which extensions are supported (stays
jpg/jpeg/png/webp); recursive directory walking; handling non-image inputs.
