### [ING-036] API: `GET /api/taxonomy` — closed enum vocabulary for the create/edit forms

**As a** wardrobe owner
**I want** the browser to fetch the approved taxonomy from the backend
**So that** the create/edit forms offer exactly the valid enum values without
the frontend hand-duplicating `03-taxonomy.md`

**Acceptance criteria** (Gherkin):
```
Given the server is running
When a client GETs /api/taxonomy
Then it receives 200 with a JSON body carrying the closed vocabulary: every
  category with its valid subcategories, the color palette, the pattern values,
  the warmth tiers, and the formality values

Given the same taxonomy the tagging pipeline validates against
When the response is compared to internal/tagging's tables
Then every value matches exactly — same categories, same per-category
  subcategories, same color palette, same patterns / warmth tiers / formality —
  so the client and the server cannot drift (06-decisions.md "Taxonomy exported
  to the browser")

Given a future taxonomy change in the approved tables
When the route is served
Then the change is reflected without editing frontend code — the route derives
  from internal/tagging's tables, not a second hard-coded copy

Given the route surface
When routes are inspected
Then the read route GET /api/taxonomy is registered, and the existing routes are
  unchanged

Given the route is consumed by the create/edit forms
When it is reviewed against the project's constraints
Then it is a read-only local route (no auth, no cloud), adds no runtime
  dependency and no new model, and invents no enum value beyond 03-taxonomy.md
```

**Spec reference:** `07-architecture.md` "Backend" → "Taxonomy read route
(create/edit forms)" (`GET /api/taxonomy`; categories with valid
subcategories, color palette, patterns, warmth tiers, formality; derived from
the same tables `internal/tagging` validates against); `06-decisions.md`
"Taxonomy exported to the browser via `GET /api/taxonomy`, not a bundled copy"
(rejects a client-side copy; the server is the single source the forms read);
`03-taxonomy.md` (the closed vocabulary); `05-vlm-tagging-spec.md` (the same
enums that validate tagging output).

**Status:** Review

**Context:** ING-033/ING-034 were blocked because no approved source of enum
values existed for the browser. This decision supplies one: a read route
backed by the existing `internal/tagging` taxonomy tables (the same ones
`ParseTaggingResult` validates against), so no new taxonomy is introduced and no
third copy is created. The route is read-only and needs no store, model, or
persistence.

**Routing:** Ready → Coder. Touches `internal/api/` and tests. ING-033 and
ING-034 consume this route and list ING-036 as a dependency; ING-036 itself
depends on nothing new (it reuses the existing `internal/tagging` tables).

**Depends on:** nothing new — existing `internal/tagging` taxonomy tables. It is
a dependency of ING-033 and ING-034 (the reverse direction).

**Test note:** the route-set assertion in
`tests/ing_019_api_test.go` (`TestING019_AC7_OnlyReadOnlyRoutes`) currently
asserts exactly two read-only routes; adding this route means that assertion

**Out of scope:** the create/edit form UI (ING-033/034); any change to the
taxonomy values themselves (`03-taxonomy.md` is read-only to agents); write
routes; adding a client-side enum module.

## Implementation notes

Implemented `GET /api/taxonomy` as a pure read of `internal/tagging`'s
existing validation tables — no second enum copy, no store, no model, no
auth, no new dependency (`go.mod` untouched).

**What was done**

1. `internal/tagging/validate.go`: added the exported `Taxonomy` struct
   (JSON shape: `categories` mapping each category to its valid
   subcategories, plus `colors`, `patterns`, `warmth_tiers`,
   `formality`) and `TaxonomyTables()`, which builds it from the same
   package vars `ParseTaggingResult` validates against
   (`validCategories`, `validSubcategories`, `colorPalette`,
   `validPatterns`, `validWarmthTiers`, `validFormalities`). The
   categories map is keyed by iterating `validCategories`, so every
   approved category appears with its subcategories.
2. `internal/api/api.go`: registered `r.GET("/api/taxonomy", taxonomy)`
   in `New` and added the handler — `c.JSON(http.StatusOK,
   tagging.TaxonomyTables())`, a pure table read with no store or model
   dependency. Package doc and `New` doc comments updated to mention the
   taxonomy surface. No other route's registration or handler changed.
3. `tests/ing_019_api_test.go`: `TestING019_AC7_OnlyReadOnlyRoutes`'s
   route-set assertion updated from 2 to the 3 approved read-only routes
   (adds `GET /api/taxonomy`), per this ticket's test note and ING-030's.
   All routes remain GET-only, so the "no create/update/delete route"
   intent holds.
4. `tests/ing_036_taxonomy_test.go` (new):
   - `TestING036_AC1_TaxonomyRouteServes200JSON` — plain unauthenticated
     GET → 200, `application/json`, and exactly the five contract keys
     (`categories`, `colors`, `patterns`, `warmth_tiers`, `formality`);
     the key names are the asserted wire contract (like
     `ing019ItemKeys`), the enum values are never spelled out.
   - `TestING036_AC2_ResponseMatchesTaggingTables` — response compared
     to `tagging.TaxonomyTables()` field by field (every list, every
     category, every per-category subcategory list, both directions on
     the category key set). The expected side is derived from the
     tables, not hand-copied — the ING-014 "tables match the spec"
     spirit. Chained with `TestTaxonomyTablesMatchSpec` (tables ==
     `03-taxonomy.md`, already green), the response is pinned to the
     approved spec without re-parsing it in this test file.

  (category → subcategories) rather than an ordered array: Go marshals

### Edge cases checked (spec-implied)

- **Empty vocabulary** — would be caught by the chain, not silently passed:
  AC2 hard-fails on empty `categories` and on any list differing from the
  tables; `TestTaxonomyTablesMatchSpec` fails if the tables themselves
  became empty vs. the spec (and `loadTaxonomy` in `tests/` fatals on an
  empty parse).
- **Non-GET method on the route** — AC7's exact route set proves only
  `GET /api/taxonomy` is registered; combined with ING-021's
  `TestING021_AC3_UnknownAPIPathIs404NotHTML` (unknown `/api` paths →
  404 JSON-less, never SPA HTML), write-method probes cannot hit a
  handler.
- **Wire key names / category order** — neither the ticket nor the specs
  pin JSON key names or category ordering; Coder's chosen snake_case keys
  mirror `07-architecture.md`'s wording, and `03-taxonomy.md` defines no

  ING-033/034 need spec order — acceptable, not a defect.

  satisfied by a hand copy living on either side; the transitive pin to
  the spec file relies on `TestTaxonomyTablesMatchSpec`, which was
  re-run green in this session.
