### [ING-026] Automated check that the Tailwind v4 build/config still produces v4 CSS

**As a** wardrobe owner
**I want** an automated check that fails if the Tailwind v4 pipeline
(`@tailwindcss/vite` plugin, single `@import "tailwindcss";`, no v3-era
config files, v4 markers in the built CSS) regresses
**So that** the Tailwind v4 setup `07-architecture.md` mandates is verified by
a command, not by a one-off manual build — the coverage ING-025 retired

**Acceptance criteria** (Gherkin):
```
Given the frontend build pipeline
When `npm test` runs in frontend/
Then the check exercises the real Vite + Tailwind build and fails if the
  emitted `frontend/dist/assets/*.css` stops containing Tailwind-generated
  v4 output (Tailwind custom properties / `@layer` at-rules), rather than
  passing on an empty or unprocessed stylesheet

Given the Tailwind v4 configuration fixed by 07-architecture.md
When the check runs
Then it fails if the `@tailwindcss/vite` plugin is removed from
  `vite.config.js`, if `src/index.css` stops being the single
  `@import "tailwindcss";` entry point, or if a v3-era
  `tailwind.config.js` / `postcss.config.js` is introduced
And those config-shape clauses may be asserted by reading the files — this
  is build configuration, not component behavior, so a structural check is
  the right kind here (unlike the retired ING-020 component suite)

Given the tracked placeholder `frontend/dist/index.html`
When the check runs
Then it does not overwrite that file in place and does not depend on it —
  build output is produced into an isolated/temporary outDir (or the check
  otherwise leaves the tracked placeholder's content untouched)

Given the new check
When `npm test` and `go test ./...` run
Then both are green, and the check adds no runtime dependency (dev/test-time
  tooling only — 00-overview.md's fully-local constraint and the
  single-binary runtime model are untouched)
```

**Spec reference:** `07-architecture.md` "Frontend" (the Tailwind v4 setup:
`@tailwindcss/vite` plugin, single `@import "tailwindcss";`, no
`tailwind.config.js`); `06-decisions.md` "Testing tooling: Vitest + Testing
Library for the frontend, stdlib-first for Go" (tests live under `frontend/`,
run via `npm test`); `backlog/ING-020.md` AC4 (the structural assertions being

**How each AC is met**
- **AC1 — real build, v4 CSS.** `beforeAll` calls Vite's programmatic
  `build()` with `root: frontend/` and `configFile: frontend/vite.config.js`,
  so the project's own `@tailwindcss/vite` plugin compiles the real
  `src/index.css`; output goes to the scratch `outDir`. The test then locates
  the emitted `.css` and asserts it is (a) non-empty, (b) contains a
  Tailwind `@layer` at-rule, (c) contains theme custom properties
  (`--x:`), and (d) contains a utility the app actually uses (`.grid`, from
  `App.jsx`). (d) is deliberate: the raw `tailwindcss` package CSS already
  ships `@layer`/`--color-*`, so markers alone would not distinguish an
  *unprocessed* stylesheet; `.grid` exists only after the plugin scans source,
  so the check fails on an empty/unprocessed stylesheet. It does not grep
  source for CSS.
- **AC2 — config shape, structural reads.** Three `it`s read files:
  `vite.config.js` contains `@tailwindcss/vite` and registers
  `tailwindcss()` in `plugins`; `src/index.css` trims to exactly
  `@import "tailwindcss";`; and no `tailwind.config.{js,cjs}` /
  `postcss.config.{js,cjs}` exists at the `frontend/` root.
- **AC3 — isolated outDir, placeholder untouched.** The build writes to
  `<project root>/temp/ing-026-vite-build` (gitignored project scratch per
  `AGENTS.md` §10), never `frontend/dist`. The test reads
  `frontend/dist/index.html` before the build and asserts it is byte-for-byte
  identical afterwards. `afterAll` removes the scratch dir, so a failing test
  still cleans up.
- **AC4 — no new dependency / both suites green.** The check imports only the
  already-installed `vite` and `vitest` plus Node built-ins; `package.json` is
  unchanged. `npm test` and `go test ./...` are both green (evidence below).

   it opts into the node environment for this file only; `App.test.jsx` keeps
   jsdom via `vite.config.js`. This is a per-file environment, not a second
   runner.
4. **Generated-utility assertion added to AC1 (`.grid`).** The ticket permits
   marker-based assertions, but markers are also present in the raw package
   CSS. `.grid` is not present anywhere in `tailwindcss` (verified) and is only
   emitted when the plugin processes `App.jsx`, so this makes AC1 fail on an
   unprocessed stylesheet rather than only on a literally empty one. This
   strengthens AC1; it does not weaken or reinterpret it.
5. **Banned-config scan is the `frontend/` root only.** Project config files
   live at the package root; a recursive scan would false-positive on
   `postcss.config.js` fixtures inside `node_modules/`. This matches the
   previous ING-020 AC4 check.
