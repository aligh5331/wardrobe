### [ING-034] Frontend: add a garment (upload → local draft → correct → save)

**As a** wardrobe owner
**I want** to upload one garment photo in the browser, see the local VLM's draft,
correct it, and save it
**So that** I can catalog a garment without the CLI and confirm the tags before
they are written

**Acceptance criteria** (Gherkin):
```
Given the catalog UI
When the user activates an add control
Then a form with a file input appears, accepting .jpg / .jpeg / .png / .webp

Given a chosen photo file
When the user submits it
Then the client POSTs multipart to /api/items/photo and shows a loading state
  while the local VLM tags it

Given the upload succeeds
When the draft returns
Then its seven tagging fields pre-fill editable inputs (plus optional notes)
  with a preview of the uploaded photo, and nothing is persisted yet

Given the draft form
When it needs the valid values for a field
Then it loads them from GET /api/taxonomy (ING-036) rather than a bundled
  client-side copy, so the choices match the enums the server validates against

Given the draft is shown
When the user corrects fields and saves
Then the client POSTs /api/items with the item id and the corrected fields, and
  on a 2xx the grid refreshes and shows the new item

Given tagging fails after the retry-once policy
When the error returns
Then the UI surfaces it and lets the user retry or pick another photo, with
  nothing persisted

Given the server returns 400 naming a field
When the user saves
Then the named field is surfaced to the user and the error is not silently
  swallowed

Given the change
When it is reviewed against the project's constraints
Then it uses only the local API, adds no runtime dependency, and is covered by
  Vitest + Testing Library tests under frontend/ (npm test)
```

**Spec reference:** `07-architecture.md` "Backend" → "Catalog write API
(interactive create/edit)" (`POST /api/items/photo`, `POST /api/items`) and
"Taxonomy read route (create/edit forms)" (`GET /api/taxonomy`, the enum source
the form loads) plus "Frontend"; `06-decisions.md` "Taxonomy exported to the
browser via `GET /api/taxonomy`, not a bundled copy"; `06-decisions.md`
"Interactive catalog create/edit UI: local VLM draft, human confirm, shared
persistence" (create returns an unpersisted draft, the human confirms, then
save); `06-decisions.md` "Photo upload trust boundary" (the accepted extensions
and cap the UI must respect); `05-vlm-tagging-spec.md` "Interactive tagging (web
UI)"; `04-data-schema.md`.

**Status:** Ready

**Resolved (was blocked on the taxonomy source):** the corrected-fields form
needs the approved enum values so the user can pick valid ones. This is now
decided: the backend serves them via `GET /api/taxonomy` (`06-decisions.md`
"Taxonomy exported to the browser via `GET /api/taxonomy`, not a bundled copy";
`07-architecture.md` "Taxonomy read route (create/edit forms)"), ticketed as
ING-036. The form loads its choices from that route instead of a bundled copy,
so the client and server cannot drift.

**Context:** This is the browser-side counterpart of `cmd/ingest`: same local
model, same retry-once policy, but with a human confirm step before persist.
`frontend/src/App.test.jsx` currently asserts no write controls are rendered and
only GETs `/api/items` — that assertion must be revised by whichever frontend
ticket lands first.

**Routing:** Ready → Coder. Touches `frontend/src/` and its tests.

**Out of scope:** editing existing items (ING-033); drag-drop, multi-file, or
bulk upload (not in Phase 1); client-side image editing/cropping; re-tagging;
