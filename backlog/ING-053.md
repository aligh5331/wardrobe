### [ING-053] `internal/api`: Gin access-log middleware, request-scoped logger, `WithLogger` option

**As a** wardrobe owner
**I want** every HTTP request logged with method, matched route, status,
latency, size, client IP, and a server-generated `request_id`, at a level chosen
from the status class, with a request-scoped logger available to handlers and
`item_id` on server-error records of `:id` routes
**So that** a local API request is observable and can be correlated with
server-side error logs, without adding any logger dependency

**Acceptance criteria** (Gherkin):
```
Given the Gin engine built by internal/api
When any request is served
Then exactly one access-log record is emitted for it
And that record carries the request method, the matched route, the response
  status, the latency, the response size, and the client IP
And it carries a request_id

Given a request whose response status is 2xx or 3xx
When the access log is emitted
Then its level is info
Given a request whose response status is 4xx
Then its level is warn
Given a request whose response status is 5xx
Then its level is error

Given each registered route: GET /api/items, GET /api/items/:id,
  PUT /api/items/:id, POST /api/items, POST /api/items/photo,
  GET /api/photos/:filename, GET /api/taxonomy, GET /api/weather,
  GET /api/weather/cities, GET /api/weather/location,
  PUT /api/weather/location, POST /api/recommendations
When a request is served on each
Then its record's matched route is the registered pattern (for example
  "/api/items/:id", not the concrete path)
And its level follows the response status class
  (for example GET /api/taxonomy 200 is info, POST /api/recommendations with a
  malformed body 400 is warn, and a route that returns 503 because its client is
  not wired, such as GET /api/weather or POST /api/recommendations without the
  option, is error)

Given requests that are not API calls: a static asset or SPA path served by the
  ServeFrontend fallback, a photo request under /api/photos/:filename, and an
  unknown /api path that returns 404
When each is served
Then each produces exactly one access-log record (no path is filtered out)

Given any request
When the response is written
Then the response carries an X-Request-ID header equal to the request_id in the
  access-log record
And two different requests receive different request_ids

Given a request that carries its own X-Request-ID header (for example "abc")
When it is served
Then the request_id in the record and in the response header is server-generated
  and is not "abc"

Given the middleware has run for a request
When a handler calls logging.FromContext(c.Request.Context())
Then it gets a logger whose records carry the same request_id as that request's
  access-log record
And those records go to the logger passed via WithLogger, not slog.Default()

Given a request that results in a 5xx on a route with an :id path parameter
  (for example GET /api/items/:id or PUT /api/items/:id on a failing store)
When the error-level access log is emitted
Then the record carries the request_id and an item_id equal to that path id

Given a route with no :id path parameter whose handler calls
  c.Set("item_id", "x") (a test route on the returned engine) and then returns 5xx
When the error-level access log is emitted
Then the record carries the request_id and item_id "x"
And when the handler does not call c.Set, the record has no item_id
  (the real handlers set it in ING-058)

Given a handler that panics
When the request is served
Then the client receives 500, and one error-level access-log record with status
  500 is emitted for it

Given existing callers that call api.New(st, photosDir, ...) without a logger
When the engine serves a request
Then their behavior is unchanged and access logs go to slog.Default()
Given api.New is called with the new WithLogger option
Then access-log records go to that logger

Given the change
When existing route, response-body, and status behavior is compared
Then registered routes are unchanged (still 12), no response body or status
  changes, and no handler body is edited in this ticket
And it is local only (no network/telemetry) and adds no dependency
  (stdlib log/slog only; go.mod and go.sum unchanged)
```

**Spec reference:** `07-architecture.md` "## Logging": "HTTP access log: every
request to the Gin engine logs method, matched route, status, latency, response
size, client IP and a generated `request_id`. The id is always generated
server-side and returned as an `X-Request-ID` response header; an incoming
`X-Request-ID` is ignored. Level follows the status class: 2xx/3xx `info`, 4xx
`warn`, 5xx `error`. Every request is logged, including static assets and
photos", "Request-scoped logger: the middleware stores a logger carrying
`request_id` in the request context", and "Correlation: error logs carry
`request_id` and, where one exists, the `item_id`, so an API request can be
joined to its `logs/vlm-attempts.jsonl` records"; `06-decisions.md` "Structured
logging: stdlib `log/slog`, local stderr + file, env-configurable level/format"
(Access logging and Correlation bullets; rejects `gin.Logger()` as-is).

**Status:** Testing

**Context:** The middleware is added in `internal/api` (`api.New`) and takes a
`*slog.Logger` through a new option, `WithLogger(*slog.Logger)` (same `Option`
style as `WithWeather`); the default when absent is `slog.Default()`, so every
existing caller, including the `api.New(st, photosDir)` calls in `tests/`, is
behaviorally unchanged. It stores a `request_id`-carrying child logger in the
request context with the ING-052 `logging.WithLogger` helper, so `internal/api`
now imports `internal/logging`; that is why this ticket depends on ING-052.
Register it before `gin.Recovery()` so a panic is seen as a 500 by the logger.
Gin's `c.FullPath()` is the "matched route" (empty on the `NoRoute` path, which
is acceptable); response size is the Gin writer's byte count. The `request_id`
format is not pinned by the spec; reusing the codebase's existing id generator
(`tagging.NewItemID` or similar) or an equivalent is a Coder choice. Attribute
names other than `request_id` and `item_id` (both named in the spec) are a Coder
choice, but must be consistent and are asserted by the tests; record the chosen
names in the ticket.

**`item_id` on error records:** `07-architecture.md` says `item_id` is attached
"where one exists" without naming how a handler conveys it. Ali decided: the
middleware reads `c.Param("id")` on `:id` routes, and falls back to
`c.GetString("item_id")` when there is no `:id` param. That value is empty until
ING-058 adds the two `c.Set("item_id", ...)` lines to the upload and create
handlers, so ING-058 needs no middleware change. This ticket edits no handler
body.

**Routing:** Ready -> Coder. Touches `internal/api/api.go` (option and middleware
registration only), possibly a new file in `internal/api/` for the middleware, and
tests under `tests/` (or `internal/api/`). `cmd/server` is not touched here; it
keeps the default `slog.Default()` until ING-054 passes the configured logger.

**Depends on:** ING-052 (the `logging.WithLogger`/`FromContext` context helper).
Do not start this ticket if ING-052 is not yet Done.

**Out of scope:** building the logger from config (ING-052); replacing stdlib
`log` in `cmd/ingest`/`cmd/server` and passing the configured logger to
`api.New` (ING-054); LLM attempt logging and use of the request-scoped logger
inside `internal/recommend` and the `502` path in `internal/api/recommend.go`
(ING-055); Open-Meteo attempt logging (ING-056); log filtering of static or
photo requests; any new route or any handler body change. The two
`c.Set("item_id", ...)` lines in `uploadPhoto` and `createItem`, and the
`item_id` behavior for `POST /api/items/photo` and `POST /api/items`, belong to
ING-058.

**Test note:** engine-level tests using `httptest` and

## Implementation notes

Two commits: 66f61f4 (middleware, option, four tests) and part 2 (remaining
tests and these notes).

`internal/api/accesslog.go` (new): `accessLog(base *slog.Logger)` Gin
middleware. `internal/api/api.go`: `config.logger`, the `WithLogger(*slog.Logger)`
option, and `r.Use(accessLog(cfg.logger), gin.Recovery())`. No handler body is
edited, `engine.Routes()` is unchanged (12), and `go.mod`/`go.sum` are untouched.
Part 2 found no middleware bug and changed no non-test code.

**Record shape.** Message `"http request"`, one record per request, with these
attributes:

| Attribute | Value |
|---|---|
| `method` | request method |
| `route` | `c.FullPath()`, the registered pattern (empty on the `NoRoute` path) |
| `status` | response status |
| `latency` | `slog.Duration`, from middleware entry to return |
| `size` | response bytes written (0 when nothing was written) |
| `client_ip` | `c.ClientIP()` |
| `request_id` | server-generated id, also in the `X-Request-ID` response header |
| `item_id` | 5xx records only, and only when known (see below) |

Level: 2xx/3xx info, 4xx warn, 5xx error. The `request_id` is added to a child
logger, so it appears on the handler's own records too.

**request_id format.** UUIDv4 from `tagging.NewItemID`, the generator the
codebase already uses for item ids. An inbound `X-Request-ID` is ignored.

**item_id.** On a 5xx the middleware reads `c.Param("id")`, then falls back to
`c.GetString("item_id")`. It adds the attribute only when the value is non-empty,
so a 5xx with neither (for example `GET /api/weather` 503) has no `item_id` key.
Real handlers do not call `c.Set` until ING-058.

**Panic.** The middleware is registered before `gin.Recovery()`. Recovery writes
the 500 and returns normally to `c.Next()` in the middleware, so the record has
status 500 at error level, with no `defer`/`recover` in the middleware. Recovery
still prints its own stack trace to Gin's default error writer (stderr), outside
`slog`. That is not an access-log record and this ticket does not change it.

**Default logger.** With no `WithLogger`, `slog.Default()` is read on every
request, not once in `New`, so a later `slog.SetDefault` (ING-054) takes effect
on an engine that already exists.

**Assumptions**

- Routes that need heavy setup use the cheapest real outcome. `POST /api/items/photo`
  is covered by its 503 (processor not wired), not a live VLM. `POST /api/items`
  is covered by a 400 for a malformed body, not a staged-upload create.
  `POST /api/recommendations` is covered by 400 (malformed body) and 503 (not
  wired). No 502 from a dead LLM URL is asserted for it.
- `GET /api/weather` and `GET /api/weather/cities` also get a dead-URL 502
  (`http://127.0.0.1:1`, refused immediately). This is error level, so the 5xx
  class is exercised for a route wired to an upstream.
- `GET /api/photos/:filename` covers a missing file (404) and a bad name (400).
  A 200 with a real file is not logged-tested here. The route already has ING-019
  coverage and the level logic does not depend on the body.
- The non-API test asserts an empty `route` on the `NoRoute` path, which the
  ticket calls acceptable.
- `PUT /api/items/:id` on a closed store gets a 500 from the id lookup, before
  the body is read, so the test sends `{}`.
