### [ING-043] API: `/api/weather`, `/api/weather/cities`, `GET`/`PUT /api/weather/location` + server wiring

**As a** wardrobe owner
**I want** local API routes for weather, city search, and my saved location
**So that** the web UI can show weather and change location while only talking to `localhost`

**Acceptance criteria** (Gherkin):
```
Given no saved location and a fake Open-Meteo forecast server
When a client GETs /api/weather
Then it receives 200 with {location, current, today} in the exact shape of
  07-architecture.md "Weather (Phase 2)", location being the Tehran default
  {name, country, latitude, longitude}

Given a saved location
When a client GETs /api/weather
Then the forecast is fetched for the saved latitude/longitude and the response
  location is the saved one

Given the fake forecast server returns null for some requested variables
When a client GETs /api/weather
Then it receives 200 and those fields are JSON null (not 0); other fields are unchanged

Given the forecast upstream is unreachable, returns non-2xx, or returns an unparseable body
When a client GETs /api/weather
Then it receives 502 with a JSON error message

Given a fake geocoding server with matches for "par"
When a client GETs /api/weather/cities?q=par
Then it receives 200 with a JSON array of at most 10 {name, country, admin1, latitude, longitude}

Given the geocoding server returns zero results
When a client GETs /api/weather/cities?q=zzzz
Then it receives 200 with [] (not null)

Given q is missing, empty, or whitespace-only
When a client GETs /api/weather/cities
Then it receives 400 and no upstream call is made

Given the geocoding upstream fails (unreachable, non-2xx, unparseable)
When a client GETs /api/weather/cities?q=par
Then it receives 502 with a JSON error message

Given no saved location
When a client GETs /api/weather/location
Then it receives 200 with the Tehran default {name, country, latitude, longitude}

Given a valid body {name, country, latitude, longitude}
When a client PUTs /api/weather/location
Then it receives 200 with the saved {name, country, latitude, longitude}
And a following GET /api/weather/location returns the saved values

Given a PUT body with name missing, empty, or whitespace-only; latitude or longitude
  missing (absent, not treated as 0); latitude outside -90..90; or longitude outside -180..180
When a client PUTs /api/weather/location
Then it receives 400 whose error names the offending field, and the saved location is unchanged

Given a PUT body {name: "Null Island", latitude: 0, longitude: 0}
When a client PUTs /api/weather/location
Then it receives 200 (an explicit 0 is valid; only an absent field is rejected)

Given the local database read or write fails
When a client calls any weather route that touches the saved location
Then it receives 500

Given a geocoding result with no country or admin1
When a client GETs /api/weather/cities?q=par
Then that result has "" for the missing field
And the upstream request carries name=<q> and count=10 and no language parameter

Given a malformed JSON body
When a client PUTs /api/weather/location
Then it receives 400

Given the weather upstream is down
When catalog routes (/api/items, /api/taxonomy, ...) are called, or the server starts
Then they behave exactly as before; weather failures never affect catalog routes or startup
  (cmd/server makes no Open-Meteo call at startup)

Given the registered route set
When routes are inspected
Then exactly the four new routes are added to the existing seven, and no
  existing route changed
```

**Rulings on Tester's open notes**

1. **503 when `WithWeather` is not wired: acceptable.** This is the same
   convention as `WithTagging`, which returns 503 `tagging is not configured`
   (`api.go:557`). The route set stays fixed, and production always wires the
   client, so the spec's 502/500 contract is unaffected. It is not a spec
   change, and it only applies in tests and embedders that choose not to wire
   the client.
2. **502 message includes upstream detail: acceptable, not a leak.** The
   detail is the Open-Meteo status text, a JSON parse error, or a `url.Error`
   that can include the request URL with the saved lat/lon. Those
   coordinates are the user's own public-API query, returned to the same
   user's browser on `localhost`. There is no key, secret, catalog data, or
   filesystem path. `07` only requires "502 with an error message", and the
   detail helps debugging. A fixed message would be fine too, but it is not
   required.
3. **Coordinate presence checked before name: acceptable.** `07` requires
   that the error name "the field", which means one field. Any consistent
   order meets that, and it matches ING-042, where one field is named per
   error.
4. **A string latitude gives a 400 that mentions `putLocationRequest`:
   acceptable, because it is consistent.** The existing catalog routes use
   the identical pattern: `updateItem` (`api.go:376-377`) and `createItem`
   (`api.go:446-447`) both return `"invalid JSON body: " + err.Error()` from
   `ShouldBindJSON`, so they expose `updateItemRequest`/`createItemRequest`
   the same way. The message still names `latitude`, as `07` requires.
   Consistency wins. Changing it would be a cross-route cleanup ticket, not
   an ING-043 fix.

**Over-engineering: none of substance.** There is one `Option`, as the
ticket asks, and no interface, cache, retry, or config. The anonymous
response struct embedding `weather.Forecast` is the smallest shape that
exists in only one place. One non-blocking nit: after a successful save, the
extra `st.WeatherLocation()` read could be avoided if `SaveWeatherLocation`
returned the stored value. It is not worth changing the store API for this.
Leave it.
