### [ING-049] API: `POST /api/recommendations` + server wiring

**As a** wardrobe owner
**I want** one local route that returns today's 3 outfit suggestions
**So that** the web UI can show recommendations on a button click

**Acceptance criteria** (Gherkin):
```
Given a catalog that fills every slot, a fake weather server, and a fake LLM returning valid outfits
When a client POSTs /api/recommendations with {} (and separately with no body)
Then it receives 200 with {weather, outfits}
And weather has the same shape and values as GET /api/weather
And outfits has 3 entries, each {items, reason}, items in the same shape as GET /api/items
And items in an outfit are ordered outerwear, top, bottom, footwear, headwear, accessory

Given body {"formality":"formal","note":"  wedding  "}
When it is posted
Then only formal items reach the LLM prompt and the note is trimmed

Given formality not in the taxonomy (e.g. "business"), or a note longer than 500 characters
  after trimming, or malformed JSON
When it is posted
Then it receives 400 whose error names formality, note, or the body

Given the weather upstream fails
When it is posted
Then it receives 502 and the LLM is not called

Given the filtered catalog lacks footwear (or any required slot)
When it is posted
Then it receives 422 whose error names the missing slot(s), and the LLM is not called

Given the LLM is unreachable, times out, returns non-2xx, or is invalid twice
When it is posted
Then it receives 502 with a JSON error message
And with LLM_MODEL empty and a non-2xx LLM answer, the message says to set LLM_MODEL

Given the local database fails
When it is posted
Then it receives 500

Given the recommendation route exists
When GET /api/items, /api/weather, and the catalog write routes are called
Then they behave exactly as before

Given the registered route set
When routes are inspected
Then exactly one route (POST /api/recommendations) is added to the existing 11

Given cmd/server
When it starts
Then it wires the recommender with LLM_URL, LLM_API_KEY, LLM_MODEL, LLM_TEMPERATURE
  and makes no LLM call at startup
```

## Implementation notes

`internal/api/recommend.go` (new): `postRecommendations(st, w, p)` and the
types `recommendRequest`, `outfitResponse` and `recommendResponse`. Steps in
order:

1. 503 when the recommender is unwired.
2. Body parse. Failure is 400 naming "body".
3. Formality checked against `tagging.TaxonomyTables().Formality`. Failure is
   400 naming "formality".
4. Note trimmed, then limited to 500 runes. Failure is 400 naming "note".
5. Weather fetch: 503 unwired, 500 DB, 502 upstream.
6. Catalog list. Failure is 500.
7. `RulesFor`, `Filter`, then `MissingSlots`. Any missing slot is 422 naming
   the slots, with no LLM call.
8. `Pick`. Any error is 502 with the error text.
9. Response `{weather, outfits}`. Items come from the candidates by id and are
   sorted stably outerwear, top, bottom, footwear, headwear, accessory.

## Review

**Decision: APPROVED**

Reviewed `git diff` for `internal/api/api.go`, `cmd/server/main.go` and
`tests/ing_019_api_test.go`, the untracked `internal/api/recommend.go`,
`tests/ing_049_recommendations_test.go` and `tests/ing_049_gap_test.go`, and the
Implementation notes and Test results above. Checked against the ticket ACs,
`07-architecture.md` "Recommender (Phase 3)" (flow, response, ordering, error
table), `06-decisions.md` "Recommender approach", "Recommender output
validation" and "LLM config", `00-overview.md` hard constraints and `AGENTS.md`.
The review agent did not run `go vet`, `gofmt` or `go test`. Ali ran all three
just before this review (clean, all ok), and Tester recorded the same. I read
the code and the test names directly.

Blocking findings: none.

- **Flow order matches the spec.** In `postRecommendations`: unwired 503, body
  and field validation (400), weather (`fetchWeather`, 502 on upstream failure,
  no `Pick` call), `st.List` (500), `RulesFor`, `Filter`, `MissingSlots` (422
  naming the slots, no `Pick` call), then `Pick` (502 on any error). Validating
  the request before the weather fetch saves an outbound call on a bad request
  and does not contradict the spec, which lists weather first only within the
  flow of a valid request.
- **Response.** `items` is built with `make`, never nil, and so are `outfits`.
  Items come from the candidate map by id (`validate` already rejects ids that
  are not candidates, so `byID[id]` cannot return a zero item) and go through
  `toResponse`, the same function `GET /api/items` uses, so the shape and the
  non-null `secondary_colors` match. `SortStableFunc` on the category rank gives
  outerwear, top, bottom, footwear, headwear, accessory. Tester's raw-JSON test
  checks the key sets.
- **`getWeather` refactor.** Compared line by line. Same order (nil client 503,
  location 500, forecast 502), same three messages, same
  `{location, current, today}` JSON: the anonymous struct became the named
  `weatherResponse` with the same fields and tags. `GET /api/weather` still
  writes the error with `gin.H{"error": msg}`. No behavior change. One shared
  helper instead of a copy, as the ticket routing asked.
- **Trust boundary.** Formality is checked with
  `slices.Contains(tagging.TaxonomyTables().Formality, ...)`, so there is no
  second list, and an empty string means any. The note is trimmed, then counted
  in runes (`utf8.RuneCountInString`), so 500 passes and 501 fails. Malformed or
  truncated JSON is 400 (`io.EOF` only, so `{"formality":` is 400 and an empty or
  whitespace body is valid). Wrong JSON types are 400 naming the body. The body
  is capped at 64 KiB with `http.MaxBytesReader`, so an oversize body is 400 and
  not read into memory. The cap is not in the spec, is far above any valid
  request (500-character note) and is stated in the notes. Fine.
- **Data after the first JSON value is ignored** (`{"note":"x"} junk` gives 200).
  The spec says "bad JSON body" is 400. The trailing bytes are not a valid
  document, so this is a small gap against the spec's wording. The code comment
  flags it, no invalid value can pass, and the caller is the project's own UI.
  Not blocking. See note 3.
- **LLM error text (Tester finding 1, Coder gap 2): non-blocking, not a spec
  question.** The spec table says only `502`, and the UI paragraph says a failure
  "shows the server's error message", so the browser is meant to see a
  useful message. The text carries the 300-byte, single-line reply snippet from
  `snippet()` and, for a non-2xx with empty `LLM_MODEL`, the hint the spec
  requires. In a single-user local app the browser user owns the LLM server, the
  catalog and the note, so nothing crosses a trust boundary. The snippet cannot
  hold the API key: the key is only in the `Authorization` header, is never
  formatted into an error, and `TestT49_APIKeyNotInResponse` checks the 401,
  invalid-output and success bodies. Photo paths and `notes` are never in the
  prompt (ING-048), so an echoing server could return at most ids, attribute
  values and the user's own note. The reply snippet is also the fastest way to
  debug a wrong `LLM_URL` or model name. No log line exists, so nothing is
  logged today. If Ali wants the shorter-message variant it is a small follow-up
  (log the snippet, return `llm returned <status>`), not a fix for this ticket.
- **Scope.** `git status` shows only: `backlog/ING-049.md`, `cmd/server/main.go`,
  `internal/api/api.go`, `tests/ing_019_api_test.go`, new `internal/api/recommend.go`
  and two new test files. No UI, cache, outfit log, config change,
  `.env.example`, `go.mod`, `go.sum` or protected file touched. No `data/` or
  `.env` content in the diff.
- **Route count.** One `r.POST("/api/recommendations", ...)` added. The ING-019
  edit is the comment, `11` to `12` (two places) and one `want` entry. Nothing
  else changed there.
- **`cmd/server`.** `api.WithRecommender(&recommend.Picker{URL, APIKey, Model,
  Temperature})` from `cfg.LLMURL`, `cfg.LLMAPIKey`, `cfg.LLMModel`,
  `cfg.LLMTemperature`, added as one more option after `WithWeather`. Existing
  wiring is unchanged and there is no LLM call at startup. `Timeout` is unset, so
  the 120 s default applies per call.
- **Hard constraints clean.** The only new outbound call goes to the configured
  `LLM_URL`. No cloud service, no fine-tuning, no photo handling, no
  multi-garment assumption. Stdlib plus Gin and the project packages only
  (`cmp`, `slices` and `unicode/utf8` are stdlib).
- **Over-engineering: none worth cutting.** One handler, three small types, one
  tiny order map. `fetchWeather` returns `(response, status, msg)`, which is
  plain and avoids duplicating the three error branches. `WithRecommender`
  follows `WithWeather`. The gap test file overlaps the Coder file in a few
  places (success path, 502 cases) but adds raw-JSON, list-failure, API-key,
  cold/hot and body-edge cases. The source-reading wiring test is a workaround for
  `cmd/server` having no test files, and is stated as such.
- **Style.** No em dashes and no banned vocabulary in the new code, comments,
  error messages or ticket text I read. The em dashes in `api.go` comments are
  old lines, not in this diff.

Non-blocking notes for Ali (no ticket created):

1. **Tester finding 2 (503 before body validation): fine.** The server always
   wires the recommender, and the spec does not order these.
2. **Tester finding 3 (240 s worst case, no `WriteTimeout`): no spec edit
   needed, ING-050 must handle it.** The spec allows 120 s per call and two
   attempts. `http.ListenAndServe` has no write timeout, so the server does not
   cut the request. ING-050's fetch must not time out before about 240 s and
   should show a busy state. Put this in ING-050's ticket text, since it is a UI
   concern and not a change to this route. If the client disconnects, the
   request context cancels the LLM call.
3. **Trailing data after the JSON value.** If Ali wants strict parsing, one
   `dec.More()` or second `Decode` check would return 400. Low value, so a
   follow-up only if wanted.
4. **404 for `GET /api/recommendations` (Tester finding 5): fine.** Same as
   the other POST-only paths, and the spec names no status.
5. **`snippet` cuts at 300 bytes**, which can split a multi-byte character. JSON
   encoding replaces the broken byte, so the response stays valid. Cosmetic, and
   in ING-048 code.
6. **Test gaps are acceptable.** `cmd/server` has no test harness (wiring checked
   by source), no test runs the real 120 s timeout, and the list-failure test
   covers a dropped table only. None is a spec or ticket miss.
