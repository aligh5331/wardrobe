### [ING-052] `internal/logging`: configured `log/slog` logger (stderr + `logs/app.log`) and context helper

**As a** wardrobe owner
**I want** one `log/slog` logger built from the validated level/format that
writes to stderr and an append-only `logs/app.log`, plus a way to carry a
logger in a `context.Context`
**So that** every runtime log record shares the same sinks, level, and format,
request-scoped code can find its logger, and the whole app still ships with no
logging dependency

**Acceptance criteria** (Gherkin):
```
Given a validated LOG_LEVEL and LOG_FORMAT
When a logger is built from them
Then records at or above the level are emitted to both the stderr sink and
  logs/app.log
And records below the level are emitted to neither

Given LOG_LEVEL=warn
When a debug and an info record are logged followed by a warn record
Then only the warn record appears in the sinks

Given LOG_FORMAT=json
When a record is logged
Then each sink line is a parseable JSON object carrying the record's
  level, message, and attributes

Given LOG_FORMAT=text
When a record is logged
Then each sink line is the text handler's key=value rendering (not JSON)

Given logs/app.log does not exist
When the logger is built
Then the file (and its logs/ directory) is created and the first records are
  appended to it
And a second build appends to the same file rather than truncating it

Given the log path and the stderr writer are injectable
When a unit test builds a logger pointed at a temp directory and a bytes.Buffer
Then no test writes to the repository's real logs/ directory or real stderr

Given logs/app.log cannot be opened (unwritable path or a directory)
When the logger is built
Then building does not fail
And a warning record naming the failure and the fallback to stderr only is
  emitted to the stderr sink
And subsequent records still reach stderr

Given the ING-005 attempt trail logs/vlm-attempts.jsonl
When the logger is built
Then that trail is separate and unchanged: its records are not merged into
  logs/app.log

Given a context that carries no logger (for example context.Background())
When logging.FromContext(ctx) is called
Then it returns slog.Default()

Given a logger l and ctx2 = logging.WithLogger(ctx, l)
When logging.FromContext(ctx2) is called
Then it returns l
And it also returns l for a context derived from ctx2 (for example via
  context.WithCancel)
And the original ctx still returns slog.Default()
```

**Spec reference:** `07-architecture.md` "## Logging": "Sinks: process stderr

## Implementation notes

New package `internal/logging`, stdlib only. `logging.go` holds the code and
`logging_test.go` the tests.

**Exported API** (ING-053 and ING-054 call these)

```go
func New(level, format, path string, stderr io.Writer) (*slog.Logger, io.Closer, error)
func WithLogger(ctx context.Context, l *slog.Logger) context.Context
func FromContext(ctx context.Context) *slog.Logger
```

Callers pass `cfg.LogLevel`, `cfg.LogFormat`, `"logs/app.log"` and `os.Stderr`.
`New` takes the already-normalized lower-case values from `config.Load` and does
not re-validate env vars. It returns an error only if `level` or `format` is not
one of `debug|info|warn|error` and `text|json`, which a caller wired to
`config.Load` cannot hit. No error is returned for a file problem.

**File handling.** `New` creates the parent directory (`MkdirAll`, 0755), then
opens the file with `O_APPEND|O_CREATE|O_WRONLY` (0644). The handler writes to
`io.MultiWriter(stderr, file)`. The returned `io.Closer` closes the file. It is
never nil. After a fallback it is a no-op. Callers may `defer` it or skip it in
a long-running process, because the OS closes the file on exit and `slog` does
not buffer.

**Fallback warning.** If the directory or file cannot be created or opened, `New`
still succeeds and the logger writes to stderr only. Before returning it writes
one record at `WARN` directly through the handler to the stderr sink:
message `cannot open log file, logging to stderr only`, attrs `path=<path>` and
`error=<open error>`. The record bypasses the level filter, so `LOG_LEVEL=error`
does not hide it. It uses the configured format (text or JSON).

Blocking findings: none.

- **Spec intent.** One handler over `io.MultiWriter(stderr, file)` with one
  `HandlerOptions{Level}`, so level and format apply to both sinks alike, as the
  spec's "Level and format" bullet requires. The file is opened
  `O_APPEND|O_CREATE|O_WRONLY` after `MkdirAll`, with no `O_TRUNC`, which is the

  stderr-only logger. Calling `h.Handle` directly bypasses the level filter, so
  `LOG_LEVEL=error` cannot hide it. That matches "startup logs a warning and

  error, which there is nowhere to report.
- **Invalid level or format.** `New` returns an error instead of picking a default,
  so no silent fallback exists even for a direct caller. `config.Load` already
  rejects both values first, so a caller wired to it cannot hit this.
- **Tests.** Every test uses `t.TempDir()` and a `bytes.Buffer`, so nothing writes
  to the real `logs/` or stderr. Both sinks are asserted separately in the level,

  `TestContextHelper` covers the empty context, `ctx2`, a `WithCancel` child and
  the original context.
- **Exported API fits ING-053 and ING-054.** `New(level, format, path, stderr)

  straight in. `New` does not install `slog.Default()`, which the ING-054 ticket
  leaves to that Coder. `FromContext` returns `slog.Default()` when no logger is

**Tester's edge notes, judged.** None needs a fix.

1. **`WithLogger(ctx, nil)`: acceptable, no fix.** A nil logger panics on first use.
   No AC covers it, and both callers (ING-053, tests) pass a real logger. A guard
   would add a branch for a case nobody hits, and `slog.Default()` returned silently
   would hide the caller's bug.
2. **Level parser looser than `config.Load`: acceptable, no fix.** `UnmarshalText`
   also accepts upper-case and forms like `warn+2`. `New` is fed the already
   validated lower-case value, so the extra forms are unreachable through the
   wired path. Rejecting them would duplicate `config.Load`'s validation, which the
   ticket says not to redo.
3. **JSON open-failure warning untested: acceptable, no fix.** The warning goes
   through the same `h` the tests already exercise in JSON format
   (`TestJSONFormat`) and in fallback with text (`TestOpenFailureFallsBackToStderr`).
   No separate code path exists for the JSON case, and the ticket asks only that the
   warning reach the stderr sink. ING-054's JSON startup test also covers the
   configured handler end to end.
4. **`io.MultiWriter` stops at the first failing writer: acceptable, no fix.**
   Stderr is listed first, so a broken stderr would skip the file. `slog` ignores
   write errors, real stderr does not fail in normal runs, and a per-writer
   tolerant multiwriter is speculative for a single-user local app.
