### [ING-012] Ingestion pipeline: photo path → validated tagged JSON (no DB)

**As a** wardrobe owner
**I want** a runnable pipeline that takes a garment photo path, builds the
VLM client from config (configured temperature + opt-in serialization),
validates the response using the settled retry-once policy, and emits the
tagged JSON
**So that** I can actually run a photo through the Phase 1 tagging
pipeline end to end — this sprint's "photo → tagged JSON" outcome —
without waiting for the catalog store or the grid UI, which are the next
sprint

**Acceptance criteria** (Gherkin):
```
Given a garment photo path and a reachable VLM configured from the
  environment
When the photo is passed through the ingestion pipeline
Then a JSON object is emitted containing all seven validated tagging
  fields (category, subcategory, dominant_color, secondary_colors,
  pattern, warmth_tier, formality) plus the original photo_path
And no catalog row is written and no data/wardrobe.db is created

Given VLM_TEMPERATURE and VLM_SERIALIZE_REQUESTS are set
When the pipeline builds its VLM client from config
Then every tagging request carries the configured temperature read fresh
  per call, and VLM_SERIALIZE_REQUESTS=true enables the ING-003
  serialized queue — i.e. the config→client wiring ING-003 and ING-007
  deferred to "the future handler/route ticket" is applied

Given a photo whose attempt-1 response fails validation (ING-004)
When the pipeline processes it
Then the per-photo retry/flag behavior and the logs/vlm-attempts.jsonl
  records are exactly ING-005's, driven through this pipeline

Given a batch in which one photo is flagged for manual review
When the batch is processed
Then the remaining photos still emit tagged JSON and the flagged photo is
  reported separately, without aborting the run

Given the VLM is unreachable while processing a photo
When the pipeline processes it
Then the ING-002 ErrVLMUnreachable error surfaces distinctly, is not
  treated as a malformed-output flag, and is not retried into one

Given the documented invocation with a photo path or a directory of
  photos
When it is run
Then it prints the tagged JSON to stdout and exits 0 on success, and
  exits nonzero on a hard error (VLM unreachable, missing photo)
```

**Spec reference:** `05-vlm-tagging-spec.md` "Input", "Model", "Prompt",
"Output validation", and "Acceptance criteria (for the first ingestion
ticket)"; `04-data-schema.md` (the seven tagging fields the emitted JSON
carries); `06-decisions.md` "Malformed VLM output: retry once at nonzero
temperature, then flag"; `07-architecture.md` "Runtime model", "VLM
request behavior", and "Env var contract"

**Depends on:** ING-002 (VLM client), ING-003 (opt-in serialization),
ING-004 (parse + validate), ING-005 (retry/flag processor and attempt
log — **now Done**), ING-007 (temperature payload). All are Done or in
Review; this ticket wires and drives ING-005's processor, it does not
reimplement it.

**ING-005's implemented API** (`internal/tagging/processor.go`, for
wiring — no design work needed here):
- `tagging.NewProcessor(client, opts...) *Processor`
- `(*Processor).Process(ctx, photoPath) (Outcome, error)`
- `Outcome{ItemID, PhotoPath, Result, Flagged, Attempts}` — `ItemID` is
  generated inside `Process` (UUIDv4), so ING-012 must **not** generate
  its own.
- A `nil` error means success *or* flag — check `Outcome.Flagged`. A
  non-nil error is a hard failure (VLM unreachable, transport/envelope,
  or attempt-log write) and is neither retried nor flagged.
- The default attempt logger appends to `logs/vlm-attempts.jsonl`
  relative to the process CWD.

**Open integration points ING-005's review left to this ticket:**
1. On a hard error after attempt 1 was already logged, `Process` returns
   `Outcome{}` — the first attempt's detail is on disk but absent from
   the returned value. Decide how this layer surfaces it (report the
   photo path + error and rely on the log, or attach the partial
   attempt).
2. The default attempt-log path is CWD-relative; the CLI must run from
   the project root or pass an explicit logger path so attempts land in
   the repo's `logs/`.
3. **Recommended, needs Ali's confirm:** emit `Outcome.ItemID` alongside
   the seven tagging fields. ING-005 generates it and the attempt log
   keys on it; carrying it out now lets the next sprint's store row
   reuse the same id and keeps the `later-ideas.md` calibration join
   intact. Without it, the next sprint mints a fresh uuid and the log no
   longer joins to the row.

**Out of scope (next sprint — "ingestion: JSON → DB row + grid UI"):**
`internal/store`, GORM/SQLite, `data/wardrobe.db` writes, the catalog
store columns `added_date` / `notes`, any Gin route, and the frontend.

**Entry point — needs Ali's confirmation:** no approved spec names how the
pipeline is invoked. This ticket proposes the minimal default: a small CLI
entry point (e.g. `cmd/ingest`) so the sprint can be "actually used"
without pulling in Gin. A Gin HTTP route is the alternative, but
`ING-001`'s approval condition attaches to the first route-bearing ticket
(wire Gin, make the listen address configurable, remove the empty-mux
placeholder), which would expand this ticket well past one Coder pass.
Confirm CLI, and this stays `Ready`; if a route is wanted instead, this
ticket must be re-scoped before Coder starts.
